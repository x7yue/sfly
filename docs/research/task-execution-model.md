# 执行器的进程模型：「一个任务一个进程」的开销与替代方式

调研日期：2026 年 11 月。背景是 issue #76：每个包节点的每次执行（每个任务、每次重试）都由 Agent 新启动一个执行器进程 `python -I -u -m sfly.runner`（`agent/src/executor.rs`、`sdk/python/src/sfly/runner.py`，ARCHITECTURE §5.4），一条链上有大量短节点或依赖很重的节点时，启动和导入会不会成为瓶颈，要不要换一种执行方式。

完整测量数据（三轮，含方法、机器、提交号、样本量）在 #76 的评论里：[第一、二轮][data]、[第三轮（原型实测）][data3]。本文只写结论和关键数值。

## 1. 结论

1. **保持「一个任务一个进程」**。任务之间的隔离写进语义规范，作为对用户的承诺（SEMANTICS §3.5）。常驻进程池和进程内执行不再考虑。
2. **先做不改进程模型的优化**：SDK 和执行器推迟导入用不到的标准库，缩短「解释器启动到开始导入节点模块」这一段（原来约 23 ms）。已在 #142 完成，见 §3.2。
3. **不做**：
   - Agent 安装节点包时生成字节码（§3.3）；
   - 执行器写完结果就上报、不等进程退出，或用 `os._exit` 跳过解释器退出（§3.4）；
   - 备用进程、一条链一个执行器、在 Agent 进程里嵌入 Python（§3.5）。
4. **forkserver 已经越过门槛，但暂不做，以后再决定**。原定的门槛是：延迟导入合入之后，sfly-std 短节点的「解释器启动 + 导入」**占每节点端到端耗时的一半以上**，而且**绝对值不低于 50 ms**。延迟导入（#142）合入后，空节点每个从 45 ms 降到 37 ms，sfly-std 节点不变（约 105 ms）：httpx 本来就会导入被推迟的那些标准库，「解释器启动 + 导入」仍约 58 ms、占 55%，两条都满足。第三轮用原型实测（§2.3），forkserver 在单链、并发和内存上都明显最好。但它要重新设计执行器和 Agent 的父子关系、模板进程的生命周期，以及节点模块在导入阶段的语义。维护者决定（2026-11-08）**先保持现状**，以后再定；重新开始时从 §4 的设计草案出发。复测仍用 `pnpm perf` 的「短节点链路」一项。

这件事要解决的是**链路延迟**：编排是单链（ADR 0001），一条链上的节点依次执行，每个节点的启动和导入开销会串行叠加，槽位再多也帮不上。内存和吞吐是次要目标。

## 2. 测量结果

本机：i5-1135G7（4 核 8 线程），7.2 GiB 内存，Python 3.13.18。数值是中位数，只用于相对比较。

### 2.1 端到端：一个节点的时间花在哪里

测法：打包后的控制面 + PostgreSQL + release Agent，跑 30 个节点的单链，临时打点拆出各段。节点模块已有字节码。

| 节点 | 每节点总耗时 | 解释器启动 + 导入 sfly | 导入节点模块 | 执行 | 进程退出 | 控制面派发 | Agent 自身 | 30 节点整条链 |
|---|---|---|---|---|---|---|---|---|
| 空节点 | **46** | 31 | 0 | 0 | 6.5 | 7 | 1 | 1.4 s |
| sfly-std `http_request` | **106** | 31 | 27 | 20 | 16 | 11 | 1 | 3.3 s |
| pandas 节点 | **318** | 31 | 218 | 0 | 52 | 17 | 1 | 9.6 s |

- **时间主要花在进程本身**：启动、导入和退出合计占每节点耗时的 70–94%。控制面派发 7–17 ms，Agent 自身（写 `task.json`、建 FIFO、启动进程、回报）约 1 ms。
- `http_request` 的「执行」20 ms 里大半也是导入：第一次创建 `httpx.Client` 时才懒加载 httpcore、anyio、certifi 等，并加载 CA 证书包。
- 导入 sfly 的约 23 ms 几乎都花在它引用的标准库上：json/re/enum 约 8 ms、inspect 约 6 ms、traceback、urllib.parse、typing 各约 3.7 ms、pathlib 约 3 ms。

### 2.2 执行器单独测：几种执行方式的对比

测法：不经过控制面和 Agent，直接按 Agent 的方式启动执行器，同时写了 forkserver 和常驻进程的原型做对照（ms）。

| 方式 | 空节点 | pandas 节点 |
|---|---|---|
| 现状：每个任务启动新解释器 | 37 | 306 |
| 现状，节点包刚安装、还没有字节码 | – | 1145 |
| forkserver，只预导入 sfly | 2.4 | 230 |
| forkserver，预导入 sfly 和节点模块 | – | 3.5 |
| 常驻进程（第二次起） | 0.17 | 0.21 |

- 只预导入 sfly 的 forkserver，每个节点只省约 30 ms（再加上退出的那段）。要让依赖重的节点明显变快，必须连节点模块一起预导入。
- 内存：4 个 pandas 任务同时运行，独立进程合计 PSS 185 MB。forkserver 在 fork 前 `gc.collect(); gc.freeze()` 后是 72 MB；不 freeze 的话，子进程一跑 GC 写时复制就失效，变成 137 MB。常驻进程不能共享内存，仍是 185 MB。

### 2.3 原型实测：备用进程和 forkserver（第三轮）

测法：在 #142 之后的 main 上写原型，用真实的控制面和 release Agent 跑「短节点链路」（30 个节点的单链），另测两种不利情况、内存和节点包第一次运行。

- **备用进程**：每个任务开始时，Agent 为同一个节点包预先启动一个新进程，导入好 sfly 和节点模块；下一个任务直接交给它，用完退出，不复用。
- **forkserver**：每个「节点包 @ 版本」一个单线程的模板进程，预导入整个包，每个任务从它 fork 一个执行器。

| | 现状 | 备用进程 | forkserver |
|---|---|---|---|
| 单链每节点（ms）：空节点 / sfly-std `http_request` / 重依赖节点 | 37 / 106 / 286 | 26 / 71–81 / 195–210\* | 27 / 47 / 27 |
| 30 节点整条链（s）：同上三类 | 1.15 / 3.3 / 8.6 | 0.77 / 2.2–2.5 / 5.4–6.1 | 0.84 / 1.45 / 0.87 |
| 4 条重依赖链并发，每条链（s） | 14.9 | 12.7 | 1.6 |
| 4 个重依赖任务同时运行，合计 PSS（MB） | 144 | 278 | 52 |

\* 备用进程的重依赖链快慢交替，取平均值。

- **forkserver 真正少做了工作**，所以并发时同样有效。剩下的约 19 ms 里有 16 ms 是执行器正常退出：解释器要清理从模板继承来的整个堆，触发写时复制。模板里预导入了重模块之后，同一个包里的轻节点退出也会变慢（4.9 → 18.5 ms）。
- **forkserver 的第一个任务要等模板导入完整个节点包**：和重依赖节点同包的空节点，第一个任务从约 190 ms 变成约 410 ms，从第二个任务起恢复正常。
- **备用进程只是把导入挪到上一个节点运行时去做**，CPU 工作一点没少：导入比一个节点周期长时就赶不上下一个任务；CPU 本来就满的并发场景只快 0–15%。每个正在执行的任务各备一个进程，内存几乎翻倍。链上交替换包、并按方案丢弃别的包的备用进程时，比现状还慢 3–18%。
- 实现规模：备用进程约 220 行，几乎不碰现有的进程语义；forkserver 约 350 行，而且原型省略了模板崩溃、Agent 退出时的清理（#113）、安装后重建、数量上限、预导入声明和回退路径（§4）。
- **fork 的连带影响**：所有执行器共享模板的 `PYTHONHASHSEED`，集合和字典的迭代顺序在各任务之间都相同（现状下每个进程各不相同）。节点模块在任务开始之前导入，导入时没有 `SFLY_*` 环境变量，当前目录也不是任务目录。

## 3. 各种做法的对比

### 3.1 成熟系统的五类做法

| 做法 | 代表 | 隔离 | 超时 / 取消 | 和 sfly 的契合度 |
|---|---|---|---|---|
| A. 每个任务启动新解释器（现状） | [Prefect 3 process worker][prefect3]（新会话 + killpg，SIGTERM → 30 s → SIGKILL）、RQ SpawnWorker、Airflow 3 在 macOS 上 | 最干净 | 杀进程组，可靠 | 已经在用；慢在启动和导入 |
| B. 每个任务从预热好的进程 fork | [Airflow 3][airflow-sup] 默认（先导入 task_runner、`gc.freeze()` 再 fork）、RQ 默认 Worker | 每个任务一个新进程，但继承父进程的线程、锁和连接 | 杀进程组，可靠 | 父进程必须单线程。[Airflow #71707][airflow-71707]：fork 时父进程的线程正持有 OpenSSL 锁，任务第一次发 TLS 请求就永久挂住。Agent 是多线程的 tokio 进程，自己不能 fork，所以这条路对 sfly 来说就是 C |
| C. forkserver / Zygote | Python 3.14 起 POSIX 的[默认启动方式][py-mp]、[Dagster multiprocess][dagster-mp]（`forkserver` + `preload_modules`，明确不支持 fork）、[PySpark daemon][spark-daemon]、Android Zygote | 和 B 一样，但模板进程是专门起的、干净的单线程进程 | 子进程不是 Agent 的直接子进程，pid 和退出状态要由模板进程回报 | **最贴近现有语义** |
| D. 常驻进程池 | [Celery prefork][celery-request]、Huey、Dramatiq、Gunicorn、Ray、Bazel persistent workers | 全局状态、内存泄漏、后台线程跨任务残留，只能靠 max-tasks / max-memory 定期换进程 | Celery 硬超时是 SIGTERM，0.1 s 后 SIGKILL，**再补一个进程**；`revoke(terminate)` 可能误杀已经在跑下一个任务的进程 | 违背任务之间互不影响 |
| E. 进程内线程 / 子解释器 | Celery solo/threads、Temporal 线程模式 activity、3.14 的 `InterpreterPoolExecutor` | 最弱 | 线程注入异常打断不了卡在 C 代码里的调用；[子解释器][py-interp]无法销毁正在运行的解释器 | 不可行：numpy 不支持子解释器 |

D 和 E 被隔离承诺排除（SEMANTICS §3.5）。测试平台最怕前一个用例污染后一个用例，取消和超时也要靠杀进程组兜底。剩下 A（现状）和 C（forkserver）。

### 3.2 不改进程模型的优化

| 优化 | 能省多少 | 决定 |
|---|---|---|
| 延迟导入标准库 | 实测空节点每个 -8 ms（45 → 37 ms）；sfly-std 和重依赖节点不变，因为它们的依赖本来就会导入这些模块（#142） | 已做 |
| 安装时生成字节码 | 首次运行变快，但编译更贵 | 不做（§3.3） |
| 写完结果就上报 / `os._exit` | 每个节点 6–52 ms（退出的那段） | 不做（§3.4） |

### 3.3 为什么不在安装时生成字节码

节点包刚安装、还没有 `.pyc` 时，第一次运行要多付编译时间（pandas 节点从 0.3 s 变成 1.1 s）。但 Agent 是在**第一个任务到达时**才安装节点包的，编译时间也算在这个任务上，而且 `uv pip install --compile-bytecode` 会编译包里的所有文件，不只是实际导入的：

| 节点包 | 安装时多花 | 首次运行省下 | 净效果 |
|---|---|---|---|
| pandas | +1.8 s（编译 1890 个文件） | 0.8 s | 慢约 1 s |
| sfly-std（httpx、psutil） | +133 ms | 约 98 ms | 基本持平 |

现在的做法是第一次导入时由 Python 只编译实际用到的模块，并写回共享 venv，之后的任务都用缓存。只有安装能提前、不阻塞第一个任务，或者 site-packages 不可写时，预编译才划算。

### 3.4 为什么不提前上报结果

执行器写完 `output.json` 之后还要退出解释器：空节点 6.5 ms，`http_request` 16 ms，pandas 52 ms。有两种办法能省掉这段：Agent 看到结果就上报、进程留在后台慢慢退出；或者执行器用 `os._exit` 直接跳过退出流程。两种都不做：

- 节点注册的 atexit 处理和非守护线程，可能还在运行时下一个任务就开始了；用 `os._exit` 的话，它们干脆不会执行；
- 退出阶段输出的日志会排在结果之后；
- 槽位会被还没退出的进程多占一会儿；
- 违反隔离承诺里「任务结束 = 执行器进程已经退出」这一条（SEMANTICS §3.5）。

### 3.5 其他讨论过、决定不做的方向

| 方向 | 为什么不做 |
|---|---|
| **备用进程**（§2.3） | 只是把导入挪到上一个节点运行时去做：重依赖链快慢交替，CPU 饱和时几乎没有收益，内存翻倍，交替换包的链还更慢。各方面都不如 forkserver。 |
| **一条链一个执行器**：一条链（主链或一个子流程）上的包节点依次在同一个进程里执行 | 这是做法 D 限定在一条链内。估计每个节点能降到 15–20 ms，比 forkserver 再省约 30 ms，但代价是：<br>① 推翻隔离承诺（SEMANTICS §3.5 第 1、2 条），重试也在失败留下的进程里跑；<br>② 链内共享的状态会被超时或取消、节点换 Agent、等待节点、中途安装、Agent 重启打断，用户既不能依赖它，又躲不开污染；<br>③ 一个节点超时时，会连带终止前面节点留在进程组里的后台进程（§3.5 第 4 条）；<br>④ `SFLY_*` 环境变量、当前目录、标准输出要按任务切换，留在后台的线程打的日志会算到下一个节点头上；<br>⑤ 控制面要按链派发、通知 Agent 回收进程；<br>⑥ 很短的链和多链并发时不如 forkserver。<br>链内节点确实需要共享连接或会话时，应作为显式功能另行设计，不靠进程复用顺带得到。 |
| **在 Agent 进程里用 PyO3 嵌入 Python** | 三种做法都不成立：<br>① 任务直接在 Agent 进程里执行，就是做法 E，Agent 还会被节点的段错误、内存泄漏、改环境变量或当前目录拖累；<br>② 从多线程的 tokio 进程 fork，就是做法 B，子进程会被其他线程持有的锁（malloc、TLS、GIL）挂住；<br>③ Agent 启动时、还是单线程的时候先 fork 一个嵌入 Python 的助手，它本身就是模板进程，只是用 Rust 写，还要让 Agent 二进制在运行时链接共享 venv 里的 libpython，和 ADR 0002、0010、0012 冲突。 |
| **改用 Python 写 Agent，让 Agent 自己当模板** | Agent 当不了模板，和语言无关：<br>① Agent 要维持 gRPC 流、转发多个任务的日志、上传产物、安装节点包，天生是多线程的；[Airflow #71707][airflow-71707] 就是 Python 写的 supervisor 自己 fork 时被 TLS 锁挂住；<br>② Agent 必须和共享 venv 隔离（ADR 0002），导入不了节点包；<br>③ 每次安装都要重建模板，Agent 不能跟着重启。<br>换成 Python 后，模板进程照样省不掉，反而丢掉单个静态二进制、自更新等选 Rust 的理由（ADR 0003）。 |

## 4. 如果要做 forkserver：设计草案

下面是 2026-11-08 讨论时的倾向，**都还没有定**，重新开始时逐条确认。原来列出的问题和当时的倾向：

- **按什么分组**：每个「节点包 @ 版本」一个模板进程。倾向于模板启动时只导入 sfly，某个节点的第一个任务到达时，才把它的模块导入模板再 fork。这样同一个包里没用到的重模块不进模板，避开 §2.3 里轻节点第一次运行多等约 200 ms、每次退出多约 11 ms 的问题。另外两种方案：模板启动时导入包里全部节点模块（原型的做法），或每个节点模块一个模板（模板数量成倍增加）。共享 venv 有任何安装或切换时，**丢弃全部模板**，因为一个包的安装可能升级其他包已经导入的公共依赖；安装本来就和启动新任务互斥（ADR 0002），而且很少发生。不提前预热，模板在这个包的第一个任务到达时才建。类似的分组方式：Spark 按解释器加环境变量，Ray 按 runtime_env 哈希，Bazel 按 WorkerKey。
- **预导入用户模块的副作用**：节点包在导入时可能起线程、开连接、读配置或环境变量，这些都会被所有 fork 出的执行器继承，而且导入时看到的环境和现状不同。倾向于只给**主动声明了可以预导入**的节点包建模板：在 `pyproject.toml` 的 `[tool.sfly]` 里声明，`sfly build` 写进 `sfly-package.json`，sfly-std 第一个声明。模板每次导入后检查只剩 1 个线程，不满足时作废这个模板，这个包在本次 Agent 运行期间都退回现状，并写一条警告日志。已打开的连接和文件查不出来，靠声明保证。Agent 另设一个总开关，供运维紧急关闭。默认开启的话收益覆盖面更大，但用户的包一旦在导入时起线程，就会出 [Airflow #71707][airflow-71707] 那种问题。
- **pid、退出状态和进程组**：执行器 fork 出来后先 `setsid`，模板把 pid 回报给 Agent；Agent 把这个进程组登记进 Agent 退出时要终止的进程树（#113），超时和取消照旧终止进程组。执行器退出后，模板 `waitpid` 拿到原始退出状态再回报，Agent 收到后才算任务结束（SEMANTICS §3.5 第 2 条）。执行器的标准输出和标准错误用命名管道，和事件管道的做法一致（ADR 0015），不用 SCM_RIGHTS。模板意外退出时，终止它手上执行器的进程组，任务失败（错误类型待定：`node_error` 会按 `retries` 重试，`env_error` 不会），下一个任务到达时重建模板。不让 Agent 当 child subreaper：脱离进程组的后台进程也会挂到 Agent 名下，要由它回收，牵连太广。Spark、Zygote 都是由模板代为回报退出状态。
- **内存**：fork 前执行 `gc.collect(); gc.freeze()`。按 ADR 0002，同一个包只会装着一个版本，所以模板数量不会超过声明了预导入的已安装包的个数。实测 sfly-std 的模板约 23 MB，重依赖包约 40 MB。倾向于上限等于槽位数，按最近使用淘汰空闲的模板（手上还有执行器的不淘汰），不设空闲超时。
- **两套行为**：下面这些情况仍用现状：Windows Agent（路线图 P4，没有 fork）、没有声明预导入的包、开发版本 `包名@dev`（源码随时在改）、模板启动失败或线程检查不通过、总开关关闭。本地调试 `sfly run` / `sfly.testing` 一直用现状，不模拟模板。
- **命名**：倾向于在 GLOSSARY 里定两个名字。**执行器**指执行一个任务的那个进程，每个任务一个，不管是新启动的还是 fork 出来的。**执行器模板**指预先导入了 SDK 和节点模块、用来 fork 执行器的常驻进程，避免叫 forkserver、zygote、预热进程、worker、进程池。

还没讨论到的：

- **SEMANTICS §3.5 要改的地方**：第一句「新启动的执行器进程」；声明了预导入的包，模块级代码在每个模板里只执行一次，而且是在任务开始之前、在任务的环境变量和工作目录之外执行（本地调试时每个任务都执行，两边不一致）；各任务的 `PYTHONHASHSEED` 相同。
- **节点模块在模板里导入失败时**怎么报告给这个任务，模板是否要因此重建（失败的导入可能已经留下部分子模块和副作用）。
- **执行器退出那 16 ms** 来自清理继承来的堆。`os._exit` 已被 §3.4 排除，目前没有别的办法。
