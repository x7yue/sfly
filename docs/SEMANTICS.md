# 场景执行语义规范

> 状态：草案 · 2026-11-04（术语随 #25 更新：「编排」作名词改为「场景」，「编排」只作动词）
> 术语以仓库根目录的 `GLOSSARY.md` 为准。本规范定义场景"是什么、怎么跑"，与实现语言无关；引擎、画布、Agent 的行为都必须与本规范一致。

---

## 1. 场景结构

### 1.1 组成

一个**场景**的链路由以下部分组成（场景的名称、说明、运行通知的设置、运行预设和关注项不属于场景版本，见 §6）：

- **主链**：从唯一的**入口节点**开始的一条链。
- **子流程**：零个或多个，每个从唯一的**子流程入口节点**开始，也是一条链。子流程入口声明子流程的**名称**（必填，场景内不重复；没有名称的旧版本以节点 ID 作为名称）。
- **默认 Agent**：场景级配置，未单独选择 Agent 的包节点都派发到它上面。

### 1.2 链的规则

| 规则 | 说明 |
|---|---|
| 单入单出 | 链上每个节点最多一条入线、一条出线；不分叉、不汇合、不成环 |
| 起点唯一 | 主链只有一个入口节点；每个子流程只有一个子流程入口节点 |
| 无结束节点 | 链的最后一个节点完成，这条链就结束 |
| 调度连线 | 异步任务节点除链上的出线外，另有一条**调度连线**，连到恰好一个子流程入口节点 |
| 子流程被触发方式 | 每个子流程入口节点恰好被一个异步任务节点连接 |
| 嵌套 | 子流程里可以再放异步任务节点；嵌套深度最多 3 层（主链为第 0 层）。由此一次运行里每个子流程最多有一个实例 |
| 无孤立节点 | 每个节点都必须位于某条链上 |

结构规则和引用规则（§2.4）在**保存时只产生警告**，编排到一半的场景也可以保存；**触发时必须全部通过**（注释框的警告除外，见 §1.6：它只提示，不阻断触发）。

并行**只能**通过异步任务节点触发子流程产生；链本身永远是顺序执行。

### 1.3 节点种类

| 种类 | 执行位置 | 说明 |
|---|---|---|
| 入口节点 | 控制面 | 声明场景参数，运行开始时立即完成 |
| 子流程入口节点 | 控制面 | 声明子流程参数，子流程实例创建时立即完成 |
| 异步任务节点 | 控制面 | 创建一个子流程实例后立即成功，主链继续往下执行 |
| 停止子流程节点 | 控制面 | 停止本链触发的某个子流程，等它完全结束后完成（§4.1） |
| **包节点** | Agent | 节点类型来自已发布的节点包，在选定的 Agent 上执行 |

只有包节点需要选 Agent；内置节点不占用 Agent。

**已移除的节点种类**（ADR 0028）：飞书通知节点（`feishu_notify`）、定时节点（`timer`）、Sleep 节点（`sleep`）已不再支持，登记在 `@sfly/schema` 的 `REMOVED_NODE_KINDS`（种类名、原来的名称、替换办法）。移除之前保存的版本和运行里还留着这种节点，只读显示，配置原样保留，不执行，节点显示成「已移除的节点类型 timer」这样的名称：文档检查给出警告 `node_kind_removed`（写明替换办法），触发被预检阻断（§6 第 2 条）；保存新版本的请求里不能带这种节点，要先把它从场景里删掉。升级前开始、升级时还在运行的运行，推进到它时它按 `config_error` 失败（不重试），后面的节点按失败的规则推进（§3.2），不影响别的运行。

- 飞书通知节点：通知只剩两条路，节点代码里的 `ctx.notify`，和运行失败或被取消时的运行通知（§4.2）；替换办法是在节点代码里用 `ctx.notify` 发飞书消息。
- 定时节点、Sleep 节点：见 §5。

### 1.4 显示名称

除子流程入口节点外，每个节点都可以有一个可选的 `display_name`（显示名称）：一行文字，最长 40 个 Unicode 字符（按字符计，一个 emoji 算一个），不能换行，去掉首尾空白后为空就不保存，不要求唯一。子流程入口节点没有这个字段：子流程名称（`name`）就是它的显示名称。

- 它只用于显示：卡片标题是显示名称，原来的标题挪到卡片头部；卡片以外写成「显示名称（节点 ID）」，没有显示名称时只写节点 ID。
- **显示名称不影响执行**：不参与引用（引用、停止子流程节点的目标、日志和接口仍然以节点 ID 为准）、派发，也不影响保存时的警告和触发时的校验。
- 它和节点的位置一样属于场景版本的内容（ADR 0023），只改显示名称也会保存出新版本。

### 1.5 备注

所有节点种类都可以带一份可选的 `note`（备注）：多行文字，写这个节点在场景里做什么、为什么这样配置，最长 2000 个 Unicode 字符（按字符计，一个 emoji 算一个，换行也算一个），去掉首尾空白后为空就不保存。

- 它只用于显示：画布上节点卡片的头部有备注图标，悬停或键盘聚焦时显示全文；版本对比和 `sfly scenario show` 会列出它。
- **备注不影响执行**：不参与引用（里面写 `${{ … }}` 也不会被解析）、校验、派发和日志，超过长度才会让保存失败。
- 它和节点的位置一样属于场景版本的内容（ADR 0023），只改备注也会保存出新版本，运行显示的是它绑定的那个版本里的备注。

### 1.6 注释框

场景文档顶层可以有 `annotations`（注释框，默认是空数组），给一组节点和子流程写说明。每个注释框有：`id`（注释框之间唯一，重复时文档不合法、保存失败）、`title`（标题：一行，去掉首尾空白后 1 到 40 个 Unicode 字符）、可选的 `note`（备注，规则同 1.5）、可选的 `color`（颜色：`gray`、`blue`、`green`、`yellow`、`orange`、`pink` 之一，不写就是灰色，只用于在画布上分开几个注释框，ADR 0025）、`nodes`（成员节点的节点 ID）和 `subflows`（成员子流程的子流程入口节点 ID，子流程改名不影响）。子流程成员连同它直接或间接触发的下级子流程：框住整棵子流程树，下级子流程不用再写。

- 它只记成员，不存坐标和大小：画布上框的范围由成员算出，算法和子流程区域相同（节点成员取卡片，子流程成员取它和它下级子流程的区域；外接框四周留白），成员移动、往子流程成员里加节点时框跟着变（ADR 0023）。
- 一个节点可以同时在几个注释框里；删除节点时它从所有注释框里去掉，删除子流程入口时这个子流程从注释框里去掉，因此没有成员的注释框一起删除。
- **注释框不影响执行**：不参与引用和派发，不影响触发时的校验，也不形成任何「分组」语义（不能按注释框重试、停止）。
- 注释框写错时保存只给**警告**，不阻断保存，也不阻断触发（触发前的预检不看这些警告）。警告的结构和别的警告一样是 `{code, message, node_id?, input?}`，另有可选的 `annotation_id`（出问题的注释框的 `id`；注释框的警告没有 `node_id`）。`message` 写出注释框的标题和 ID，提到节点时写成「显示名称（节点 ID）」，例如「注释框「造测试数据」（annotation_1）引用了不存在的节点 http_request_9」。有三种情况，分四个 `code`：
  - `annotation_unknown_node`：`nodes` 里写了场景里不存在的节点；
  - `annotation_unknown_subflow`：`subflows` 里写的不是子流程入口节点的节点 ID（不存在，或者是别的节点，或者写成了子流程名称）；
  - `annotation_no_members`：`nodes` 和 `subflows` 都是空；
  - `annotation_duplicate_member`：同一个节点在 `nodes` 里写了几次，或者同一个子流程在 `subflows` 里写了几次，每个成员警告一次并写出次数。同一个节点既写在 `nodes` 里又写在 `subflows` 里不算重复：节点成员只框它的卡片，子流程成员框整个子流程。
- 引用了不存在成员的注释框（只会来自命令行 push）：画框时跳过不存在的成员，一个有效成员都没有的注释框不画；画布打开、保存时都不自动清理这些成员（用户没改什么，保存后就不会多出一处变化）；画布的校验面板列出警告，「前往」选中这个注释框。
- 它和节点的位置一样属于场景版本的内容（ADR 0023），只改注释框也会保存出新版本。


### 1.7 已移除的便签

场景文档顶层曾有 `sticky_notes`（便签：画布上自由摆放、不挂在任何节点上的说明，ADR 0026），已移除（ADR 0028）：场景文档没有这一项，画布和整理布局里也没有便签。说明一个节点写进节点的备注（1.5），说明一组节点写进注释框的备注（1.6）。

- **存量数据**：ADR 0026 之后保存的每个版本都带着 `sticky_notes`（默认是空数组，也可能有内容）。这些版本不改、不写迁移；控制面读库时丢掉这个字段，读到的文档里没有它，所以读取不报错也不显示（画布、版本对比、`sfly scenario show`、`sfly scenario pull` 都没有便签），保存新版本时也不再带上它。已移除的顶层字段登记在 `@sfly/schema` 的 `REMOVED_DOCUMENT_FIELDS`（字段名、原来的名称、替换办法）。
- **保存**：文档里没有 `sticky_notes` 或是空数组：接受并丢掉，不报错，新版本里没有它（读出来改一处再存回去照常可用）；数组里有内容：保存被拒绝（400 `invalid_document`，写明有几条，先把要留的内容写进节点的备注或注释框的备注，再把这一项删掉）；`sfly scenario push` 的本地检查报同样的说明。画布保存、恢复历史版本、复制场景产生的新版本都不带它。升级后有内容的便签读不到了（版本里还在，查库能读到）：升级前把内容导出，办法见 ADR 0028「第 3 步」。
- **不影响执行**：便签不执行，没有引用，不阻断触发（预检不看它，§6 第 2 条），也没有警告。

## 2. 参数与引用

### 2.1 参数声明

入口节点和子流程入口节点声明参数，每个参数包括：`name`、`type`（`string | number | boolean | json`）、`default`、`required`、`secret`，以及可选的 `description`。

- 手动触发运行时，用户填写入口节点的参数；缺少必填参数时拒绝触发。可以选用场景的一个运行预设（§6 第 6 条）：预设参数取预设保存的值、不能修改，其余参数照常填写。
- `secret` 参数在界面和日志中打码显示，数据库中明文保存。**打码按值匹配**，要换掉的东西只有一份（`apps/server/src/logs/secrets.ts` 的 `SecretSet`），读取运行（运行视图、列表、事件流、关注项……）、写日志和动作、触发时的报错用的都是它。规则（#479 的决定）有六条：
  1. **secret 参数本身**读出来是掩码，不论类型：运行和各个链实例的参数里，声明为 secret 的参数整个读成 `******`（没有值和空串没有什么可隐藏的，原样）。
  2. **值是字符串、数字、布尔的 secret 参数**：按值打码，不论多短（使用者对这一个值明确说了保密）。数字、布尔按它们的 JSON 文本（`4242`、`true`）匹配，数字另外认节点（Python）打印它的写法（见下面「数字的写法」）；字符串还连同它在 JSON 里的转义写法（引号、反斜杠、换行；非 ASCII 字符和 DEL 再加 Python `json.dumps` 默认的 `\uXXXX` 写法，小写十六进制）一起匹配，因为日志里常常是 JSON 写出来的样子。
  3. **值是对象或数组（`json` 类型）的 secret 参数**，它里面的值出现在别处时：字符串和数字的叶子，写出来**不少于 4 个字符**的（`MIN_LEAF_CHARS`；字符串按字符数算，数字按它的 JSON 文本算）按值打码，字符串叶子同样带转义写法；更短的叶子（`a`、`1`、`on`）、布尔和空值（空串、`null`）不单独打码，只在整个对象被原样写出时随整段一起盖住：整段的写法有紧凑写法和 Python `json.dumps` 默认的写法（`", "`、`": "` 分隔），键按「节点收到时的顺序」和「参数里写的顺序」两种，各自带或不带 `\uXXXX` 转义（`ensure_ascii`）。键不算。没有任何可打码内容的（`{}`、`[]`、`[[]]`、只有空串和 `null` 的）不产生要打码的文本。4 个字符是一个取舍：真正的密钥、口令、令牌几乎都比它长，而短叶子多是配置里的标签和开关，按子串打码会把日志、错误、输出整片换掉，读不了（#479）。**键的顺序**：Agent 把任务输入里对象的键递归地按 UTF-8 字节序排好再交给节点（`serde_json` 的对象是 BTreeMap；`sort_keys=True` 排出来的也是这个顺序），所以节点原样写出它收到的对象（`json.dumps(cfg)`，默认、紧凑、`ensure_ascii=False` 都一样）时，写出来的是排好序的顺序，和参数里（库里 jsonb）写的顺序不同；控制面两种都认。键的顺序既不是这两种时（节点自己重排、挑几个键再写），整段对不上，不少于 4 个字符的叶子照样被打码，短的叶子留着。排序是字节序，不是 JS 默认的 UTF-16 码元序（BMP 之外的字符不同），整数样子的键（`"10"` 在 `"9"` 之前）也按字节序：两端的排序用同一张用例表（`testdata/key-order-cases.json`），Agent 一端断言 `serde_json` 的写出，控制面一端断言排序函数。
  4. **多行的值**（例如一段 PEM）：整个值，加上每一行（去掉两头的空白后）不少于 4 个字符的：日志是按行写的，整段对不上。
  5. **短叶子的警告**：secret 的对象或数组里有短于 4 个字符的字符串或数字叶子时，预检给一条警告（`secret_short_leaf`，§6 第 2 条），写明是哪个参数（入口节点还是子流程入口节点）、有几个，不写出值，并说明它们单独出现时不会被打码，要保密的短值单独做成一个 secret 参数。警告只在预检里给（触发接口的响应是运行视图，没有放警告的位置；`sfly run start` 把预检的警告写在触发之后的输出里）。预检看得到的是场景最新版本里 secret 参数的默认值和运行预设里的值；触发请求里临时给的值预检时还不知道，不在其中。
  6. **打码不改变值的类型**：运行和链实例的参数、任务的输入和输出本身是「名字到值」的映射，映射不会被整个换成掩码（节点把收到的 secret 对象原样作为整个输出时，输出仍是对象，里面的值逐个处理）。映射里的值整个换成掩码只发生在它就是 secret 值本身的时候：和 secret 对象相等的对象或数组，数字、布尔整个等于顶层是数字、布尔的 secret 参数（或 secret 对象里不少于 4 个字符的数字叶子）；别处的对象逐个叶子处理，字符串叶子不会让写法相同的数字、布尔被换掉。
  - **数字的写法**：数字从控制面到节点里被打印出来要经过三步，三端写数字的规则各不相同：控制面用 JS 的 `JSON.stringify`，Agent 的 `serde_json` 解析再写成 `task.json`，Python 的 SDK 用 `json.loads` 读进来，节点用 `json.dumps` / `repr` 打印。所以节点里能看到的写法有三种：**控制面写的**（参数里存的）、**Agent 写进任务文件的**（节点读 `SFLY_TASK` 指向的文件再原样打印文本时）、**Python 打印的**（直接打印拿到的值时），都认：数字叶子和顶层的数字 secret 按值打码的文本带着三种写法，整段的写法也各带一份（整个值一起换一种写数字的规则；同一个值里的数字各按各的规则，所以任务文件里同时有小数和超出 64 位的整数时，写出来是两种写法混在一起，这一份也有）。三种写法不同的数字有三类：绝对值在 1e-9 到 1e-4 之间的小数（控制面 `0.00001`，Python `1e-05`），绝对值在 [1e-6, 1e-5) 的小数（控制面 `0.000001`，Python `1e-06`，Agent 写 `1e-6`，是第三种），和超出 64 位整数范围又小于 1e21 的整数（Agent 按浮点解析，Agent 和 Python 都写 `9.876543210987654e+19`）。三端共用的用例表是 `testdata/number-form-cases.json`，每一列都由真实的实现产生：Agent 一端 `agent/tests/number_forms.rs` 断言 `serde_json`，Python 一端 `sdk/python/tests/test_number_forms.py` 断言 `json.dumps`，控制面一端 `apps/server/test/secret-number-forms.test.ts` 断言 `JSON.stringify`、`pythonNumber` 和 `serdeNumber`。**`serdeNumber` 的规则绑在 `serde_json` 的版本上**：升级后写法变了，Agent 一端的断言先红，红了就要改 `serdeNumber` 并更新表里的 `serde` 列。
  - 打码时先换长的：整段先于它里面的叶子，所以整个对象被原样写出时是一个 `******`，不是留着结构的一串。**重叠的合并**：两个值在文字里首尾相接地重叠时（`abcd` 和 `cdef` 在 `abcdef` 里），重叠的位置合成一段、只换一个掩码，不留下任何一个值的尾巴；相邻但不重叠的各是一个掩码。很长的值（走字面量查找的）和普通的值（走正则的）结果一样。**一次打码的工作量有上限**：值来自用户、文字来自节点，周期性的值（一千个 `0`）出现在周期性的文字（一百万个 `0`）里时，每个位置都是一个出现位置，工作量是「文字长 × 值长」，同步执行会让控制面卡住好几秒；工作量（出现位置的长度之和，每个位置另加固定的一份）超过 3200 万时，把这一段文字整个盖住（宁可多盖）。正常的输入远在它下面（400 万字的输出里出现一百次 4 万字的值，工作量是 400 万）。
  - **按值打码是尽力而为，不是保证**：认的是 secret 值原样出现的写法，值被节点变形之后认不出。**覆盖的写法**：原样；JSON 转义（紧凑、缩进、键排序）；Python 的 `json.dumps` 默认写法、`ensure_ascii=False`、`sort_keys=True`（整个对象的整段，包括里面短的叶子）；`repr` / `str` / `print` / `pprint` 写出的对象，其中不少于 4 个字符的叶子（字符串叶子里不含引号和反斜杠时与原文一样）；多行的值按行。**没有覆盖的写法**（这样写出来的短叶子留着明文，不少于 4 个字符的叶子仍按值打码）：`str(dict)` / `repr(dict)` / `print(dict)` 打出整个对象时，整段对不上，里面短于 4 个字符的字符串和数字叶子（Python 的写法是单引号、`True` / `False` / `None`）；逐个键值分开打印（`print(k, v)`、`for k in cfg: print(k, cfg[k])`）时每个短叶子；缩进（`indent=2`）分行写出时的短叶子；自定义分隔符（例如 `separators=(",", ": ")`，逗号后没有空格、冒号后有空格）写出的整段，因为整段只认紧凑写法和 Python 默认的写法这两种分隔。另外：base64 等编码、含特殊字符的百分号编码、被切开或和别的文字拼成新文字的值、截断、`repr` 里含两种引号或控制字符的字符串（`repr` 换了另一套转义）。不能让节点接触到的 secret 值，不要交给节点。
- **secret 参数的默认值**也不读回来：所有返回场景文档的接口（编辑起点、某个版本、保存和恢复版本的响应）、触发前预检里入口参数的声明、命令行的 `scenario pull` 和 `show`，secret 参数的 `default` 都是占位符 `******`，和运行的参数、运行预设里的 secret 值是同一个掩码，不论参数的类型；没有默认值（没写或 `null`）的不动，普通参数的默认值照常返回。场景版本离开存储层的那一处（`OrchestrationStore` 的 `toVersionView`）统一打码，新增的出口默认就是打码的；引擎派发、触发准入在自己的事务里读库，不经过它，所以用默认值触发的运行，节点收到的是原值（运行视图、日志里仍是打码的，见上一条）。每个版本按它自己的声明打码：参数在某个旧版本里还不是 secret 时，那个版本里它的默认值是明文。
- **保存时的占位符**：读出来的文档原样存回去（命令行 `pull` 再 `push`、画布打开再保存都是这样）时，secret 参数的默认值是 `******` 表示「沿用上一个版本里同名参数的默认值」：保存要求 `base_version` 就是最新版本（不是的话照常返回 409 版本冲突，在占位符的处理之前），所以沿用的是最新版本的值；按（入口节点 ID，参数名）对应，主链入口和各个子流程入口里的同名参数互不相干。想换默认值就给新的值，想去掉就删掉 `default`。沿用不了时返回 400 `secret_default_placeholder`，什么都不保存，`details` 逐个写明参数和原因（`SecretDefaultProblem`）：场景还没有保存过版本（新场景的第一个版本，命令行 `scenario create --from` 在新建场景之前就报错），上一个版本里没有这个参数（新增的、改了名的）或它没有默认值，参数的类型变了，参数从 secret 改成了普通参数（占位符不能存成普通参数的默认值，原来的 secret 默认值也不会带过去：那会明文显示）。画布「另存为新场景」没有可以沿用的值，把「已设置」的默认值去掉并提示。因此 **secret 参数的默认值写不成 `******` 本身**；普通参数没有打码，默认值可以是 `******`。恢复历史版本、复制场景是控制面内部原样复制，不经过占位符。
- **触发时的占位符和报错**：触发请求里 secret 参数的值恰好是 `******`（把读到的占位符当成值传了回来）时拒绝，400 `invalid_params`，写明「这是读取时打的码，不是值；不传这个参数就用默认值，要用别的值就传真正的值」，不产生运行；运行预设保存时同理（新建和修改给 secret 参数写 `******` 被拒绝，沿用原值写 `keep`，规则不变）。普通参数没有打码，值可以是 `******`。触发时的报错（400 `invalid_params` 的 `message` 和 `details`）不回显 secret 参数的值：说明里要写出实际值的地方，值里 secret 的部分写成 `******`（调用方传的值、预设固定的值、默认值都一样），判断照旧，只是说明里不写值。
- **复制场景**时 secret 参数的默认值跟着复制（和运行预设里的 secret 值一样，§6 第 6 条）：联调副本要和原场景跑起来一样，复制不把值交给任何人，读副本仍是占位符。
- **保存时的提醒**：保存（和恢复）出的新版本里 secret 参数写了默认值，响应的 `warnings` 里每个这样的参数一条 `secret_param_default`：版本不能修改，默认值会一直留在这个版本里，建议去掉默认值，改用运行预设固定它，或者触发时再给出。只提醒，不阻止保存，也不影响触发运行（已有的场景在用）。版本对比看不出 secret 默认值有没有改过：两边读出来都是占位符。
- `description` 是参数的一行说明：最长 200 个 Unicode 字符（按字符计，一个 emoji 算一个），不能换行，去掉首尾空白后为空就不保存。它只用于显示：触发表单里作为帮助文字，异步任务节点映射子流程参数时显示子流程参数的说明，命令行的参数表里放在「说明」列最前面。**参数说明不影响执行**：不参与引用、校验和默认值，`secret` 参数的说明照常显示（只有值打码）。它和节点的位置一样属于场景版本的内容（ADR 0023），只改说明也会保存出新版本。

### 2.2 引用语法

节点输入的值可以是常量，也可以是引用。引用**只取值，不计算**，没有运算符和函数。

| 写法 | 含义 |
|---|---|
| `${{ params.<name> }}` | 当前链的入口参数（主链取入口节点参数，子流程取子流程入口节点参数） |
| `${{ nodes.<nodeId>.outputs.<key> }}` | 同一条链上**前面**某个节点的输出 |
| `${{ run.state }}` | 这次运行**此刻**的状态：运行的状态、每个链实例和它上面每个节点的状态、尝试次数、起止时间和失败原因（§2.7）。只能整值引用，只能写在包节点的输入里 |

- **整值引用**（输入值就是一个引用）保持原类型。
- **内嵌引用**（引用出现在字符串里）只允许引用标量，结果按字符串拼接。`${{ run.state }}` 是对象，不能内嵌。

### 2.3 作用域

- 链上的节点只能引用**本链的入口参数**和**本链上前面节点**的输出；`run.state` 是唯一的例外：它不传值，只是观察，范围是整个运行（§2.7）。
- 子流程看不到主链；主链也读不到子流程的输出。
- 主链的数据进入子流程的唯一途径是异步任务节点的参数传递（§4），并且按值复制。

### 2.4 何时解析

- **静态检查**：引用的节点必须在本链上、位于当前节点之前；引用的输出键必须在该节点类型的元信息中声明过。保存时只提示警告、仍允许保存；触发时必须全部通过。
- **派发时解析**：任务派发前才把引用替换成实际值。
- 普通节点执行时，前面的节点一定都已成功；如果被引用的输出键在运行时缺失，该任务以**配置错误**失败。
- `always` 节点执行时，前面的节点可能失败或被跳过；这时被引用的缺失输出解析为 `null`，由节点代码自行处理。

### 2.5 输出里的 NUL 字符

数据库存不下 NUL 字符（U+0000）。节点输出（键和值）、错误信息、进度说明、指标的名称和标签里的 NUL，在控制面保存前换成 U+FFFD（�），任务照常以原本的状态结束；后续节点引用到的、界面上看到的都是替换后的值。需要原样保存的二进制内容存成产物，输出里放产物引用。日志不受影响，原样保存。

### 2.6 输出里的数值

节点输出里的数值按双精度数（IEEE 754）处理：保存、整值引用、内嵌引用、对象和数组里的数、经接口和命令行读出，节点写出什么数，下游节点收到的、`GET /runs/:id` 返回的就是同一个双精度数，最短表示不变（`60.157000000000004` 仍是 `60.157000000000004`，不会变成 `60.157`），不需要为了对比先保留若干位小数。双精度数表达不了、或 JSON 里没有的值有下面几种：

| 节点写出的值 | 保存的、下游收到的 |
|---|---|
| 绝对值超过 2^53 的整数（`9007199254740993`） | 最接近的双精度数（`9007199254740992`）。要精确的大整数，输出里写成字符串 |
| 超过 2^64 - 1 的整数（负数小于 -2^63） | 同上；下游节点收到的是浮点数（Python 的 `float`），不是整数 |
| `-0.0` | `0`：符号丢掉，下游收到的是整数 `0`（和 `3.0` 一样，类型变了） |
| 整数值的小数（`3.0`） | `3`：JSON 里是同一个数，下游收到整数 |
| `NaN`、`Infinity` | JSON 里没有这些值：任务以 `node_error` 失败，没有输出；错误信息写明是哪个输出、怎么办（`输出 x 的值是 NaN。JSON 里没有 NaN 和无穷，换成 None（表示没有值），或者换成字符串（例如 str(值)）再返回`），嵌套的写成 `stats["items"][2]` |

内嵌在字符串里的引用，数按 JavaScript 的写法拼进去：最短表示，整数不带小数点，绝对值小于 1e-6 或不小于 1e21 时用指数（`1e-7`、`1e+21`），`-0` 写成 `0`；Python 的 `float()` 读回来是同一个数。测试：`apps/server/test/number-roundtrip.test.ts`（控制面）、`agent/tests/execute.rs`（Agent）、`apps/server/test/full-stack-number-roundtrip.test.ts`（整条链路）。

### 2.7 运行状态 `${{ run.state }}`

汇总节点（放在链末尾、总是执行）要知道前面的节点各自是成功、失败、被取消还是被跳过，失败的原因是什么。失败的节点没有输出，引用输出做不到，所以有这一个引用：它在派发时解析成这次运行此刻的状态（ADR 0031）。形状只有一份定义（`@sfly/schema` 的 `RunState`），运行摘要接口（`GET /runs/:id/summary`）给出的运行状态是同一个结构。

1. **写法。** 只能整值引用，只能写在包节点的输入里；不能引用它的字段（`${{ run.state.status }}`、`${{ run.state.chains[0] }}`），保存时警告、触发前阻断，说明里写「运行状态只能整个引用，字段在节点里读」（解析时的报错同一句）。夹在文字里、写在异步任务节点的参数映射里（参数映射在子流程创建时解析并按值复制，子流程里的节点拿到的会是一份过时的状态；子流程里的节点要用就在自己的输入里引用），保存时警告、触发时阻断（§2.4）。节点类型里用 `sfly.RunState` 声明的输入（输入 schema 里带标记 `x-sfly-type: run_state`）必须接它：必填的输入没接、或写了别的值（字面值、别的引用），同样保存时警告、触发时阻断，警告里直接写出该填 `${{ run.state }}`；可选的（`RunState | None`）不接没有警告。接到不带标记的普通输入（例如 json 类型）上也允许。
2. **时刻。** 任务派发时解析，和把这次尝试记为「准备中」是同一个事务。节点执行期间它不变；重试时每次尝试各解析一次。解析出的值和其他输入一样记在这次尝试上，运行视图里看得到汇总节点当时拿到了什么。只有输入里引用了 `run.state` 的节点才读运行状态；没有引用它的节点，派发时的查询和以前一样。
3. **范围。** 运行里已经创建的全部链实例（主链和已被触发的子流程实例），不论引用它的节点在哪条链上。每个链实例列出它那条链上的全部节点，按链上的顺序。还没被触发的子流程不在里面，看触发它的异步任务节点的状态。
4. **每个节点给什么。** `status` 是最近一次尝试的状态（取值同 §3.1 的节点状态，另有 `pending`）；`attempts` 是尝试次数，口径和运行视图相同（不含被跳过、没开始就被取消或停止的占位）；`started_at`、`ended_at` 是最近一次尝试的；`error` 只在 `failed` 时有：

   | 情况 | 给什么 |
   |---|---|
   | 本链上排在引用者前面的节点 | 一定已经结束：`success`、`failed`、`skipped`、`cancelled`、`stopped` 之一 |
   | 引用者自己 | `dispatched`，`attempts` 是这次尝试的序号 |
   | 本链上排在引用者后面的节点 | `pending` |
   | 其他链实例上的节点 | 那一刻的状态，可能还在进行 |
   | 被跳过的节点 | `skipped`，没有尝试，没有 `error` |
   | 重试过的节点 | 状态、错误、时间都是最后一次尝试的，`attempts` 是总次数 |
   | 被取消的节点 | `cancelled`，没有 `error`；`started_at` 为空是还没开始就被取消 |
   | 被停止的节点 | `stopped`，没有 `error`，不算失败 |
   | 超时的节点 | `failed`，错误类型 `timeout`，不是取消 |

   `error` 有四项：`kind`（错误类型）、`headline`（失败原因的一行，和运行监控的页头同一个取法，最长 300 个字符）、`message`（异常信息本身，不含堆栈，最长 2000 个字符，被截断时 `message_truncated` 为 true，末尾是「…」）、`location`（节点代码里出错的位置，没有时为空）。异常信息和堆栈在执行器的失败结果里是分开的，Agent 上报时拼成「异常信息 + 空行 + 堆栈」存下，这里从第一个独占一行、顶格的 `Traceback (most recent call last):`（或异常组的 `  + Exception Group Traceback (most recent call last):`）处拆开，之前的是异常信息；执行器异常退出、没有写出结果时，标准错误里堆栈前面的行留在异常信息里；没有堆栈的错误（配置错误、超时、Agent 掉线）整段都是异常信息。
5. **运行级的字段。** `status` 是运行此刻的状态：引用者自己还没结束，所以它在节点里看到的总是 `running`，不能用它判断结果。`cancel` 是取消请求（谁、经哪个 AI 编程助手、什么时候、是否强制），没有时为空。`result_so_far` 是按运行结果的规则（§6 第 4 条）对「到此刻为止」算出的结果：已请求取消是 `cancelled`，否则有节点最终失败是 `failed`，否则是 `success`；运行结束时的最终状态只会比它更坏（例如汇总节点自己失败了）。`failures` 是最终失败的节点的 ID，按失败的先后（和控制台、运行记录、运行通知同一份顺序），第一项就是第一个失败的节点。`self` 标出引用者自己（链实例和节点 ID）。`truncated` 见第 8 条。
6. **子流程。** 每个链实例带子流程名称（主链为空）、层数、上级链实例、触发它的异步任务节点和它自己的状态。异步任务节点的 `success` 只表示子流程实例已创建，子流程的结果看对应链实例的状态。
7. **不改变调度。** 引用 `run.state` 不构成对任何节点的依赖，不让引用者等待任何东西，引用了它的节点和没引用的节点就绪、派发的时机相同。主链不等待的子流程在汇总节点派发时可能还在进行，它之后的失败不在这份状态里；要让汇总看到某个子流程的最终结果，把汇总节点放在停止这个子流程的节点之后。
8. **打码与大小。** 错误信息按这次运行的保密参数的值打码（含只传给子流程的），和运行视图里看到的一样，所以节点收到的输入和记在任务上的输入里都搜不到原值。整份超过 256 KB 时，从 `failures` 的末尾开始去掉 `error.message`（那几个节点的 `message_truncated` 为 true），直到放得下，并把顶层的 `truncated` 标为 true；30 个节点、6 个链实例、3 个失败的运行解析出的值小于 16 KB。**去掉全部 `error.message` 之后仍然超过 256 KB**（运行里的节点特别多）时，引用它的节点不派发，任务以 `config_error` 失败（不重试），错误信息写明运行状态有多大、上限多少、有多少个节点和链实例；不再做第二层裁剪，免得汇总节点悄悄拿到不全的数据。

   **打码的时刻**：「按这次运行的保密参数的值」指解析那一刻（和运行视图的读取是同一个口径，都在 `readRuns` 里完成）。保密参数由后建的子流程在汇总节点**派发之后**才带进来时，派发那一刻它还不是这次运行的保密参数，发给 Agent 的那份输入（Agent 机器上任务工作目录里的 `task.json`）里错误信息按当时知道的保密参数打码，带着这个值就是原值；之后运行视图里这个节点记下的输入、运行摘要读出来的都是掩码，因为它们在读取那一刻打码。Agent 机器上的 `task.json` 不在读取时打码的范围里。对象类型的保密参数的值（不是字符串）不在错误信息的打码里，由另一份任务（#521）处理。
9. **字段总是存在**，没有值时是空值（null、空数组）。不含任何节点的输入、输出、进度、日志、动作，也不含堆栈。以后要加字段只增不改。
10. **兜底。** 汇总节点有执行不到的时候：强制取消、它自己失败或它的 Agent 掉线、主链结束之后才失败的子流程。这几种情况由运行通知（§6 第 5 条）兜底。
11. **解析出错。** 读运行状态出错、或整份太大放不下（第 8 条）、或准备这个任务的派发内容时别的步骤出错：这个任务以 `config_error` 失败（不重试），错误信息写明是解析 `${{ run.state }}` 时出的错和原因；同一个事务里同一台 Agent 上排在它后面的任务照常派发，不会被它卡住，下一次扫描也不再重试它。

## 3. 链的执行规则

### 3.1 节点状态

```
pending ──▶ queued ──▶ dispatched ──▶ running ──▶ success
   │           │                         │      └─▶ failed
   │           │                         └────────▶ cancelled
   │           └─(停止子流程节点)─▶ waiting ──▶ success / cancelled
   ├──▶ skipped     （前面失败或被取消，且本节点不是 always）
   └──▶ cancelled   （运行被取消，且本节点不是 always）

queued / dispatched / running / waiting / pending ──▶ stopped（所在子流程被停止，§4.1；不算失败）
```

`waiting`：只有停止子流程节点会进入，它在等被停止的子流程完全结束（§4.1）。

`dispatched`（界面写「准备中」）：任务已派发给 Agent，Agent 还在下载、安装节点包或启动执行器；Agent 上报开始执行后才是 `running`。超时和耗时从 `running` 起算（§3.3）。

### 3.2 顺序与失败

1. 链从起点开始逐个执行。前一个节点 `success` 后，下一个节点才开始。
2. 某个节点最终失败（重试用尽）后，后面的**普通节点**依次标记为 `skipped`，**`always` 节点照常执行**。
3. `always` 节点自身失败时，这条链标记为失败，后面的 `always` 节点继续执行。
4. `always` 只能用于包节点和停止子流程节点；异步任务节点不能设置为 `always`。

### 3.3 超时与重试

每个包节点可以配置：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `timeout` | 节点类型声明的，没有时 1 小时 | 从任务进入 `running` 开始计时；超时后杀掉进程树，任务失败。生效的值按这个顺序取第一个有的：场景里这个节点写的 → 节点类型声明的（`@node(timeout=…)`，元信息里的 `timeout`）→ 平台默认的 1 小时 |
| `retries` | 0 | 失败后最多重试的次数；每次重试是一个新任务，`attempt` 加 1 |
| `queue_timeout` | 10 分钟 | 目标 Agent 不在线、还在准备环境（Welcome 之后、第一次心跳之前，派发要等它准备好）或没有空闲槽位时，最多排队这么久，超过后任务失败。1 到 4294967295 秒之间的整数，不能写成引用，节点类型不能声明（见下） |

超时的取值：场景里这个节点写的 → 节点类型声明的 → 平台默认的 1 小时（`NODE_DEFAULTS.timeout`）。三种来源的值都是 1 到 4294967295 之间的整数（派发给 Agent 的超时是 32 位无符号整数）：场景里节点写的超过上限时保存被拒绝（400，错误信息写明是哪个节点、范围和实际的值；命令行 push 的本地检查和画布的字段同一句话）；升级前保存的版本里已经有这样的值时，触发前的预检阻断（`timeout_out_of_range`），已经在排队的任务派发时以 `config_error` 失败（不重试，错误信息同一句话），同一台 Agent 上排在它后面的任务照常派发。没有场景级的默认超时，超时不能写成引用。派发时按场景锁定的节点包版本取节点类型的声明：锁定旧版本（没有声明）时超时不变，场景升级到声明了超时的版本后，没在节点上写超时的节点跟着新声明走；开发版本取节点所在 Agent 上报的元信息，其中声明的超时不是 1 到 4294967295 之间的整数时当作没声明（开发版本的元信息没经过发布校验）。用的是平台默认（节点和节点类型都没有设置超时）而超时失败时，控制面在 Agent 报的错误信息后面另起一行补一句怎么办；找不到节点类型时不补。

排队超时的取值：场景里这个节点写的，没写就是平台默认的 10 分钟（`NODE_DEFAULTS.queue_timeout`），节点类型不能声明排队超时（只有超时可以）。取值是 1 到 4294967295 秒（`QUEUE_TIMEOUT_MAX_SECONDS`，约 136 年，和超时同一个数）之间的整数：排队截止时间是「进入排队的时刻 + 排队超时」，要装进一个有效的时间（JavaScript 的 `Date` 能表示的时间，换算下来排队超时在 8.6e12 秒以内都是有效的），上限离它还差三个数量级，不会拦住任何合理的用法。场景里节点写的超过上限时保存被拒绝（400，`sfly scenario check` 同样，检查通过的文档保存也一定通过；错误信息写明是哪个节点、字段、范围和实际的值，命令行 push 的本地检查和画布的字段同一句话）；升级前保存的版本里已经有这样的值时，触发前的预检阻断（`queue_timeout_out_of_range`，指到这个节点的 `queue_timeout`），已经触发、还没排到这个节点的运行，到这个节点时它以 `config_error` 失败（不重试，错误信息同一句话），这条链后面的节点按失败的规则推进，不会返回 500，也不会把已经成功的节点记成失败。

失败分为以下几类，决定是否可以重试：

| 错误类型 | 例子 | 是否按 `retries` 重试 |
|---|---|---|
| `node_error` | 节点代码抛出异常、进程非零退出 | 是 |
| `timeout` | 执行超时 | 是 |
| `agent_lost` | Agent 断线导致租约过期 | 是（仍派发到同一个 Agent） |
| `env_error` | 节点包安装失败、依赖冲突、排队超时、Agent 版本不满足节点包需要的 SDK 版本 | 否 |
| `config_error` | 参数校验失败、引用的输出缺失、输入里有节点没有声明的名字（执行器在调用节点函数之前拒绝）、解析 `${{ run.state }}` 出错或运行状态太大（§2.7） | 否 |

排队超时的报错写明排队了多久和原因：任务排队超时那一刻它的 Agent 在线、还在准备环境时是「排队超过 N 秒仍未派发：Agent X 一直在准备环境」，其他情况（Agent 不在线、槽位一直满着）是「排队超过 N 秒仍未派发：Agent X 不在线或没有空闲槽位」。

排队中的任务在等什么，由控制面在读取运行的那一刻按派发的条件判断（运行视图里排队中的尝试的 `queue_wait`，不是任务自己存下来的状态）：Agent 不在线（写明最后在线的时间）；在线但还在准备环境（写明开始准备的时间）；版本与控制面不一致，不派新任务；在线、已准备好但槽位用满（写明占着槽位的任务，`agents/slot-holders.ts` 的 `slotHolders(db, agent, 读者的项目)`）；条件都满足、正在派发。这几条就是派发（`engine.ts` 的 `#dispatch`）用的闸门，两边调用同一个纯函数（`agents/dispatch-gate.ts`），页面上说的原因不会和实际派发不一致。占着槽位的任务写明是哪次运行（运行编号的前 8 位），并且按读这个运行的人所在的项目过滤：同一台 Agent 上别的项目的任务只给个数（`other_project_holders`），不给场景名、运行编号和节点名。再加排队超时的时间（`queue_timeout` 到期的控制面时间）和读取这一刻的控制面时间，排了多久、离线了多久、多久后超时都按它算。Agent 的上下线、槽位的占用和释放不让运行本身变化，运行的事件流不会因此推送：界面在尝试排队期间定时重新读取运行，命令行的 `run start --wait` 同样，`sfly run show` 读一次。

### 3.4 取消

用户可以取消整个运行（不能只取消一条链）：

1. 所有链上正在运行的任务收到取消信号：先优雅终止，宽限 10 秒后强制杀掉进程树。
2. 正在等待的停止子流程节点（没有设为 `always` 的）立即取消。
3. 未开始的普通节点标记为 `cancelled`。
4. 每条链上的 `always` 节点**照常执行**。
5. 清理过程中用户再次点击取消，就是**强制取消**：`always` 节点也立即终止。

### 3.5 任务之间的隔离

包节点的每次执行（每个任务，包括每次重试）都在一个新启动的执行器进程里运行，不和其他任务共用进程。同时运行的任务之间、先后运行的任务之间都是这样，本地调试（`sfly debug`、`sfly.testing`）也一样。

1. 节点在进程里做的改动，都随进程结束而消失，不会带到同一个 Agent 上的其他任务，包括同一个节点的重试。这些改动包括：模块级变量和缓存、已经导入的模块、环境变量、当前工作目录、信号处理函数、打开的文件和连接、启动的线程。
2. 任务结束以执行器进程退出为准。节点注册的 atexit 处理和非守护线程都执行完、进程退出后，结果才上报，链上的下一个节点才开始。
3. 超时和取消终止的是执行器的整个进程组（§3.3、§3.4）。
4. 后台进程不在隔离范围内：节点启动、执行器退出时还在运行的进程，在任务正常结束时不会被终止。超时和取消时，还留在进程组里的会被一并终止，自己调用 `setsid` 脱离进程组的不会。需要跨节点运行的进程，用标准节点 `start_process` 启动、`stop_process` 停止。
5. 文件系统也不在隔离范围内：每个任务的工作目录是独立的，但 Agent 上的其他路径和节点包环境（ADR 0002），由这个 Agent 上的所有任务共用。

## 4. 异步任务节点与子流程

1. 异步任务节点执行时，按自己配置的参数映射创建**一个**子流程实例，然后立即 `success`，主链继续往下执行。
2. 参数映射的目标是子流程入口节点声明的参数；值可以是常量，也可以引用主链上前面节点的输出，按值复制传入。
3. 异步任务节点的输出是 `chain_instance_id`（子流程实例 ID）。
4. 前面的节点失败时，异步任务节点和普通节点一样被跳过，子流程不会被触发。
5. **主链和子流程互不影响**：子流程失败不影响主链继续执行，主链失败也不取消正在运行的子流程。
6. 子流程实例 ID 由"运行 ID + 父链实例 ID + 异步任务节点 ID"确定性生成，控制面崩溃恢复后不会重复创建。
7. 主链结束不会自动停止子流程；要在某个时刻结束子流程（例如压测结束后停止监控），在链上放一个停止子流程节点。
8. 子流程触发之后，链之间不再传值。一条链上的节点要处理另一条链在另一台 Agent 上产生的文件（例如主链在 A 上压测、子流程在 B 上清洗 A 的日志），由节点通过 Agent 能力直接读写那台 Agent 上的文件（ADR 0019），不需要新的执行语义：Agent 能力的调用不是节点，不产生任务、不占槽位，随调用它的任务一起被取消、停止。文件什么时候算写完、子流程什么时候停止，由节点和场景自己决定，平台不判断（sfly-std 的辅助函数 `watch_agent_files`，用户文档「跨 Agent 处理文件」）。

### 4.1 停止子流程节点

| 配置 | 说明 |
|---|---|
| `subflow` | 要停止的子流程（画布里按名称选择，版本里记录子流程入口的节点 ID，改名不影响引用） |

1. 只能停止本链**直接或间接触发**的子流程；不能停止自己所在的链、上级链或其他分支上的子流程。子流程由本链直接触发时，触发它的异步任务节点必须在停止子流程节点之前。与 §1.2 一样，保存时只警告，触发时必须通过。
2. 执行时，子流程尚未被触发（例如异步任务节点被跳过），或者它和它直接或间接触发的子流程都已经结束时，立即成功，不做任何事。
3. 否则**停止**这个子流程实例（如果它还在进行），以及它直接或间接触发、仍在进行的子流程：
   - 正在运行、排队的任务按取消的方式终止（§3.4 第 1 条，节点里会收到 `Cancelled`），记为 `stopped`；停止期间 Agent 失联（`agent_lost`）的任务同样记为 `stopped`、不再重试，节点自己报的失败（如 `node_error`、`timeout`）仍记为 `failed`、不再重试；
   - 正在等待的停止子流程节点（没有设为 `always` 的）和未开始的普通节点记为 `stopped`；
   - `always` 节点照常执行。
4. 停止不算失败：被停止的子流程在停止前没有失败、其 `always` 节点也没有失败时，这条链记为成功。
5. 停止子流程节点等这些子流程**完全结束**（包括其中的 `always` 节点）后才成功，输出 `status`（子流程的最终结果：`success` | `failed`；运行被取消、子流程以 `cancelled` 结束时没有成功完成，也输出 `failed`）；子流程未触发时为 `null`。子流程失败不会让停止子流程节点失败。
6. 可以设为 `always`：主链前面失败时仍然去停止子流程。运行被取消时不由它处理，整个运行按 §3.4 取消。

### 4.2 飞书通知的投递与消息格式

飞书通知有两个来源：节点代码里的 `ctx.notify`，和运行失败或被取消时的运行通知（§6 第 5 条）。两者都由控制面直接发给飞书群的自定义机器人（ADR 0020）：先把消息写进**发送队列**，再按下面的规则投递。曾有的飞书通知节点已移除（ADR 0028，§1.3）。

1. **入队。**
   - `ctx.notify`：Agent 把节点写进事件管道的通知转给控制面，控制面只接受任务所在 Agent 发来的。机器人必须在任务派发时随任务下发的名单里（「飞书机器人」类型的输入引用的机器人，§6 第 2 条），并且已登记，才写进发送队列。
   - 运行通知：运行失败或被取消时，在写入运行最终状态的同一个事务里入队（§6 第 5 条）。
2. **通知不会让任务失败。** `ctx.notify` 不能发送的（机器人不在名单里或没有登记、原始消息不合格、通知的内容不完整），在这个任务的日志里写一条 warning（来源 `system`），消息不发送，`ctx.notify` 不抛异常，节点照常执行。
3. **投递**（ADR 0020）：同一个机器人的消息按入队顺序串行发出，不同机器人互不影响。`ctx.notify` 的投递结果写成发出它的任务的一条日志（来源 `system`，送达是 info，失败是 warning），地址打码；运行通知的结果记在运行详情里（§6 第 5 条）。投递从不修改节点、任务、链和运行的状态：飞书不可达、返回错误时，后面的节点照常执行，运行的结果不变。
   - **重试**：网络错误、超时、HTTP 429、5xx 和飞书的限流错误码 11232 退避重试，间隔从 1 秒起逐次翻倍，最长 60 秒；等着重试的消息仍是队首，同一个机器人后面的消息不会越过它。从入队算起 10 分钟还没送达就记为失败，日志里写明尝试了几次和最后一次的原因。其他错误（9499、19021、19022、19024 和未知的错误码）不重试，只发一次就记为失败。日志只记最终的结果，重试的过程不写。
   - **限速**：每个机器人每秒最多发 5 个请求、每分钟最多 100 个（重试也算），超出的消息排队等候。
   - **积压**：单个机器人排队的消息超过 1000 条时，丢弃最旧的，记为「已丢弃：积压过多」，同一个任务丢弃多条时只写一行日志（注明条数）。机器人被删除时，它还没投递的消息记为「已丢弃：机器人已删除」。
   - **截断**：文本消息的请求体超过 20 KB 时，组装请求体（紧接着入队）时截断正文，末尾加「…（已截断）」（「@所有人」仍留在最后）。Markdown 卡片和原始消息见下面第 5 条。
   - 退避、期限和限速都按控制面时间（ADR 0018）计算；消息和排好的下一次尝试都存在数据库里，控制面重启后接着投递，已经送达的不会重发（重启时正在发送、还没有结果的那一条会再发一次）。
4. 机器人是否已登记，保存和触发前的检查见§6 第 2 条：「飞书机器人」类型的输入的机器人是常量时必须是已登记的飞书机器人，引用入口参数时按触发时传入的值检查。
5. **三种格式的请求体**（飞书请求体不能超过 20 KB，指紧凑 JSON 按 UTF-8 编码的字节数）：
   - 文本：`ctx.notify(bot, text, at_all=...)`，`msg_type: text`，`at_all` 打开时在正文末尾追加 `<at user_id="all">所有人</at>`；正文里自己写的 at 标签原样保留。组装规则和一组与实现无关的用例在 `testdata/feishu-text-cases.json`。
   - Markdown 卡片：由 SDK 的 `sfly.feishu.card(title, markdown, color)` 组装，再用 `ctx.notify(bot, message=...)` 发，控制面把它当原始消息投递，不再组装一遍。`msg_type: interactive`，卡片 JSON 2.0：header 是标题加颜色模板（`blue`、`green`、`orange`、`red`、`grey`），body 是一个 markdown 元素。标题和正文照原样放进去，空字符串也照常组装。请求体超过 20 KB 时截断正文：留下最长的、放得下的前缀，末尾接上「…（已截断）」；标题太长，连截断后的正文都放不下时抛出 `ValueError`（写法上的错误，开发时就会看到）。组装规则和一组与实现无关的用例在 `testdata/feishu-card-cases.json`。运行通知的卡片由平台固定结构（§6 第 5 条），不走这里。
   - 原始消息：`ctx.notify(bot, message=...)`，`message` 原样发出，不改写、不补字段。只校验它是一个对象、`msg_type` 是 `text`、`post`、`image`、`share_chat`、`interactive` 之一、不超过 20 KB；不合格或超过 20 KB 时**不截断**（截断会弄坏结构），不发送，在任务日志里写 warning 说明原因，`ctx.notify` 不抛异常。图片只能用自己已有的 `image_key`。校验规则和用例在 `testdata/feishu-raw-cases.json`。

## 5. 已移除的等待节点

定时节点（`timer`）和 Sleep 节点（`sleep`）已移除（ADR 0028）：引擎不再执行它们，也没有扫描等待到期的节点。「几点做什么」由节点按被测机自己的时钟判断。

- **历史版本和运行**：照常能看，节点显示成「已移除的节点类型 timer」「已移除的节点类型 sleep」，配置原样保留，只读，不执行（§1.3）。
- **最新版本里还留着它们的场景**：预检阻断触发（`node_kind_removed`，§6 第 2 条）；保存新版本的请求里不能带它们（400 `invalid_document`），要先在画布上把它们删掉（前后的节点自动接上）。
- **升级前开始、还没跑完的运行**：走到它们时按 `config_error` 失败，不重试，后面的节点按失败的规则推进（§3.2）。升级时已经在 `waiting` 的，控制面启动时同样按 `config_error` 失败。
- **替换办法**：定时节点，在节点代码里等到那个时刻，或把场景拆成两次运行；Sleep 节点，在节点代码里等待，或把场景拆成两次运行。

## 6. 运行

1. 手动触发时，运行绑定到场景的**最新版本**（场景版本）。存在未保存的草稿时不能触发；已归档的场景不能触发。
2. 触发前的预检：
   - 结构校验（§1.2）和引用校验（§2.4）全部通过（注释框的警告不算，§1.6）；
   - 引用的 Agent 都已注册（不要求在线，不在线或还在准备环境的任务按 `queue_timeout` 排队）。预检返回的每台被引用 Agent 带 `preparing_since`（在线 Agent 这次连接开始准备环境的控制面时间，其他情况为 `null`），触发抽屉据此提醒「X 正在准备环境，任务会等它准备好再执行」，不阻止触发；
   - 「Agent」类型的输入（ADR 0019，节点访问的另一台 Agent）选的 Agent 已注册，不要求在线：常量在保存时就给出警告；引用主链入口参数的，按这次触发传入的实际值检查；值来自前序节点的输出或子流程参数的，在派发时检查，没有注册过时任务以 `config_error` 失败。派发时控制面把这些 Agent 的名称、地址、端口随任务下发（地址在派发时解析）；运行时连不上按「连不通」失败；
   - 场景里没有已移除种类的节点（§1.3、ADR 0028，`node_kind_removed`）：这种节点不能运行，要先从场景里删掉；
   - 「飞书机器人」类型的输入（ADR 0020，节点通过它发通知）选的飞书机器人已登记：常量在保存时就给出警告；引用入口参数的（含子流程里取自异步任务节点映射的），按这次触发传入的实际值检查，指出是哪个节点的哪个输入。值来自前序节点的输出的，派发时不检查，没有登记也照常派发：通知不会成为任务失败的原因。派发时控制面把任务通过这种输入引用的机器人名单（不重复）随任务下发，节点用 `ctx.notify` 只能发给名单里的、已登记的机器人，其他的不发送、在任务日志里写一条 warning；
   - 锁定的节点包版本声明了需要的 SDK 版本（§7 第 4 条）时，Agent 执行任务时的版本（即控制面版本）满足它；
   - 声明了需要的 Agent 版本（§7 第 5 条）时，节点所在的 Agent（按控制面版本）和「Agent」类型的输入选的 Agent（按它注册时上报的版本）满足它；
   - 锁定开发版本（`包名@dev`，§7 第 3 条）的节点，派发到的 Agent 已经加载了这个包（`dev_package_not_loaded`）：只判断在线的 Agent，按它这次连接上报的开发版本；不在线的 Agent 不知道它加载了什么，按上面的离线规则排队，不另外阻断，没有注册过的 Agent 由 `agent_not_registered` 指出。每个没有加载的节点一条，写明节点、Agent、缺哪个包的开发版本，下一步是在那台 Agent 所在的机器上、节点包源码目录下运行 `sfly dev`，或者把这个节点的 Agent 改成已经加载它的（列出在线的）Agent；
   - 整个引用入口参数的节点输入，按这次触发的实际值检查类型（`param_input_type_mismatch`）：值是触发时给的值、运行预设里的值或默认值（§6 第 6 条、§2.1），子流程里是异步任务节点按参数映射传入的值。值不符合输入的类型时，派发到那个节点才会以 `config_error` 失败（「输入 x 应为 integer，实际是 8.5」），所以触发前就拒绝（400 `invalid_params`），写明是哪个参数、接到哪个节点的哪个输入、值是什么、来自哪里，并给出下一步：触发时给的值写可以直接执行的命令（`sfly run start <场景> --param <参数>=<整数>`），运行预设里的值写去哪里改，默认值写触发时怎么传、或在入口节点里改默认值，子流程里的写改异步任务节点的参数映射。判断和派发时是同一个：8、8.0 都是 JSON 数值 8，是整数，放行；8.5 不是，拒绝。secret 参数的值（含经参数映射传进子流程的）不写进说明，写成 `******`。没有值（可选参数没给，null）的、值不知道的（取自前面节点的输出）、引用夹在文字里的、常量（保存时就由静态检查指出）都不在这里检查，派发时照常检查；节点包版本在控制面没有元信息（开发版本）的节点不检查。

   预检还有**警告**，不阻断触发，和阻断项一起由预检接口返回（`warnings`，结构同 `problems`），控制台的触发对话框列在检查清单最后一行，`sfly run start` 写在触发之后的输出里（`--json` 时 stdout 的对象带 `warnings`）：
   - 异步任务节点没有给子流程的参数传值，而子流程里有节点用到它（`subflow_param_not_passed`）：参数是非必填、没有默认值的（必填又没有默认值的没传是保存时就有的 `subflow_param_missing`，阻断），没传值时子流程里取到的是空值（null），用到它的节点往往要跑到才失败，而且从错误里看不出是上一级没有传值。「用到」指子流程这条链上有节点的输入里引用了 `${{ params.<名称> }}`（整值或夹在文字里，子流程里的异步任务节点把它传给下一层也算）；没有任何地方引用时不报。一条警告对应一个异步任务节点的一个参数，写明用到它的节点（最多列三个）。
   - secret 的对象或数组里有短于 4 个字符的字符串或数字叶子（`secret_short_leaf`，§2.1）：它们单独出现在日志、输出里时不会被打码（整个对象被原样写出时才会）。一条警告对应一个参数（入口节点和子流程入口节点的默认值）或一个运行预设里的一个参数，写明参数名和个数，不写出值。
3. 运行包含主链和它直接或间接触发的全部子流程实例。
4. **所有链都结束后**，运行才结束：
   - 全部成功 → `success`
   - 任一条链失败 → `failed`（详情里可以看到是哪条链失败）；被停止的子流程按 §4.1 第 4 条计
   - 用户取消 → `cancelled`
5. **运行通知**（ADR 0020）：场景自己的设置，不属于场景版本，和名称、说明一样通过更新场景的接口修改，立即生效，复制场景时一并复制。字段是飞书机器人（为空即关闭）、触发条件（接口里 `trigger` 的值：`failed` 是仅失败，运行以 `failed` 结束时发；`failed_or_cancelled` 是失败和取消，运行以 `failed` 或 `cancelled` 结束时发）、卡片标题（为空时用场景名）和附加说明（Markdown）。运行通知是**兜底**：成功的运行不发，触发条件里没有「总是」；日常的结果（关注项的值、耗时、各节点的输出）由场景自己的节点用 `ctx.notify` 发（§4.2），平台不替用户决定「运行结束该看什么」，卡片里没有它们：
   - 运行结束时，**在写入运行最终状态的同一个事务里**，读取场景**当前**的设置（不是触发时的），选了机器人且结果满足触发条件的，把卡片写进发送队列；以 `success` 结束的运行不发。运行只会结束一次，所以同一个运行最多一张卡片；控制面在运行结束之后重启，卡片也不会漏发或重复发。
   - **没有「总是」。** 触发条件曾有第三个值 `always`（成功、失败、取消都发），#446 去掉了：保存运行通知的设置时 `trigger` 还写 `always` 的请求被拒绝（400 `invalid_request`，消息写明它已经去掉、现在可以填 `failed` 或 `failed_or_cancelled`，不想发就把 `bot` 设成 null）。存量设成「总是」的场景，升级时由数据库迁移一次性改成「失败和取消」；触发条件只存在场景自己的设置里，不属于场景版本，历史版本和已经结束的运行不受影响。
   - 卡片结构由平台固定，只回答「这次运行出事了，是哪个节点、为什么」：header 是卡片标题，颜色表示结果（失败 red、取消 grey），副标题写明「运行失败」或「运行已取消」；body 依次是附加说明（有的话）、场景名、运行编号（运行 ID 的前 8 位）、触发人、第一个失败的节点和它所在的链（GLOSSARY「第一个失败的节点」，和运行监控、运行记录是同一个；链的名称与运行监控一致，节点写成「显示名称（节点 ID）」，没有显示名称时只写节点 ID）、失败原因（一行，和运行监控页头用同一个函数 `errorHeadline` 取，最长 300 个字符，超出的截断并加「…」）、出错位置（节点的 `error.location`，有值时写在失败原因的下一行，没有值时不写这一行）；最后是「查看运行」按钮，链接由 `SFLY_PUBLIC_URL` 拼出，没有配置时不显示按钮。被取消的运行没有失败的节点时，没有失败的节点、失败原因和出错位置这几行。附加说明让整张卡片超过 20 KB 时截断附加说明，其余都不动；截了还放不下的不入队，在运行上记为未发送。
   - 机器人已被删除时不拦截触发，也不拦截运行：运行失败或被取消、本该发卡片时不入队，在运行上记为「未发送：机器人已删除」；入队之后机器人才被删除的，消息记为已丢弃。运行详情里有运行通知的状态：排队中、已送达、失败（及原因）、已丢弃、未发送（及原因）；运行还没结束、场景没有选机器人、结果不满足触发条件（包括所有成功的运行）的运行没有这一项，投递记录过了保留期被清理后也没有。
   - 投递结果只记在发送队列和运行详情里，从不改变节点、任务、链或运行的状态。为通知做的准备（读设置、读第一个失败的节点、拼卡片）也一样：它们在运行结束的事务里的一个保存点里做，任何一步出错（例如库里有不认识的触发条件，列上的 CHECK 约束让这不会发生，但这里不依赖它）都只是这次不发、记一条控制面日志，运行照常结束。「运行开始」的通知不放进运行通知，在入口后面的包节点里用 `ctx.notify` 发（§4.2）。
6. **运行预设**（ADR 0024）：场景自己的设置，不属于场景版本，和运行通知一样修改后立即生效。每个预设有场景内唯一的名称（区分大小写），固定入口节点的一部分参数（**预设参数**）的值，按参数名称对照场景的最新版本：
   - **锁定由控制面执行。** 触发请求带上预设的 ID 时，控制面在补默认值、检查类型的同一步（§2.1）用预设的值填入预设参数，之后的参数检查和不用预设时完全一样。请求里给 secret 预设参数传了任何值（即使和预设里的值相同）时拒绝触发（`preset_param_locked`），因为接受还是拒绝会让调用方反复猜测、推断出 secret 的原值；给其他预设参数传了不同的值（按 JSON 深比较）同样拒绝，传相同的值照常触发。是不是 secret 以最新版本的声明为准（和打码用的是同一份声明）；预设不存在或不属于这个场景时拒绝触发（`preset_not_found`）。从控制台、`sfly` 命令行还是自建页面触发都一样，界面上的锁定只是显示这条规则。
   - **失效。** 预设参数在最新版本里已不存在（被删除或改名），或者保存的值不符合它现在的类型（和 §2.1 补参数用同一套类型检查：不做类型转换，`json` 接受任何值）时，预设**失效**：不能用来触发，不会悄悄丢掉那个值、改用默认值。触发时用了失效的预设会被拒绝（409 `preset_invalid`），响应带上问题清单，每项是参数名加原因（`missing` 是参数已不存在，`type_mismatch` 是值不符合现在的类型），不产生运行。最新版本新增的参数不算问题，参数的默认值、是否必填、是否敏感有变化也不影响预设。预设的视图（预设列表、触发前检查）带 `status`（`ok` 或 `invalid`）和问题清单，清单里每个问题除了 `reason` 还有写成一句话的原因 `message`（控制台、命令行都直接显示它，不各自拼）；预设列表、触发前检查、触发、新建和修改时的检查、保存版本时的警告判断的都是同一个规则。失效的预设可以只改名称和说明；给了预设参数时，必须对照最新版本全部通过，预设才恢复可用。
   - **保存版本时的警告。** 保存场景版本（恢复历史版本也是追加一个新版本，同样适用）时，原来可用、对照新版本会失效的预设，各给出一条警告（`preset_invalidated`），消息写明预设名和原因；原来就已失效的预设不重复警告。和结构校验（§1.2）一样只警告、不阻止保存。
   - **记录。** 预设在触发的事务里读取，之后修改预设不影响已经开始的运行。运行上记下预设的 ID、触发时的名称和预设参数的名单；预设之后改名或删除，运行上记下的都不变。运行详情和运行记录（运行列表）显示的都是这份记录，不回头读预设。
   - **维护。** 新建、修改、复制、删除预设都立即生效，不产生新的场景版本。修改时只写要改的项：没有给预设参数就只改名称和说明（失效的预设也可以改名）；给了预设参数，它就是预设参数的完整清单，和新建时一样对照最新版本检查。复制预设时取一个新名称，说明和值（包括 secret 的值）原样复制。预设上记下最后修改人的昵称和时间；两个人同时修改时，后保存的覆盖先保存的，不做冲突检测。
   - **secret 预设参数。** secret 参数也可以设为预设参数，值和触发时传入的值一样明文保存。任何接口都不返回 secret 预设参数的原值：预设的所有响应（列表、触发前检查、新建、修改、复制）里它的值一律是 `******`。是不是 secret 以最新版本的声明为准：保存之后才变成 secret 的参数同样打码，不再是 secret 的参数按普通参数显示；已经不在最新版本里的预设参数（预设已失效）原来是不是 secret 无从判断，也打码。修改时不重新输入的 secret 参数写成 `{name, keep: true}`，沿用预设现在保存的值；`keep` 只能用在最新版本里声明为 secret、预设里已经有值的参数上，沿用的值也照常按最新版本的类型检查。用预设触发时 secret 值照常进入运行参数，日志和运行视图里按值打码（§2.1）。
   - **随场景走。** 复制场景（包括联调副本）时，在同一个事务里复制全部预设（包括 secret 的值）：新的 ID，名称和值不变，最后修改人记为复制的人。场景归档期间预设原样保留，也可以新建、修改、复制和删除，和运行通知一样；恢复之后照常可用。
7. **关注项**：场景自己的设置，不属于场景版本，和运行通知一样修改后立即生效，不产生新版本。每项是 `{node_id, chart, title?}`：节点 ID 跨版本稳定，图表按**标题**引用（节点包元信息不给图表加 ID），`title` 是场景作者起的名字，没起名时显示图表标题。
   - **整份替换。** 更新场景的接口给了 `focus_items` 就用它代替现在的列表，按给出的顺序保存；同时修改时，后写的生效，不做冲突检测。检查：最多 8 项，已经失效的项也算；`(node_id, chart)` 不能重复；**新加入的项**（现在的列表里没有的）必须引用最新版本里存在的节点，并且这个节点锁定的节点包版本声明了这张图表（含平台为没被图表引用的指标生成的默认图表，docs/ARCHITECTURE.md §4.1）；已经在列表里、后来失效的项允许原样保留，也可以排序、改名；例外是撤销（见「最后修改」），它把列表恢复成上一次修改之前的样子，里面失效的项不当作新加入的检查。不合格时返回 400（`focus_items_limit`、`focus_item_duplicate`、`focus_item_unknown_chart`），列表不变。
   - **失效。** 每项和最新版本的对照在读取时得出，不存下来：可用；节点不在最新版本里（附上包含它的最后一个版本号，复制场景带过来、没有任何版本包含它的项没有）；图表不存在（节点还在，锁定的节点包版本没有这张图表）。失效的项保留在列表里，也占名额，不会悄悄消失。节点回到最新版本里，或者节点包版本又声明了这张图表，它们自动恢复可用。
   - **最后修改。** 控制面比较新旧列表，记下修改人的昵称、控制面时间和一句话说明：添加了哪些项、移除了哪些项、哪一项移到第几位、改名；把上一次修改之前的列表原样写回去，记为撤销（撤销之后没有可以再撤销的列表）。写入和现在完全一样的列表不算修改，最后修改不动。
   - **随场景走。** 复制场景（包括联调副本）时，在同一个事务里复制整份列表（包括失效的项），最后修改记为复制的人，说明写「复制自「源场景名」」；源场景没有关注项时，副本也没有最后修改。场景归档期间也可以修改，和运行通知一样。

## 7. 节点包版本

1. 节点类型的引用形式是 `包名/节点名`，版本定在节点包这一级：`包名@版本`。
2. 场景保存时，每个包节点都锁定到一个确定的节点包版本，成为场景版本内容的一部分。
3. 开发版本写作 `包名@dev`，只在以本地开发模式加载了该包的 Agent 上可以执行；派发到其他 Agent 时，任务以 `env_error` 失败。触发前的预检在这之前就拦下：在线的 Agent 没有加载时拒绝触发（§6 第 2 条）；Agent 不在线、触发时不知道它加载了什么的，任务排队，它上线后没有加载才以 `env_error` 失败。
4. 节点包可以声明需要的 SDK 版本（元信息 `requires_sdk`，例如 `>=0.0.4`）；Agent 上 SDK 运行时的版本就是 Agent 版本（ADR 0010）。派发前不满足时任务以 `env_error` 失败，错误信息写明需要的版本和 Agent 的版本、提示升级 Agent；没有声明的节点包不检查。触发前预检比较的是控制面版本而不是 Agent 记录里的版本：控制面只给与自己同版本的 Agent 派任务、版本不同的 Agent 先自更新（ADR 0014），执行时的 SDK 版本就是控制面版本，所以不满足时拒绝触发并提示升级控制面。
5. 节点包可以声明需要的 Agent 版本（元信息 `requires_agent`，用到 Agent 能力时声明，ADR 0019），格式同 `requires_sdk`；没有声明的不检查。它约束两种 Agent，不满足时写明是哪台、需要哪个版本：节点所在的 Agent 在触发前按控制面版本检查（理由同上，提示升级控制面），派发前按它连接时上报的版本检查（任务以 `env_error` 失败）；节点通过「Agent」类型的输入引用的 Agent 按它最近一次注册时上报的版本检查——常量在触发前、引用入口参数的在触发时按实际值、来自前面节点输出的在派发时检查（任务以 `env_error` 失败）。

## 8. 验收场景

节点全部用通用桩节点实现（echo、sleep、按参数成功或失败、启停常驻进程、产出文件）。

| 场景 | 覆盖的语义 |
|---|---|
| **S1 数据流** | 入口参数传递；跨 Agent 引用上游输出；产物上传和引用；A 启动进程 → B 失败 → C（always）清理 |
| **S2 并行** | 异步任务节点触发子流程，主链不等待；子流程嵌套 2 层；子流程失败不影响主链；运行等待所有链结束；停止子流程节点停止嵌套子流程（被停止的节点收到 `Cancelled`、`finally` 清理执行，记为 `stopped`；子流程的 always 清理照常执行，停止子流程节点等它结束后才成功；子流程与运行记为成功） |
| **S3 故障** | Agent 断线后按重试配置重新派发；超时杀掉进程树；取消时 always 节点照常执行，再次取消则强制终止；依赖冲突以 `env_error` 失败且不重试；控制面重启后运行继续推进 |
