# 场景执行语义规范

> 状态：草案 · 2026-11-04（术语随 #25 更新：「编排」作名词改为「场景」，「编排」只作动词）
> 术语以仓库根目录的 `GLOSSARY.md` 为准。本规范定义场景"是什么、怎么跑"，与实现语言无关；引擎、画布、Agent 的行为都必须与本规范一致。

---

## 1. 场景结构

### 1.1 组成

一个**场景**的链路由以下部分组成（场景的名称、说明和运行通知的设置不属于场景版本，见第 6 节）：

- **主链**：从唯一的**入口节点**开始的一条链。
- **子流程**：零个或多个，每个从唯一的**子流程入口节点**开始，也是一条链。子流程入口声明子流程的**名称**（必填，场景内不重复；没有名称的旧版本以节点 ID 作为名称）。
- **默认 Agent**：场景级配置，未单独选择 Agent 的包节点都派发到它上面。

### 1.2 链的规则

| 规则 | 说明 |
|---|---|
| 单入单出 | 链上每个节点最多一条入线、一条出线；不分叉、不汇合、不成环 |
| 起点唯一 | 主链只有一个入口节点；每个子流程只有一个子流程入口节点 |
| 无结束节点 | 链的最后一个节点完成，这条链就结束 |
| 调度连线 | 异步任务节点除链上的出线外，另有一条**调度连线**，连到恰好一个子流程入口节点 |
| 子流程被触发方式 | 每个子流程入口节点恰好被一个异步任务节点连接 |
| 嵌套 | 子流程里可以再放异步任务节点；嵌套深度最多 3 层（主链为第 0 层）。由此一次运行里每个子流程最多有一个实例 |
| 无孤立节点 | 每个节点都必须位于某条链上 |

结构规则和引用规则（第 2.4 节）在**保存时只产生警告**，编排到一半的场景也可以保存；**触发时必须全部通过**。

并行**只能**通过异步任务节点触发子流程产生；链本身永远是顺序执行。

### 1.3 节点种类

| 种类 | 执行位置 | 说明 |
|---|---|---|
| 入口节点 | 控制面 | 声明场景参数，运行开始时立即完成 |
| 子流程入口节点 | 控制面 | 声明子流程参数，子流程实例创建时立即完成 |
| 异步任务节点 | 控制面 | 创建一个子流程实例后立即成功，主链继续往下执行 |
| 定时节点 | 控制面 | 等到指定的绝对时刻后完成，只触发一次 |
| Sleep 节点 | 控制面 | 等待一段相对时长后完成 |
| 停止子流程节点 | 控制面 | 停止本链触发的某个子流程，等它完全结束后完成（第 4.1 节） |
| 飞书通知节点 | 控制面 | 把一条消息交给发送队列后立即成功，由控制面投递（第 4.2 节、ADR 0020） |
| **包节点** | Agent | 节点类型来自已发布的节点包，在选定的 Agent 上执行 |

只有包节点需要选 Agent；内置节点不占用 Agent。

### 1.4 显示名称

除子流程入口节点外，每个节点都可以有一个可选的 `display_name`（显示名称）：一行文字，最长 40 个 Unicode 字符（按字符计，一个 emoji 算一个），不能换行，去掉首尾空白后为空就不保存，不要求唯一。子流程入口节点没有这个字段：子流程名称（`name`）就是它的显示名称。

- 它只用于显示：卡片标题是显示名称，原来的标题挪到卡片头部；卡片以外写成「显示名称（节点 ID）」，没有显示名称时只写节点 ID。
- **显示名称不影响执行**：不参与引用（引用、停止子流程节点的目标、日志和接口仍然以节点 ID 为准）、派发，也不影响保存时的警告和触发时的校验。
- 它和节点的位置一样属于场景版本的内容（ADR 0023），只改显示名称也会保存出新版本。

### 1.5 备注

所有节点种类都可以带一份可选的 `note`（备注）：多行文字，写这个节点在场景里做什么、为什么这样配置，最长 2000 个 Unicode 字符（按字符计，一个 emoji 算一个，换行也算一个），去掉首尾空白后为空就不保存。

- 它只用于显示：画布上节点卡片的头部有备注图标，悬停或键盘聚焦时显示全文；版本对比和 `sfly scenario show` 会列出它。
- **备注不影响执行**：不参与引用（里面写 `${{ … }}` 也不会被解析）、校验、派发和日志，超过长度才会让保存失败。
- 它和节点的位置一样属于场景版本的内容（ADR 0023），只改备注也会保存出新版本，运行显示的是它绑定的那个版本里的备注。

## 2. 参数与引用

### 2.1 参数声明

入口节点和子流程入口节点声明参数，每个参数包括：`name`、`type`（`string | number | boolean | json`）、`default`、`required`、`secret`，以及可选的 `description`。

- 手动触发运行时，用户填写入口节点的参数；缺少必填参数时拒绝触发。
- `secret` 参数在界面和日志中打码显示，数据库中明文保存。
- `description` 是参数的一行说明：最长 200 个 Unicode 字符（按字符计，一个 emoji 算一个），不能换行，去掉首尾空白后为空就不保存。它只用于显示：触发表单里作为帮助文字，异步任务节点映射子流程参数时显示子流程参数的说明，命令行的参数表里放在「说明」列最前面。**参数说明不影响执行**：不参与引用、校验和默认值，`secret` 参数的说明照常显示（只有值打码）。它和节点的位置一样属于场景版本的内容（ADR 0023），只改说明也会保存出新版本。

### 2.2 引用语法

节点输入的值可以是常量，也可以是引用。引用**只取值，不计算**，没有运算符和函数。

| 写法 | 含义 |
|---|---|
| `${{ params.<name> }}` | 当前链的入口参数（主链取入口节点参数，子流程取子流程入口节点参数） |
| `${{ nodes.<nodeId>.outputs.<key> }}` | 同一条链上**前面**某个节点的输出 |

- **整值引用**（输入值就是一个引用）保持原类型。
- **内嵌引用**（引用出现在字符串里）只允许引用标量，结果按字符串拼接。

### 2.3 作用域

- 链上的节点只能引用**本链的入口参数**和**本链上前面节点**的输出。
- 子流程看不到主链；主链也读不到子流程的输出。
- 主链的数据进入子流程的唯一途径是异步任务节点的参数传递（第 4 节），并且按值复制。

### 2.4 何时解析

- **静态检查**：引用的节点必须在本链上、位于当前节点之前；引用的输出键必须在该节点类型的元信息中声明过。保存时只提示警告、仍允许保存；触发时必须全部通过。
- **派发时解析**：任务派发前才把引用替换成实际值。
- 普通节点执行时，前面的节点一定都已成功；如果被引用的输出键在运行时缺失，该任务以**配置错误**失败。
- `always` 节点执行时，前面的节点可能失败或被跳过；这时被引用的缺失输出解析为 `null`，由节点代码自行处理。
- 飞书通知节点（第 4.2 节）无论是否设为 `always`，都按 `always` 节点的规则解析引用：缺失的输出取 `null`，内嵌在文字里时显示为 `null`。通知不会成为节点失败的原因。

### 2.5 输出里的 NUL 字符

数据库存不下 NUL 字符（U+0000）。节点输出（键和值）、错误信息、进度说明、指标的名称和标签里的 NUL，在控制面保存前换成 U+FFFD（�），任务照常以原本的状态结束；后续节点引用到的、界面上看到的都是替换后的值。需要原样保存的二进制内容存成产物，输出里放产物引用。日志不受影响，原样保存。

## 3. 链的执行规则

### 3.1 节点状态

```
pending ──▶ queued ──▶ running ──▶ success
   │           │          │      └─▶ failed
   │           │          └────────▶ cancelled
   │           └─(内置定时 / Sleep)─▶ waiting ──▶ success / cancelled
   ├──▶ skipped     （前面失败或被取消，且本节点不是 always）
   └──▶ cancelled   （运行被取消，且本节点不是 always）

queued / running / waiting / pending ──▶ stopped（所在子流程被停止，第 4.1 节；不算失败）
```

### 3.2 顺序与失败

1. 链从起点开始逐个执行。前一个节点 `success` 后，下一个节点才开始。
2. 某个节点最终失败（重试用尽）后，后面的**普通节点**依次标记为 `skipped`，**`always` 节点照常执行**。
3. `always` 节点自身失败时，这条链标记为失败，后面的 `always` 节点继续执行。
4. `always` 只能用于包节点、定时节点、Sleep 节点、停止子流程节点和飞书通知节点；异步任务节点不能设置为 `always`。

### 3.3 超时与重试

每个包节点可以配置：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `timeout` | 1 小时 | 从任务进入 `running` 开始计时；超时后杀掉进程树，任务失败 |
| `retries` | 0 | 失败后最多重试的次数；每次重试是一个新任务，`attempt` 加 1 |
| `queue_timeout` | 10 分钟 | 目标 Agent 不在线、还在准备环境（Welcome 之后、第一次心跳之前，派发要等它准备好）或没有空闲槽位时，最多排队这么久，超过后任务失败 |

失败分为以下几类，决定是否可以重试：

| 错误类型 | 例子 | 是否按 `retries` 重试 |
|---|---|---|
| `node_error` | 节点代码抛出异常、进程非零退出 | 是 |
| `timeout` | 执行超时 | 是 |
| `agent_lost` | Agent 断线导致租约过期 | 是（仍派发到同一个 Agent） |
| `env_error` | 节点包安装失败、依赖冲突、排队超时、Agent 版本不满足节点包需要的 SDK 版本 | 否 |
| `config_error` | 参数校验失败、引用的输出缺失 | 否 |

排队超时的报错写明排队了多久和原因：任务排队超时那一刻它的 Agent 在线、还在准备环境时是「排队超过 N 秒仍未派发：Agent X 一直在准备环境」，其他情况（Agent 不在线、槽位一直满着）是「排队超过 N 秒仍未派发：Agent X 不在线或没有空闲槽位」。

### 3.4 取消

用户可以取消整个运行（不能只取消一条链）：

1. 所有链上正在运行的任务收到取消信号：先优雅终止，宽限 10 秒后强制杀掉进程树。
2. 正在等待的定时节点和 Sleep 节点立即取消。
3. 未开始的普通节点标记为 `cancelled`。
4. 每条链上的 `always` 节点**照常执行**。
5. 清理过程中用户再次点击取消，就是**强制取消**：`always` 节点也立即终止。

### 3.5 任务之间的隔离

包节点的每次执行（每个任务，包括每次重试）都在一个新启动的执行器进程里运行，不和其他任务共用进程。同时运行的任务之间、先后运行的任务之间都是这样，本地调试（`sfly debug`、`sfly.testing`）也一样。

1. 节点在进程里做的改动，都随进程结束而消失，不会带到同一个 Agent 上的其他任务，包括同一个节点的重试。这些改动包括：模块级变量和缓存、已经导入的模块、环境变量、当前工作目录、信号处理函数、打开的文件和连接、启动的线程。
2. 任务结束以执行器进程退出为准。节点注册的 atexit 处理和非守护线程都执行完、进程退出后，结果才上报，链上的下一个节点才开始。
3. 超时和取消终止的是执行器的整个进程组（第 3.3、3.4 节）。
4. 后台进程不在隔离范围内：节点启动、执行器退出时还在运行的进程，在任务正常结束时不会被终止。超时和取消时，还留在进程组里的会被一并终止，自己调用 `setsid` 脱离进程组的不会。需要跨节点运行的进程，用标准节点 `start_process` 启动、`stop_process` 停止。
5. 文件系统也不在隔离范围内：每个任务的工作目录是独立的，但 Agent 上的其他路径和节点包环境（ADR 0002），由这个 Agent 上的所有任务共用。

## 4. 异步任务节点与子流程

1. 异步任务节点执行时，按自己配置的参数映射创建**一个**子流程实例，然后立即 `success`，主链继续往下执行。
2. 参数映射的目标是子流程入口节点声明的参数；值可以是常量，也可以引用主链上前面节点的输出，按值复制传入。
3. 异步任务节点的输出是 `chain_instance_id`（子流程实例 ID）。
4. 前面的节点失败时，异步任务节点和普通节点一样被跳过，子流程不会被触发。
5. **主链和子流程互不影响**：子流程失败不影响主链继续执行，主链失败也不取消正在运行的子流程。
6. 子流程实例 ID 由"运行 ID + 父链实例 ID + 异步任务节点 ID"确定性生成，控制面崩溃恢复后不会重复创建。
7. 主链结束不会自动停止子流程；要在某个时刻结束子流程（例如压测结束后停止监控），在链上放一个停止子流程节点。
8. 子流程触发之后，链之间不再传值。一条链上的节点要处理另一条链在另一台 Agent 上产生的文件（例如主链在 A 上压测、子流程在 B 上清洗 A 的日志），由节点通过 Agent 能力直接读写那台 Agent 上的文件（ADR 0019），不需要新的执行语义：Agent 能力的调用不是节点，不产生任务、不占槽位，随调用它的任务一起被取消、停止。文件什么时候算写完、子流程什么时候停止，由节点和场景自己决定，平台不判断（标准节点 `watch_files`，用户文档「跨 Agent 处理文件」）。

### 4.1 停止子流程节点

| 配置 | 说明 |
|---|---|
| `subflow` | 要停止的子流程（画布里按名称选择，版本里记录子流程入口的节点 ID，改名不影响引用） |

1. 只能停止本链**直接或间接触发**的子流程；不能停止自己所在的链、上级链或其他分支上的子流程。子流程由本链直接触发时，触发它的异步任务节点必须在停止子流程节点之前。与第 1.2 节一样，保存时只警告，触发时必须通过。
2. 执行时，子流程尚未被触发（例如异步任务节点被跳过），或者它和它直接或间接触发的子流程都已经结束时，立即成功，不做任何事。
3. 否则**停止**这个子流程实例（如果它还在进行），以及它直接或间接触发、仍在进行的子流程：
   - 正在运行、排队的任务按取消的方式终止（第 3.4 节第 1 条，节点里会收到 `Cancelled`），记为 `stopped`；停止期间 Agent 失联（`agent_lost`）的任务同样记为 `stopped`、不再重试，节点自己报的失败（如 `node_error`、`timeout`）仍记为 `failed`、不再重试；
   - 正在等待的定时节点、Sleep 节点和未开始的普通节点记为 `stopped`；
   - `always` 节点照常执行。
4. 停止不算失败：被停止的子流程在停止前没有失败、其 `always` 节点也没有失败时，这条链记为成功。
5. 停止子流程节点等这些子流程**完全结束**（包括其中的 `always` 节点）后才成功，输出 `status`（子流程的最终结果：`success` | `failed`；运行被取消、子流程以 `cancelled` 结束时没有成功完成，也输出 `failed`）；子流程未触发时为 `null`。子流程失败不会让停止子流程节点失败。
6. 可以设为 `always`：主链前面失败时仍然去停止子流程。运行被取消时不由它处理，整个运行按第 3.4 节取消。

### 4.2 飞书通知节点

| 配置 | 说明 |
|---|---|
| `bot` | 飞书机器人的名称：常量，或整值引用入口参数（画布里在已登记的飞书机器人中选择）。引用前面节点的输出、或把引用夹在文字里，保存时给出警告、触发时阻断（`feishu_bot_reference_unsupported`），因为机器人要在触发前就能查清 |
| `format` | 消息格式：`text`（文本，默认）、`card`（Markdown 卡片）、`raw`（原始消息）。决定下面哪一组配置生效 |
| `text` | 文本格式：消息文本，支持内嵌引用 |
| `at_all` | 文本格式：打开时在正文末尾追加 `<at user_id="all">所有人</at>`；正文里用户自己写的 at 标签原样保留 |
| `title` | Markdown 卡片：标题，支持内嵌引用 |
| `color` | Markdown 卡片：标题颜色，`blue`（默认）、`green`、`orange`、`red`、`grey` |
| `markdown` | Markdown 卡片：Markdown 正文，支持内嵌引用 |
| `message` | 原始消息：完整的飞书请求体（JSON 对象），字符串字段里的引用按 `json` 类型输入的规则逐个字段解析；也可以整值引用一个 `json` 类型的入口参数 |

1. 在控制面执行，不占 Agent 槽位，不需要选 Agent。轮到它时，控制面解析当前格式的配置、组装请求体、写进发送队列，**在同一个事务里**把节点记为成功。节点没有输出。切换格式时其他格式里填过的内容留在文档里，但不显示、不参与引用检查和解析。
2. 可以设为 `always`：不管前面成功还是失败，都发一条收尾消息。链上前面的节点失败时，非 `always` 的飞书通知节点和其他普通节点一样被跳过。
3. 引用一律按 `always` 节点的规则解析（第 2.4 节），无论节点是否设为 `always`。
4. **通知不会让节点失败**：解析或组装出错（引用无效、机器人的值不是字符串、文字解析出对象或数组、原始消息不合格……），或者运行到这个节点时机器人已被删除，节点在日志里写一条 warning，然后成功，消息不发送。
5. 投递是节点成功之后的事（ADR 0020）：同一个机器人的消息按入队顺序串行发出，不同机器人互不影响。投递结果写成这个节点的一条日志（送达是 info，失败是 warning），地址打码；投递从不修改节点、任务、链和运行的状态——飞书不可达、返回错误时，后面的节点照常执行，运行的结果不变。
   - **重试**：网络错误、超时、HTTP 429、5xx 和飞书的限流错误码 11232 退避重试，间隔从 1 秒起逐次翻倍，最长 60 秒；等着重试的消息仍是队首，同一个机器人后面的消息不会越过它。从入队算起 10 分钟还没送达就记为失败，日志里写明尝试了几次和最后一次的原因。其他错误（9499、19021、19022、19024 和未知的错误码）不重试，只发一次就记为失败。日志只记最终的结果，重试的过程不写。
   - **限速**：每个机器人每秒最多发 5 个请求、每分钟最多 100 个（重试也算），超出的消息排队等候。
   - **积压**：单个机器人排队的消息超过 1000 条时，丢弃最旧的，记为「已丢弃：积压过多」，同一个任务丢弃多条时只写一行日志（注明条数）。机器人被删除时，它还没投递的消息记为「已丢弃：机器人已删除」。
   - **截断**：文本消息的请求体超过 20 KB 时，组装请求体（紧接着入队）时截断正文，末尾加「…（已截断）」（「@所有人」仍留在最后）。Markdown 卡片和原始消息见下面第 7 条。
   - 退避、期限和限速都按控制面时间（ADR 0018）计算；消息和排好的下一次尝试都存在数据库里，控制面重启后接着投递，已经送达的不会重发（重启时正在发送、还没有结果的那一条会再发一次）。
6. 保存和触发前的检查见第 6 节第 2 条：机器人是常量时必须是已登记的飞书机器人，引用入口参数时按触发时传入的值检查。
7. **三种格式的请求体**（飞书请求体不能超过 20 KB，指紧凑 JSON 按 UTF-8 编码的字节数）：
   - 文本：`msg_type: text`，`at_all` 打开时在正文末尾追加 `<at user_id="all">所有人</at>`。
   - Markdown 卡片：`msg_type: interactive`，卡片 JSON 2.0：header 是标题加颜色模板，body 是一个 markdown 元素。标题和正文照原样放进去，空字符串也照常组装。请求体超过 20 KB 时截断正文：留下最长的、放得下的前缀，末尾接上「…（已截断）」；标题太长，连截断后的正文都放不下时不发送（节点日志里写 warning）。组装规则和一组与实现无关的用例在 `testdata/feishu-card-cases.json`，SDK 的 `sfly.feishu.card` 跑同一组用例。
   - 原始消息：`message` 原样发出，不改写、不补字段。引用先于序列化解析，所以引用的值里有引号、换行也不会弄坏 JSON。只校验它是一个对象、`msg_type` 是 `text`、`post`、`image`、`share_chat`、`interactive` 之一、不超过 20 KB；不合格或超过 20 KB 时**不截断**（截断会弄坏结构），不发送，节点日志里写 warning 说明原因。图片只能用自己已有的 `image_key`。 节点代码里 `ctx.notify(bot, message=...)` 发的原始消息（含 `sfly.feishu.card` 组装的卡片）适用同样的校验，不合格的不发送，在任务日志里写 warning，不抛异常。

## 5. 内置等待节点

### 5.1 定时节点

| 配置 | 说明 |
|---|---|
| `at` | `HH:MM:SS`（节点开始执行当天的这个时刻），或完整的 ISO 8601 日期时间 |
| `tz` | 时区，默认 `Asia/Shanghai` |

- 完整日期时间带偏移（`Z`、`+08:00`）时按偏移，不带偏移时按 `tz`。
- 节点开始执行时，如果目标时刻**已经过去**，立即成功，输出 `late: true`。
- 输出：`triggered_at`（实际完成时间）、`late`。

### 5.2 Sleep 节点

| 配置 | 说明 |
|---|---|
| `duration` | 例如 `30s`、`10m`、`1h`（单位 `ms`/`s`/`m`/`h`/`d`，可组合如 `1h30m`）；可以引用参数，引用解析出数字时按秒 |

- 输出：`triggered_at`。

两种节点都由控制面的持久化定时器驱动，控制面重启后会继续等待；运行被取消时，等待随之取消。

## 6. 运行

1. 手动触发时，运行绑定到场景的**最新版本**（场景版本）。存在未保存的草稿时不能触发；已归档的场景不能触发。
2. 触发前的预检：
   - 结构校验（第 1.2 节）和引用校验（第 2.4 节）全部通过；
   - 引用的 Agent 都已注册（不要求在线，不在线或还在准备环境的任务按 `queue_timeout` 排队）。预检返回的每台被引用 Agent 带 `preparing_since`（在线 Agent 这次连接开始准备环境的控制面时间，其他情况为 `null`），触发抽屉据此提醒「X 正在准备环境，任务会等它准备好再执行」，不阻止触发；
   - 「Agent」类型的输入（ADR 0019，节点访问的另一台 Agent）选的 Agent 已注册，不要求在线：常量在保存时就给出警告；引用主链入口参数的，按这次触发传入的实际值检查；值来自前序节点的输出或子流程参数的，在派发时检查，没有注册过时任务以 `config_error` 失败。派发时控制面把这些 Agent 的名称、地址、端口随任务下发（地址在派发时解析）；运行时连不上按「连不通」失败；
   - 飞书通知节点（第 4.2 节）选择的飞书机器人已登记：常量在保存时就给出警告，没有选择机器人同样；整值引用入口参数的（含子流程里取自异步任务节点映射的），按这次触发传入的实际值检查；写成其他引用（前面节点的输出、夹在文字里）的，保存时警告、触发时阻断，指出是哪个节点。运行到节点时机器人又被删除的，不发送、节点照常成功；
   - 「飞书机器人」类型的输入（ADR 0020，节点通过它发通知）选的飞书机器人已登记：常量在保存时就给出警告；引用入口参数的（含子流程里取自异步任务节点映射的），按这次触发传入的实际值检查，指出是哪个节点的哪个输入。值来自前序节点的输出的，派发时不检查，没有登记也照常派发：通知不会成为任务失败的原因。派发时控制面把任务通过这种输入引用的机器人名单（不重复）随任务下发，节点用 `ctx.notify` 只能发给名单里的、已登记的机器人，其他的不发送、在任务日志里写一条 warning；
   - 锁定的节点包版本声明了需要的 SDK 版本（第 7 节第 4 条）时，Agent 执行任务时的版本（即控制面版本）满足它；
   - 声明了需要的 Agent 版本（第 7 节第 5 条）时，节点所在的 Agent（按控制面版本）和「Agent」类型的输入选的 Agent（按它注册时上报的版本）满足它。
3. 运行包含主链和它直接或间接触发的全部子流程实例。
4. **所有链都结束后**，运行才结束：
   - 全部成功 → `success`
   - 任一条链失败 → `failed`（详情里可以看到是哪条链失败）；被停止的子流程按第 4.1 节第 4 条计
   - 用户取消 → `cancelled`
5. **运行通知**（ADR 0020）：场景自己的设置，不属于场景版本，和名称、说明一样通过更新场景的接口修改，立即生效，复制场景时一并复制。字段是飞书机器人（为空即关闭）、触发条件（仅失败 → `failed`；失败和取消 → `failed` 或 `cancelled`；总是 → 三种结果都发）、卡片标题（为空时用场景名）和附加说明（Markdown）：
   - 运行结束时，**在写入运行最终状态的同一个事务里**，读取场景**当前**的设置（不是触发时的），选了机器人且结果满足触发条件的，把卡片写进发送队列。运行只会结束一次，所以同一个运行最多一张卡片；控制面在运行结束之后重启，卡片也不会漏发或重复发。
   - 卡片结构由平台固定：header 是卡片标题，颜色表示结果（成功 green、失败 red、取消 grey），副标题写明结果；body 依次是附加说明（有的话）、场景名、运行编号（运行 ID 的前 8 位）、触发人、开始时间和耗时（控制面时间，按控制面所在的时区，带上时区）、最终失败的节点和它所在的链（按失败的先后，最多列 10 个，其余写总数）；最后是「查看运行」按钮，链接由 `SFLY_PUBLIC_URL` 拼出，没有配置时不显示按钮。附加说明让整张卡片超过 20 KB 时截断附加说明。
   - 机器人已被删除时不拦截触发，也不拦截运行：运行结束时不入队，在运行上记为「未发送：机器人已删除」；入队之后机器人才被删除的，消息记为已丢弃。运行详情里有运行通知的状态：排队中、已送达、失败（及原因）、已丢弃、未发送（及原因）；运行还没结束、场景没有选机器人或不满足触发条件的运行没有这一项，投递记录过了保留期被清理后也没有。
   - 投递结果只记在发送队列和运行详情里，从不改变节点、任务、链或运行的状态。「运行开始」的通知不放进运行通知，用入口后面的飞书通知节点实现。

## 7. 节点包版本

1. 节点类型的引用形式是 `包名/节点名`，版本定在节点包这一级：`包名@版本`。
2. 场景保存时，每个包节点都锁定到一个确定的节点包版本，成为场景版本内容的一部分。
3. 开发版本写作 `包名@dev`，只在以本地开发模式加载了该包的 Agent 上可以执行；派发到其他 Agent 时，任务以 `env_error` 失败。
4. 节点包可以声明需要的 SDK 版本（元信息 `requires_sdk`，例如 `>=0.0.4`）；Agent 上 SDK 运行时的版本就是 Agent 版本（ADR 0010）。派发前不满足时任务以 `env_error` 失败，错误信息写明需要的版本和 Agent 的版本、提示升级 Agent；没有声明的节点包不检查。触发前预检比较的是控制面版本而不是 Agent 记录里的版本：控制面只给与自己同版本的 Agent 派任务、版本不同的 Agent 先自更新（ADR 0014），执行时的 SDK 版本就是控制面版本，所以不满足时拒绝触发并提示升级控制面。
5. 节点包可以声明需要的 Agent 版本（元信息 `requires_agent`，用到 Agent 能力时声明，ADR 0019），格式同 `requires_sdk`；没有声明的不检查。它约束两种 Agent，不满足时写明是哪台、需要哪个版本：节点所在的 Agent 在触发前按控制面版本检查（理由同上，提示升级控制面），派发前按它连接时上报的版本检查（任务以 `env_error` 失败）；节点通过「Agent」类型的输入引用的 Agent 按它最近一次注册时上报的版本检查——常量在触发前、引用入口参数的在触发时按实际值、来自前面节点输出的在派发时检查（任务以 `env_error` 失败）。

## 8. 验收场景

节点全部用通用桩节点实现（echo、sleep、按参数成功或失败、启停常驻进程、产出文件）。

| 场景 | 覆盖的语义 |
|---|---|
| **S1 数据流** | 入口参数传递；跨 Agent 引用上游输出；产物上传和引用；A 启动进程 → B 失败 → C（always）清理 |
| **S2 并行** | 异步任务节点触发子流程，主链不等待；子流程嵌套 2 层；子流程失败不影响主链；运行等待所有链结束；定时节点 `late`；Sleep 节点；停止子流程节点停止嵌套子流程（被停止的节点收到 `Cancelled`、`finally` 清理执行，记为 `stopped`；子流程的 always 清理照常执行，停止子流程节点等它结束后才成功；子流程与运行记为成功） |
| **S3 故障** | Agent 断线后按重试配置重新派发；超时杀掉进程树；取消时 always 节点照常执行，再次取消则强制终止；依赖冲突以 `env_error` 失败且不重试；控制面重启后定时器和运行继续推进 |
