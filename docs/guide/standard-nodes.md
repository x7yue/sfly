# 标准节点

标准节点包 `sfly-std` 由平台维护，提供 Shell 命令这类与业务无关的**标准节点**，不用每个团队自己再写一遍。它就是一个普通的节点包：在 Agent 上执行，场景锁定它的版本，可以用 `sfly run` 和 `sfly.testing` 调试。

`sfly-std` 有自己的版本号，不随控制面发布，也不会自动出现在控制面上：部署者从 Release 下载后上传一次，之后有新版本时再上传。业务相关的节点仍然由你自己开发（见 [开发节点](sdk-reference.md)）。

## 上传 sfly-std

在本仓库的 GitHub Release 里找到 tag 为 `std-vX.Y.Z` 的版本，下载附件 `sfly-std-X.Y.Z.sflypkg` 和 `SHA256SUMS`。在下载目录里校验并上传到控制面：

```sh
cd ~/Downloads
sha256sum -c SHA256SUMS --ignore-missing
curl -fsS -H 'content-type: application/octet-stream' --data-binary @sfly-std-0.2.0.sflypkg {{SFLY_URL}}/packages
```

- 上传成功时返回节点包的版本信息（JSON）；装了 sfly 命令行时也可以用 `sfly publish sfly-std-0.2.0.sflypkg`。
- 上传后 `sfly-std` 出现在 [节点包管理](/packages) 页面，它的节点出现在画布的节点选择里。Agent 第一次执行时从控制面安装它，依赖（`psutil`、`httpx`）从 PyPI 镜像安装。
- Release 说明写明了需要的**最低 Agent 版本**。Agent 版本更旧时任务以 `env_error` 失败并提示升级（见 [需要的 SDK 版本](publish.md#需要的-sdk-版本)）；Agent 跟随控制面的版本，升级控制面即可。
- 已上传的版本不能覆盖。升级时上传新版本，再在场景里把 `sfly-std` 换成新版本；旧场景不受影响。

## 安全说明

`shell` 等节点让任何能编辑场景的人在 Agent 上以 Agent 的用户身份执行任意命令。这没有扩大攻击面：控制面的发布接口本来就没有认证，任何人都能发布执行任意代码的节点包。在平台有认证和权限控制之前：

- 只让可信的网络访问控制面；
- 用权限受限的专用用户运行 Agent，不要用 root；
- 不要把密钥直接写进节点参数，参数和日志在运行页面上对所有人可见。

## 通用约定

- 节点名是英文标识符，标题是中文；下文表格里的参数名和输出名就是节点表单与引用上游输出时用的名字。
- 运行时间由节点的超时（timeout，默认 1 小时）限制；超时和取消一样终止节点的整棵进程树。
- 运行时的输出实时转为任务日志。节点输出不超过 1 MB，大内容保存为产物。
- 失败时错误信息写明原因和关键参数，在运行页面的节点详情里查看。
- 等待类节点（`wait_port`、`wait_file`、`wait_log_line`）都有 `wait` 和 `poll`：`wait` 是等待本身的期限，节点的超时（timeout）仍然有效，`wait` 比超时长时以超时为准。`wait` 为 0 时只检查一次。
- 持续运行的节点（`system_monitor`、`process_monitor`、`follow_log`）都有 `duration`：设置时（必须大于 0）到期后成功结束；不设置时一直运行，直到被停止子流程节点停止或运行被取消（用法见下文「压测期间监控被测服务」）。被停止时节点记为「已停止」，不算失败，已经上报的指标、日志和产物都保留。
- 读日志文件的节点（`wait_log_line`、`follow_log`）用 `read_from` 指定从文件末尾还是开头读起。它没有叫 `from`：参数名就是 Python 函数的参数名，`from` 是 Python 关键字，不能用作参数名。
- 进程、端口、文件类的节点作用于执行它的 Agent 所在的机器：启动进程的节点和后面停止、监控、检查它的节点要选同一个 Agent。

## 节点一览

| 类别 | 节点 | 标题 | 用途 |
|---|---|---|---|
| 执行 | `shell` | Shell 命令 | 执行一段命令，输出退出码和标准输出 |
| 执行 | `start_process` | 启动后台进程 | 启动被测系统等常驻进程，节点结束后进程继续运行 |
| 执行 | `stop_process` | 停止后台进程 | 停止 `start_process` 启动的进程组，适合作为 always 节点清理 |
| 监控 | `system_monitor` | 系统监控 | 上报机器的 CPU、内存、负载、磁盘和网络指标，磁盘和网络另按每块磁盘、每块网卡各画一条曲线 |
| 监控 | `process_monitor` | 监控进程 | 上报目标进程（默认含子孙进程）的资源合计和每个进程各自的资源，每个进程的明细写进 `processes.csv` |
| 等待 | `wait_port` | 等待端口 | 等 TCP 端口可以连接 |
| 等待 | `wait_file` | 等待文件 | 等文件出现，可以要求它保持若干秒不变 |
| 等待 | `wait_log_line` | 等待日志行 | 等日志文件里出现匹配的行，输出这一行 |
| 日志 | `follow_log` | 跟随日志 | 把日志文件实时转为任务日志，出现匹配的错误行时失败 |
| 产物 | `collect_artifacts` | 收集产物 | 按通配符把文件保存为产物，可以打成一个 zip |
| 接口 | `http_request` | HTTP 请求 | 发请求并检查状态码和响应 JSON，可以重试直到满足 |
| 断言 | `assert` | 断言 | 对上游节点的输出逐条断言 |
| 断言 | `file_assert` | 文件断言 | 检查一次文件是否存在、大小、行数和内容 |
| 断言 | `process_assert` | 进程断言 | 检查一次进程在不在、有几个 |
| 断言 | `port_assert` | 端口断言 | 检查一次端口能不能连接 |

## 压测期间监控被测服务

一个典型的压测场景：启动被测服务，等它就绪，压测期间监控机器、服务进程和服务日志；压测结束后停止监控、收集结果、停掉服务，再确认环境恢复干净。链上的节点依次执行，要和压测同时运行的监控节点都放在子流程里，压测结束后用停止子流程节点把它们停下来。下面的节点都选被测机器上的同一个 Agent。

**主链**：

1. `server`（`start_process`）：启动被测服务，`log_file` 设为 `/srv/bench/out/server.log`；
2. `ready`（`http_request`，打开 `until_ok`）：等服务的健康检查接口返回成功；
3. 异步任务节点：触发子流程「监控」，把 `server` 的输出 `pid` 和 `log_file` 作为参数传进去；
4. `bench`（`shell`）：执行压测工具，把报告写到 `/srv/bench/out`；
5. `check`（`assert`）：检查 `bench` 的输出，例如错误数为 0；
6. 停止子流程节点（always 节点）：选中子流程「监控」；
7. `collect`（`collect_artifacts`，always 节点）：`base_dir` 为 `/srv/bench/out`，收集压测报告和服务日志；
8. `stop_server`（`stop_process`，always 节点）：`pid` 引用 `server` 的输出 `pid`；
9. `port_free`（`port_assert`，`reachable` 为 `false`）、`no_leftover`（`process_assert`，`running` 为 `false`）：确认端口已经释放、没有留下进程。

**子流程「监控」**：子流程入口声明参数 `pid` 和 `log_file`。同一条链上的节点依次执行，三个不会自己结束的监控节点要各占一条链：入口之后先用两个异步任务节点触发下级子流程「进程监控」和「服务日志」，最后是 `system_monitor`。「进程监控」里是 `process_monitor`，`pid` 引用子流程参数 `pid`；「服务日志」里是 `follow_log`，`path` 引用子流程参数 `log_file`，`fail_on` 写服务致命错误的正则。三个监控节点都不设置 `duration`。

这样安排的效果：

- 监控从压测开始前一直持续到压测结束。停止子流程节点停止「监控」时，连同它触发的两个下级子流程一起停止，三个监控节点记为「已停止」，不算失败。运行页面上能看到整个压测期间的系统指标、进程指标和服务日志，`process_monitor` 的产物里有每个进程的明细 `processes.csv`。
- 停止子流程节点要设为 always 节点：压测或断言失败时也要停止监控，否则监控一直运行到节点超时，运行迟迟不能结束。
- 停止子流程节点放在 `stop_server` 之前：先停监控再停服务，否则 `process_monitor` 会因为服务退出而失败。
- 服务在压测中意外退出时 `process_monitor` 失败（`on_exit` 默认 `fail`），服务日志里出现致命错误时 `follow_log` 失败。子流程失败不影响主链继续执行，但运行最终记为失败，在运行详情里能看到是哪个子流程。
- 压测时长固定、不需要停止子流程节点时，给监控节点设置 `duration`，到期后自己成功结束；它们仍然要放在子流程里才能和压测同时运行。

## `shell`：Shell 命令

用解释器执行一段命令：`<shell> -c <command>`。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `command` | 必填 | 要执行的命令 |
| `shell` | `/bin/sh` | 解释器：`/bin/bash`、`python3` 等任何接受 `-c <命令>` 的程序 |
| `env` | 无 | 追加的环境变量（对象，值为字符串），在 Agent 的环境变量之上 |
| `cwd` | 任务工作目录 | 工作目录，必须已经存在 |
| `ok_exit_codes` | `[0]` | 算作成功的退出码 |

| 输出 | 说明 |
|---|---|
| `exit_code` | 退出码；命令被信号终止时为 128 + 信号值（与 shell 的 `$?` 相同） |
| `stdout` | 标准输出的最后 64 KiB |

- 标准输出和标准错误实时转为任务日志（来源分别是 stdout 和 stderr）。
- 退出码不在 `ok_exit_codes` 里时节点失败，错误信息是退出码、命令和标准错误的末尾（约 4 KiB）。解释器或工作目录不存在时也失败，错误信息写明是哪一个。
- 取消或超时时，命令和它启动的全部子进程都被终止：先发 SIGTERM，宽限期过后强制杀掉。自己调用 `setsid` 脱离进程组的进程不在其中。
- 命令退出时还在运行的后台进程（例如 `server &`）不会被终止，但它们之后的输出不再转为日志。

例：构建后把版本号交给后面的节点。节点 `build` 的参数：

```json
{
  "command": "make dist && cat VERSION",
  "shell": "/bin/bash",
  "cwd": "/srv/app",
  "env": { "BUILD_MODE": "release" }
}
```

后面的节点在参数里引用 `build` 的输出 `stdout` 拿到版本号（含末尾的换行）。允许 `grep` 没有匹配（退出码 1）时，把 `ok_exit_codes` 设为 `[0, 1]`。

## `start_process`：启动后台进程

在新会话里执行 `<shell> -c <command>`，不等它结束：节点立即成功，进程在节点结束后继续运行，用来启动被测系统等常驻进程。之后用 `stop_process` 停止它。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `command` | 必填 | 要执行的命令 |
| `shell` | `/bin/sh` | 解释器，与 `shell` 节点相同 |
| `env` | 无 | 追加的环境变量（对象，值为字符串），在 Agent 的环境变量之上 |
| `cwd` | 任务工作目录 | 工作目录，必须已经存在 |
| `log_file` | `$SFLY_HOME/procs/<运行 ID>/<节点 ID>.log` | 进程的标准输出和标准错误追加写入的文件；相对路径相对于 `cwd`，目录不存在时自动创建 |

| 输出 | 说明 |
|---|---|
| `pid` | 进程号：交给 `stop_process`、`process_monitor` 等节点 |
| `log_file` | 日志文件的绝对路径：交给 `wait_log_line`、`follow_log`、`collect_artifacts` 等节点 |

- 进程在新的会话和进程组里，不属于任务的进程树：节点结束、任务被取消或超时都不会终止它，运行结束后也不会自动停止，**一定要配一个 `stop_process`**（见下一节的例子）。
- 进程的输出不转为任务日志，只写进 `log_file`。默认位置不在任务目录里：任务目录被清理时不受影响，和任务目录按同一个保留期清理（运行还有任务在这个 Agent 上时不动，后台进程还在写日志时不会被删，见 [安装 Agent](install-agent.md)）。同一个节点重试时追加到同一个文件。
- 节点只负责把进程启动起来：命令随后失败退出时节点仍然成功，用 `wait_port`、`wait_log_line` 等节点等它就绪，用 `stop_process` 的 `exit_code` 查看它是否异常退出过。解释器或工作目录不存在时节点失败。
- 进程运行在执行这个节点的 Agent 所在的机器上，后面引用它的节点（`stop_process`、监控节点等）要选同一个 Agent。

例：启动被测服务。节点 `server` 的参数：

```json
{
  "command": "exec ./bin/server --port 8080",
  "cwd": "/srv/app",
  "env": { "LOG_LEVEL": "debug" }
}
```

命令前加 `exec` 让解释器直接换成服务进程，`pid` 就是服务本身的进程号（不加时是解释器的进程号，服务是它的子进程，`stop_process` 同样能把它们一起停掉）。

## `stop_process`：停止后台进程

终止 `pid` 所在的整个进程组：先发 SIGTERM，宽限期过后还没退出的发 SIGKILL。进程已经不在时直接成功。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `pid` | 无 | 要停止的进程号，通常引用 `start_process` 的输出 `pid`；为空时什么也不做、直接成功 |
| `grace` | `10` | 从 SIGTERM 到 SIGKILL 的宽限期（秒） |

| 输出 | 说明 |
|---|---|
| `was_running` | 开始停止时进程是否还在运行 |
| `exit_code` | 进程的退出码：被信号终止时为 128 + 信号值（SIGTERM 为 143，被 SIGKILL 强制杀掉为 137）；拿不到时为 null |

- 终止的是整个进程组：`start_process` 启动的命令和它的子进程（包括命令自己已经退出、留在后台的进程）都会被终止。自己调用 `setsid` 脱离进程组的进程不在其中。
- `exit_code`：进程由同一次运行里、同一个 Agent 上的 `start_process` 启动时能拿到。`was_running` 为 false、`exit_code` 不是 0 时，说明进程在停止之前就异常退出了。
- 宽限期加 SIGKILL 后进程仍没有退出（例如卡在不可中断的磁盘读写里）时节点失败。

**放在 always 节点里清理**：把 `stop_process` 设为 always 节点，前面的节点失败或运行被取消时它仍然执行，被测进程不会留在机器上。`start_process` 本身失败时，引用的 `pid` 解析为空，`stop_process` 直接成功。例：场景依次是 `server`（`start_process`）、等待就绪、压测，最后是 always 节点 `stop_server`（`stop_process`），参数里的 `pid` 引用节点 `server` 的输出 `pid`，宽限期设为 30 秒：

```json
{
  "grace": 30
}
```

`stop_server` 要和 `server` 选同一个 Agent。压测中服务意外退出时，`stop_server` 的输出是 `was_running` 为 false、`exit_code` 为服务的退出码。

## `system_monitor`：系统监控

按采样间隔上报执行它的 Agent 所在机器的 CPU、内存、负载、磁盘和网络指标，运行页面上按声明的图表画出来。磁盘和网络的速率除了合计，还按每块磁盘、每块网卡各上报一个序列，在「按磁盘」「按网卡」的图表里每块一条曲线。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `interval` | `1` | 采样间隔（秒），必须大于 0 |
| `duration` | 无 | 监控多少秒后成功结束；不设置时一直运行，直到被停止子流程节点停止或运行被取消 |
| `disk_path` | `/` | 统计哪个文件系统的空间使用率：给出其中的任意路径，必须已经存在 |
| `nic` | 全部网卡合计 | 统计哪块网卡的收发速率，例如 `eth0`；合计包含回环网卡 `lo` |
| `disk` | 全部磁盘合计 | 统计哪块磁盘的读写速率，例如 `nvme0n1` 或 `/dev/sda`；合计只算整块磁盘，不重复计入分区 |

没有输出。

| 指标 | 单位 | 说明 |
|---|---|---|
| `cpu_percent`（主指标） | % | CPU 使用率，所有核的平均 |
| `mem_used_percent` | % | 已用内存占总内存的比例 |
| `mem_used_bytes` | B | 已用内存：总内存减去可用内存（available），不含可以回收的缓存 |
| `load1` | | 1 分钟平均负载 |
| `disk_used_percent` | % | `disk_path` 所在文件系统的已用空间比例 |
| `disk_read_bytes_per_s`、`disk_write_bytes_per_s` | B/s | 磁盘每秒读取、写入的字节数 |
| `net_rx_bytes_per_s`、`net_tx_bytes_per_s` | B/s | 网卡每秒接收、发送的字节数 |
| `disk_read_bytes_per_s_by_disk`、`disk_write_bytes_per_s_by_disk` | B/s | 每块整块磁盘每秒读取、写入的字节数，标签 `disk` |
| `net_rx_bytes_per_s_by_nic`、`net_tx_bytes_per_s_by_nic` | B/s | 每块网卡每秒接收、发送的字节数，标签 `nic` |

- 第一次采样在开始后一个 `interval`：CPU 使用率和各项速率都是两次采样之间的平均值。
- 默认图表：CPU 使用率、内存使用率、已用内存、负载、磁盘空间使用率、磁盘读写、网络收发、磁盘读写（按磁盘）、网络收发（按网卡）各一张。
- 按磁盘、按网卡的指标覆盖本机全部整块磁盘（不含分区，与磁盘合计的口径相同）和全部网卡（包括回环网卡 `lo`），每块一个序列，标签值是磁盘名（例如 `nvme0n1`）、网卡名（例如 `eth0`）；不受 `disk`、`nic` 参数影响，参数只决定合计指标统计哪一块。监控期间新出现的网卡、磁盘从下一次采样开始上报。
- 指定的网卡、磁盘或 `disk_path` 不存在时节点立即失败，错误信息列出本机有哪些网卡、磁盘。
- 被停止或取消时节点立即结束，已经上报的指标都保留，运行页面上仍能看到完整的曲线。
- 监控的是执行这个节点的 Agent 所在的机器：要监控被测机器，就让节点选那台机器上的 Agent。

**压测期间一直监控**：把 `system_monitor` 放在子流程里、不设置 `duration`，主链先用异步任务节点触发这个子流程再执行压测，压测之后用停止子流程节点（设为 always 节点）停止它；节点记为「已停止」，不算失败。完整的安排见上文「压测期间监控被测服务」。例：监控子流程里的节点 `monitor` 的参数，每 2 秒采样一次，只看业务网卡和数据盘：

```json
{
  "interval": 2,
  "nic": "eth0",
  "disk": "nvme1n1",
  "disk_path": "/data"
}
```

## `process_monitor`：监控进程

按采样间隔统计一个或多个目标进程（默认连同它们的全部子孙进程）用了多少资源，上报所有进程的合计，并按每个进程各上报一个序列；每个进程每次采样的明细写进产物 `processes.csv`。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `pid` | 无 | 进程号，或进程号的列表；通常引用 `start_process` 的输出 `pid` |
| `name` | 无 | 进程名（可执行文件名，例如 `nginx`，必须完全一致），或进程名的列表 |
| `match` | 无 | 命令行（各参数以空格连接）的正则表达式，部分匹配即可，或正则的列表 |
| `include_children` | `true` | 是否连同目标的全部子孙进程一起统计 |
| `wait_for_process` | `60` | 开始时最多等多少秒让每个目标都出现 |
| `interval` | `1` | 采样间隔（秒） |
| `duration` | 无 | 监控多少秒后成功结束；不设置时一直运行，直到被停止子流程节点停止或运行被取消 |
| `on_exit` | `fail` | 目标进程退出时：`fail` 让节点失败，`succeed` 让节点成功结束 |

| 输出 | 说明 |
|---|---|
| `samples` | 采样了多少次 |
| `processes_csv` | 产物 `processes.csv` 的引用 |

| 指标 | 单位 | 说明 |
|---|---|---|
| `cpu_percent`（主指标） | % | CPU 占用之和，一个核满载为 100 |
| `rss_bytes` | B | 常驻内存之和 |
| `threads` | | 线程数之和 |
| `open_fds` | | 打开的文件描述符数之和 |
| `io_read_bytes_per_s` | B/s | 磁盘读取速率之和 |
| `io_write_bytes_per_s` | B/s | 磁盘写入速率之和 |
| `cpu_percent_by_process` | % | 每个进程的 CPU 占用，标签 `pid`、`name` |
| `rss_bytes_by_process` | B | 每个进程的常驻内存，标签 `pid`、`name` |
| `threads_by_process` | | 每个进程的线程数，标签 `pid`、`name` |
| `open_fds_by_process` | | 每个进程打开的文件描述符数，标签 `pid`、`name` |
| `io_read_bytes_per_s_by_process` | B/s | 每个进程的磁盘读取速率，标签 `pid`、`name` |
| `io_write_bytes_per_s_by_process` | B/s | 每个进程的磁盘写入速率，标签 `pid`、`name` |

| `processes.csv` 的列 | 说明 |
|---|---|
| `time` | 采样时间（UTC，ISO 8601，到毫秒），同一次采样的各行相同 |
| `pid` | 进程号 |
| `ppid` | 父进程号 |
| `name` | 进程名 |
| `cpu_percent` | 这个进程在上一次采样以来的 CPU 占用 |
| `rss_bytes` | 常驻内存（字节） |
| `threads` | 线程数 |
| `open_fds` | 打开的文件描述符数 |
| `io_read_bytes_per_s` | 磁盘读取速率（字节/秒） |
| `io_write_bytes_per_s` | 磁盘写入速率（字节/秒） |
| `cmdline` | 命令行 |

- 目标：`pid`、`name`、`match` 至少给一个，可以同时给多个；每个进程号、进程名、正则各是一个目标，所有目标匹配到的进程合在一起统计，同一个进程只算一次。
- 开始时每个目标都要匹配到进程，最多等 `wait_for_process` 秒，等不到时节点失败，错误信息列出没找到的目标。
- 每次采样都重新查找：按名称或正则匹配的新进程、新的子进程会加进来，退出的进程不再统计。进程列表开始时写一次日志，之后有进程加入或退出时写一次，没有变化时每 60 秒写一次（附每个进程的 CPU、内存、线程数、文件描述符数）。
- **目标退出**：某个目标匹配的进程全部退出时（子孙进程退出不算），按 `on_exit` 失败或成功结束。被监控的进程是同一次运行里 `start_process` 启动的时，错误信息附上它的退出码。想在被测进程退出时正常结束监控，设为 `succeed`。
- `processes.csv` 每采样一次就写入：节点被停止、取消、因目标退出失败时，已采集的明细都在产物里。第一次采样在开始后一个 `interval` 时（CPU 占用要两次读数才能算出来）；某个进程第一次被采样时它的 IO 速率为空。
- 默认图表：CPU、内存、线程与文件描述符、磁盘读写这四张画合计；CPU（按进程）、内存（按进程）、线程数（按进程）、文件描述符（按进程）、磁盘读写（按进程）这五张每个进程一条曲线，图例是 `进程号 · 进程名`。按进程的指标和 `processes.csv` 里同一次采样的那一行数值相同。
- 别的用户的进程读不到文件描述符数和 IO（Agent 不是 root 时），`processes.csv` 里这两项为空，不计入合计，也不上报这个进程的 `open_fds_by_process`、`io_read_bytes_per_s_by_process`、`io_write_bytes_per_s_by_process`。
- 每个进程是一个序列：进程很多或者频繁启停（例如每个请求起一个子进程）时序列会很多，一个任务最多 1000 个序列（见 [SDK 参考](sdk-reference.md) `ctx.metric` 一节的「序列上限」），超出后新进程的点不再上报，任务日志里每个按进程的指标有一条警告；合计和 `processes.csv` 不受影响。
- 监控的是执行这个节点的 Agent 所在机器上的进程，引用 `start_process` 的 `pid` 时要选同一个 Agent。

例：压测期间监控被测服务。服务由 `start_process` 节点 `server` 启动，会再启动若干工作进程；在一个子流程里放 `process_monitor`，参数里的 `pid` 引用节点 `server` 的输出 `pid`，压测结束后用停止子流程节点停止这个子流程，服务中途退出时监控失败、暴露问题：

```json
{
  "interval": 2
}
```

按名称和命令行监控机器上已有的几个服务，不统计子进程，最多监控 10 分钟，其中任何一个服务的进程全部退出时提前成功结束：

```json
{
  "name": ["nginx", "redis-server"],
  "match": "java .*-jar /srv/app/app\\.jar",
  "include_children": false,
  "duration": 600,
  "on_exit": "succeed"
}
```

## `wait_port`：等待端口

每隔 `poll` 秒尝试连接一次 TCP 端口，能连上就成功；`wait` 秒内一直连不上时失败。用来等被测服务开始监听。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `port` | 必填 | 端口号 |
| `host` | `127.0.0.1` | 主机名或 IP 地址，从执行节点的 Agent 所在的机器上连接 |
| `wait` | `300` | 最多等多少秒 |
| `poll` | `1` | 检查间隔（秒） |

没有输出。

- 超时的错误信息写明等的是哪个地址、等了多久和最后一次连接的错误，例如 `TimeoutError: 等待端口 127.0.0.1:8080 可以连接超时：已等 300 秒，最后一次连接：Connection refused`。
- 端口能连上只说明进程在监听，不一定已经能正常处理请求：服务有健康检查接口时改用 `http_request`（打开 `until_ok`）等它返回成功，或用 `wait_log_line` 等它打出就绪日志。

例：`start_process` 启动服务后等它监听 8080 端口，最多等 1 分钟：

```json
{
  "port": 8080,
  "wait": 60
}
```

## `wait_file`：等待文件

每隔 `poll` 秒检查一次文件，文件存在就成功；可以要求文件再保持若干秒不变（例如等对方把报告写完）。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `path` | 必填 | 文件路径；相对路径相对于任务工作目录 |
| `stable` | `0` | 文件出现后，还要等它的大小和修改时间连续这么多秒不变；为 0 时出现就成功 |
| `wait` | `300` | 最多等多少秒 |
| `poll` | `1` | 检查间隔（秒） |

| 输出 | 说明 |
|---|---|
| `size` | 成功时文件的大小（字节） |

- 只等普通文件：路径是目录时一直等到超时，错误信息里写明「路径存在但不是文件」。
- 超时的错误信息写明当时的情况：「文件不存在」或「文件仍在变化」。
- 「稳定」按检查时看到的大小和修改时间判断，`stable` 小于 `poll` 时实际至少等一个检查间隔。

例：等压测工具写完结果文件，写完的标志是 5 秒内没有再变化：

```json
{
  "path": "/srv/bench/result.csv",
  "stable": 5
}
```

## `wait_log_line`：等待日志行

每隔 `poll` 秒读取日志文件新增的行，有一行匹配正则 `pattern` 就成功，输出这一行。用来等被测系统打出就绪日志。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `path` | 必填 | 日志文件路径；相对路径相对于任务工作目录 |
| `pattern` | 必填 | Python 正则表达式，匹配行内任意位置（`re.search`）；要匹配整行用 `^...$` |
| `read_from` | `end` | 从哪里开始看：`end` 只看节点开始之后新写入的内容，`start` 从文件开头看起 |
| `wait` | `300` | 最多等多少秒 |
| `poll` | `1` | 检查间隔（秒） |

| 输出 | 说明 |
|---|---|
| `line` | 第一行匹配的内容（不含换行符） |

- 默认（`read_from` 为 `end`）忽略节点开始前已经在文件里的内容，上一次运行留下的「就绪」日志不会误触发。被测进程可能在 `wait_log_line` 开始前就打出了就绪日志时（例如两者之间隔着别的节点），改用 `start`。
- 文件还不存在时等它出现，出现后从头读；文件被轮转或截断时继续读新的内容（规则与 `follow_log` 相同）。
- 只匹配完整的行：最后一行还没写完（没有换行符）时等它写完。按 UTF-8 解码，无法解码的字节显示为 �。
- 超时的错误信息写明文件、正则和等了多久；文件一直不存在时注明「文件不存在」。

例：等 `start_process`（节点 `server`）启动的服务打出监听日志。`path` 引用节点 `server` 的输出 `log_file`，其余参数：

```json
{
  "pattern": "listening on :8080",
  "wait": 120
}
```

后面的节点可以引用输出 `line`，例如从中取出实际监听的端口。

## `follow_log`：跟随日志

把日志文件新增的行实时转为任务日志（来源 stdout），在运行页面上直接看被测系统的日志；出现匹配 `fail_on` 的行时节点失败。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `path` | 必填 | 日志文件路径；相对路径相对于任务工作目录 |
| `read_from` | `end` | 从哪里开始跟随：`end` 从节点开始时的文件末尾，`start` 先转发文件里已有的内容 |
| `fail_on` | `[]` | 正则表达式列表（`re.search`）：有一行匹配其中任意一个时节点失败 |
| `duration` | 无 | 跟随多少秒后成功结束；不设置时一直跟随，直到被停止子流程节点停止或运行被取消 |

| 输出 | 说明 |
|---|---|
| `lines` | 转发的总行数（`duration` 到期时才有输出） |

| 指标 | 单位 | 说明 |
|---|---|---|
| `lines_per_s`（主指标） | 行/s | 每秒新增的行数 |
| `fail_matches` | | 累计匹配 `fail_on` 的行数 |

- 每 0.2 秒检查一次新内容，指标每秒上报一次。文件还不存在时等它出现，出现后从头转发。
- 文件被轮转（改名后新建，路径指向另一个文件）时，先转发旧文件剩下的内容，再从头跟随新文件；文件被截断（例如 logrotate 的 copytruncate）时从头跟随。两次检查之间被截断又写到超过原来长度的情况分辨不出来。
- 匹配 `fail_on` 时立即失败，错误信息附上第一行匹配的内容和匹配的正则；同一次检查读到的其余行照常转发并计入 `fail_matches`。
- 被停止或取消时，已经转发的行都留在任务日志里。超过 64 KiB 还没有换行符的内容先作为一行转发。

**与子流程配合**：把 `follow_log` 放在子流程里、不设置 `duration`，压测期间一直跟随被测服务的日志，压测结束后用停止子流程节点停止它，停止不算失败（见上文「压测期间监控被测服务」）。被测服务在压测中打出致命错误时 `follow_log` 失败，运行把它暴露出来。例：`path` 引用 `start_process` 的输出 `log_file`，其余参数：

```json
{
  "fail_on": ["panic:", "OutOfMemoryError", "^FATAL"]
}
```

## `collect_artifacts`：收集产物

按通配符把文件保存为产物，在运行页面的节点详情里下载，也可以把产物引用交给后面的节点。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `paths` | 必填 | 通配符列表，都是相对 `base_dir` 的路径，例如 `["*.log", "reports/**/*.html", "screenshots"]` |
| `base_dir` | 任务工作目录 | 在哪个目录下匹配，通常写被测系统或前面的 `shell` 写结果的绝对路径 |
| `archive` | `false` | 为 `true` 时把匹配到的文件打成一个 zip 产物 `artifacts.zip`，不再逐个保存 |
| `required` | `true` | 一个文件都没匹配到时是否让节点失败 |

| 输出 | 说明 |
|---|---|
| `refs` | 产物名称（相对 `base_dir` 的路径，`/` 分隔）→ 产物引用；`archive` 为 `true` 时只有 `artifacts.zip` 一项；没有匹配到文件时为空对象 |

- 通配符：`*` 匹配一段路径里的任意字符（不跨目录，以 `.` 开头的文件也匹配），`?` 匹配一个字符，`[abc]` 匹配其中一个字符，`**` 匹配任意层子目录（包括零层：`**/*.log` 也匹配 `base_dir` 下直接的 `.log` 文件）。
- 匹配到目录时收集其中的全部文件（含子目录）。多个通配符匹配到同一个文件时只收集一次。
- 产物名称保留相对 `base_dir` 的目录结构，所以通配符不能是绝对路径、不能含 `..`；要收集别处的文件时改 `base_dir`。
- 一个都没匹配到时，`required` 为 `true` 则节点失败，错误信息写明 `base_dir` 和通配符；为 `false` 则成功、`refs` 为空（`archive` 时也不生成 zip）。`base_dir` 不存在时总是失败。
- 节点输出不能超过 1 MB，所以 `refs` 最多 512 KiB（大约一两千个文件，取决于文件名长短）：匹配的文件多到超过时节点失败、一个都不保存，错误信息写明文件数，提示改用 `archive` 或缩小 `paths`。
- 每个任务的工作目录是独立的新目录，前面的节点写在它自己工作目录里的文件这里看不到：让前面的节点把结果写到一个约定的绝对路径，再把它设为 `base_dir`。产物目录本身不会被收集。
- 产物引用是控制面上的下载地址。`refs` 的键含 `.`，引用语法取不到其中一项：后面的节点整值引用 `refs`，再按名称取（例如 `assert` 的路径 `$["report.html"]`）。产物随运行一起按保留期清理。

例：前面的 `shell` 节点把压测报告写在 `/srv/bench/out` 下，收集其中的 HTML 报告和整个 `logs` 目录：

```json
{
  "paths": ["*.html", "logs"],
  "base_dir": "/srv/bench/out"
}
```

运行页面上会出现 `report.html`、`logs/app.log` 这样的产物。文件很多时加上 `"archive": true` 打成一个 zip 下载；收集可能不存在的崩溃转储时加上 `"required": false`。

## `http_request`：HTTP 请求

发一个 HTTP 请求，检查状态码和响应 JSON；打开 `until_ok` 时重试直到满足，可以用来等待 HTTP 服务就绪。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `url` | 必填 | 请求地址，`http://` 或 `https://` |
| `method` | `GET` | `GET`、`POST`、`PUT`、`PATCH`、`DELETE`、`HEAD`、`OPTIONS` |
| `headers` | 无 | 请求头（对象，值为字符串） |
| `json` | 无 | JSON 请求体（任意 JSON 值），自动加上 `Content-Type: application/json` |
| `body` | 无 | 文本请求体，按 UTF-8 发送；需要时在 `headers` 里写 `Content-Type`。与 `json` 只能填一个 |
| `request_timeout` | `30` | 单次请求最多等多少秒（连接、发送、等响应） |
| `verify_tls` | `true` | 是否校验 HTTPS 证书；被测环境用自签证书时设为 `false` |
| `expect_status` | `"2xx"` | 算作成功的状态码：状态码（例如 `404`）或 `"1xx"`～`"5xx"`，可以是列表，例如 `[200, "3xx"]` |
| `expect_json` | 无 | 对响应 JSON 的断言列表，格式与 `assert` 节点的 `assertions` 相同（见 `assert` 一节） |
| `until_ok` | `false` | 打开时，没有得到响应（连接失败、超时）或断言不通过就每 `poll` 秒重试一次，直到通过或超过 `wait` 秒 |
| `wait` | `300` | `until_ok` 时最多等多少秒 |
| `poll` | `1` | `until_ok` 时的重试间隔（秒） |

| 输出 | 说明 |
|---|---|
| `status` | 状态码 |
| `headers` | 响应头（对象）。名字都是小写；同名的多个响应头用 `, ` 连起来。名字和值合计超过 64 KiB 时只保留前面的响应头（写一条警告日志） |
| `json` | 响应内容是 JSON、且解析后的值写进输出（JSON 序列化）后不超过 256 KiB 时，解析后的值 |
| `text` | 响应内容不是 JSON 或 `json` 超过 256 KiB 时的文本，写进输出后最多 256 KiB，超过时只保留开头（截断、或 JSON 改为输出 `text` 时写一条警告日志） |
| `elapsed_ms` | 最后一次请求的耗时（毫秒） |

| 指标 | 单位 | 说明 |
|---|---|---|
| `elapsed_ms`（主指标） | ms | 每次请求的耗时 |

- 先检查状态码，再检查 `expect_json`。不满足时节点失败，错误信息写明请求方法和地址、状态码，以及不在 `expect_status` 里时响应的开头、不通过的断言（与 `assert` 一样逐条列出）。响应不是 JSON 而填了 `expect_json` 时也失败。
- `expect_json` 检查完整的响应 JSON：超过 256 KiB、输出里只有截断的 `text` 时也一样。
- 256 KiB 按写进输出后的大小算，不是响应的原始字节数：控制字符会转义成 `\u00XX`（每个 6 字节），引号、反斜杠、换行转义成 2 字节，无法解码的字节换成 `�`（3 字节）。所以二进制或含大量控制字符的响应，`text` 保留的字符会少得多；这样整个节点输出不会超过 1 MB 上限。
- 没有得到响应时（连接被拒绝、请求超时、证书校验失败）节点失败，错误信息写明原因。
- `until_ok` 重试时，原因变化时写一条日志（第几次、为什么不满足）；超过 `wait` 时失败，错误信息是请求次数和最后一次不满足的原因。每次请求最多等 `request_timeout` 秒，所以实际可能比 `wait` 多等一次请求的时间。
- 不跟随重定向：3xx 响应按原样检查，需要时把它写进 `expect_status`。
- 走 Agent 的 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY` 环境变量设置的代理。
- 请求头和请求体在运行页面上对所有人可见，不要直接写密钥。

例：被测服务用 `start_process` 启动后，等它的健康检查接口返回 `{"status": "ok"}`，最多等 2 分钟。节点 `ready` 的参数：

```json
{
  "url": "http://127.0.0.1:8080/health",
  "expect_json": [{ "path": "$.status", "op": "eq", "value": "ok" }],
  "until_ok": true,
  "wait": 120,
  "poll": 2
}
```

服务启动前连接被拒绝也会重试。下单接口要返回 201 和订单号时，节点 `order` 的参数：

```json
{
  "method": "POST",
  "url": "http://127.0.0.1:8080/api/orders",
  "headers": { "X-Request-Id": "sfly-smoke" },
  "json": { "sku": "A-100", "count": 2 },
  "expect_status": 201,
  "expect_json": [{ "path": "$.order_id", "op": "exists" }]
}
```

后面的节点引用 `order` 的输出 `json` 拿到整个响应，或者用 `assert` 对它做更多检查。

## `assert`：断言

对任意值逐条做断言：数值、文本、JSON 都用同一个节点检查。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `actual` | 必填 | 要检查的值，通常整个值就是一个引用（引用上游节点的输出，保持原类型）；也可以是包含多个引用的对象 |
| `assertions` | 必填 | 断言列表，至少一条；每条是 `{"path": ..., "op": ..., "value": ...}` |

每条断言的写法：

| 键 | 说明 |
|---|---|
| `path` | 取 `actual` 的哪一部分，默认 `$`（整个值）。支持 JSONPath 的常用子集：`$.a.b`、`$.items[0]`、`$.items[-1]`（从末尾数）、`$["带 空格.的键"]`、通配 `$.items[*]` 和 `$.service.*` |
| `op` | 比较方式，见下表 |
| `value` | 期望值；`exists` 可以省略 |

| `op` | 通过的条件 |
|---|---|
| `eq` / `ne` | 等于 / 不等于 `value`。按 JSON 比较：`1` 等于 `1.0`，`true` 不等于 `1`，数组按顺序比较，对象按键比较 |
| `gt` `ge` `lt` `le` | 大于、大于等于、小于、小于等于 `value`（数字）。实际值是数字文本时按数值比较，例如 shell 的 stdout `"42\n"` |
| `contains` | 文本包含 `value` 这段文字；数组含有等于 `value` 的元素；对象含有名为 `value` 的键 |
| `matches` | 文本里有匹配正则表达式 `value` 的部分（Python 语法，多行模式：`^` `$` 匹配每一行的开头和结尾）。要求整段匹配时写成 `\A...\Z` |
| `exists` | 路径存在；`value` 为 `false` 时要求路径不存在 |
| `len_eq` | 文本的字符数、数组的元素数或对象的键数等于 `value` |

| 输出 | 说明 |
|---|---|
| `passed` | 全部通过时为 `true` |

- 有断言不通过时节点失败，错误信息逐条列出不通过的断言：第几条、具体路径、期望和实际值。例如 `第 2 条：$.items[1].status 应 eq "ok"，实际是 "error"`；值太长时只显示开头。
- 路径里有通配时，每个匹配到的值都要满足；一个都没匹配到时不通过（`exists` 为 `false` 时通过）。
- 路径不存在时，除 `exists` 外的断言都不通过（`ne` 也一样），错误信息写明「路径不存在」。
- 断言写错时（路径无法解析、缺少 `value`、`value` 类型不对、正则表达式不合法、有未知的键）节点失败，错误信息写明是第几条、哪里不对，不检查任何断言。
- 断言格式与 `http_request` 的 `expect_json` 相同。

例：节点 `count` 是一个 `shell`，输出某个目录下的文件数。检查它成功执行、文件数至少 3 个，节点 `check` 的参数：

```json
{
  "actual": {
    "exit_code": "<引用 count 的输出 exit_code>",
    "stdout": "<引用 count 的输出 stdout>"
  },
  "assertions": [
    { "path": "$.exit_code", "op": "eq", "value": 0 },
    { "path": "$.stdout", "op": "ge", "value": 3 }
  ]
}
```

两处尖括号在画布里分别填成对 `count` 输出 `exit_code` 和 `stdout` 的整值引用。检查一个 JSON 响应里每一项的状态都是 `ok`（`items` 为空时也不通过）、并且有 `total` 字段时，`actual` 整值引用上游的 JSON 输出，`assertions` 写成：

```json
[
  { "path": "$.items[*].status", "op": "eq", "value": "ok" },
  { "path": "$.total", "op": "exists" }
]
```

## `file_assert`：文件断言

检查一次文件的状态：存在或不存在、大小、行数、内容匹配正则。只检查当下这一次，不等待（要等文件出现用 `wait_file`）。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `path` | 必填 | 文件路径；相对路径相对任务工作目录，通常写绝对路径 |
| `exists` | `true` | 文件应存在；为 `false` 时应不存在，这时不能再给下面的检查 |
| `min_size` / `max_size` | 无 | 大小（字节）的下限 / 上限，含边界 |
| `min_lines` / `max_lines` | 无 | 行数的下限 / 上限，含边界；最后一行没有换行符也算一行，空文件是 0 行 |
| `matches` | 无 | 内容（按 UTF-8 解码）应匹配的正则表达式：在任意位置匹配即可，多行模式（`^` `$` 匹配每一行的开头和结尾） |

| 输出 | 说明 |
|---|---|
| `passed` | 全部通过时为 `true` |

- 不通过时节点失败，错误信息逐项列出不通过的检查和实际值，例如 `/var/log/app/error.log 的 2 项检查中 1 项不通过：- 大小应 ≤ 0 字节，实际是 512 字节`。
- 给了大小、行数或内容的检查而路径是目录时节点失败。检查行数和内容会把整个文件读进内存，不要用于很大的文件。
- 要求精确的大小或行数时把上下限设成同一个值。

例：清理后确认错误日志是空的、PID 文件已经删掉，用两个 `file_assert`：

```json
{
  "path": "/var/log/app/error.log",
  "max_size": 0
}
```

```json
{
  "path": "/var/run/app.pid",
  "exists": false
}
```

## `process_assert`：进程断言

检查一次进程：在或不在、有几个。只检查当下这一次，不等待。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `pid` | 无 | 进程号，通常引用 `start_process` 的输出 `pid` |
| `name` | 无 | 进程名（可执行文件名，例如 `nginx`，必须完全一致） |
| `match` | 无 | 命令行（各参数以空格连接）的正则表达式，部分匹配即可 |
| `running` | `true` | 应至少有一个匹配的进程；为 `false` 时应一个都没有 |
| `count` | 无 | 应恰好有这么多个匹配的进程；给出时代替 `running` 的检查 |

| 输出 | 说明 |
|---|---|
| `passed` | 通过时为 `true` |
| `count` | 匹配的进程数 |
| `pids` | 匹配的进程号，从小到大；最多列出 1000 个（超过时写一条警告日志，`count` 仍是全部数量） |

- `pid`、`name`、`match` 至少给一个；同时给几个时，进程要全部满足（例如 `name` 为 `python`、`match` 为 `server\.py`）。
- 僵尸进程（已退出、还没被父进程回收）不算在运行。执行这个节点的进程自己不参与匹配。
- 不通过时节点失败，错误信息写明期望与实际，并列出匹配到的进程（进程号、进程名、命令行，最多 20 个）。
- 检查的是执行这个节点的 Agent 所在机器上的进程，引用 `start_process` 的 `pid` 时要选同一个 Agent。

例：清理后确认被测服务的进程都已经退出：

```json
{
  "match": "java .*-jar /srv/app/app\\.jar",
  "running": false
}
```

确认 nginx 正好有 1 个 master 和 4 个 worker 进程：`name` 为 `nginx`、`count` 为 `5`。

## `port_assert`：端口断言

尝试连接一次 TCP 端口，检查能连或不能连。只检查当下这一次，不等待、不重试（要等端口可连用 `wait_port`）。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `port` | 必填 | 端口号 |
| `host` | `127.0.0.1` | 主机名或 IP 地址 |
| `reachable` | `true` | 应能连接；为 `false` 时应不能连接（连接被拒绝或超时） |
| `connect_timeout` | `3` | 这一次连接最多等多少秒，超时算不能连接 |

| 输出 | 说明 |
|---|---|
| `passed` | 通过时为 `true` |

- 不通过时节点失败，错误信息写明地址、期望与实际，例如 `127.0.0.1:8080 应能连接，实际连接失败：[Errno 111] Connection refused`。
- 主机名解析不到时无论 `reachable` 是什么都失败：多半是主机名写错了，不能当成「不能连接」而通过。
- 连接从执行这个节点的 Agent 发起。

例：停止服务后确认端口已经释放：

```json
{
  "port": 8080,
  "reachable": false
}
```
