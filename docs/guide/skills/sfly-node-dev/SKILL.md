# sfly 节点开发

这个目录（节点包目录）是一个 sfly 节点包：用 `@node` 声明的 Python 函数，发布到控制面后由 sfly Agent 在测试机的共享 venv 里执行。SDK 接口见 [reference.md](reference.md)；命令参数以 `uv run sfly <命令> --help` 为准。

## 步骤

1. **写节点**：在 `src/<模块>/` 里增删 `@node` 函数，遵守下面的「规则」。
   完成：每个改动的节点都有对应的单元测试（`sfly.testing.run_node`），成功路径和失败路径各至少一个；都有 `title` 和文档字符串，每个输入和输出都有 `Doc`，每个指标都有 `description`（见「说明」）。
2. **检查**：`uv run ruff format`、`uv run ruff check`、`uv run pytest`。
   完成：三条命令全部通过。
3. **本地调试**：对每个改动的节点运行 `uv run sfly debug <节点> --params '<JSON>'`，参数尽量接近真实值。
   完成：输出、日志、指标、产物都符合预期；失败路径（错误参数、节点抛出异常、Ctrl-C 取消）各至少跑过一次；节点抛出异常时，`节点失败：` 下面一行「出错位置：模块.函数 第 N 行」指到出错的那一行节点代码，先看它。
4. **联调**：需要连真实被测系统，或要验证和上下游节点的配合时做这一步。按 `sfly-platform` skill 的「联调」流程自己用命令行做完：装开发版本、复制场景并改成开发版本和本机 Agent、运行，再按退出码和摘要改到成功。
   完成：运行成功，输出、日志、指标符合预期。
5. **发布**：递增 `[project].version`，把版本号和改动摘要交给用户确认；用户确认后运行 `uv run sfly publish`（先构建再上传）。
   完成：publish 输出「已发布 <包名>@<版本>」。已发布的 `包名@版本` 不能覆盖，冲突时改版本号再发。

## 规则

### 输入与输出
- 首个参数是 `ctx: Context`，其余参数都是输入，每个都写类型注解：输入的 schema 由注解生成，画布据此渲染参数表单，派发前按它校验参数。可用类型见 reference.md「输入」；可选输入给能 JSON 序列化的默认值。
- 输出用 TypedDict 返回类型声明（或 `@node(outputs=...)`）。返回值是能 JSON 序列化的 dict，不超过 1 MB；大块数据存成产物，输出里放产物引用。
- 失败就抛异常，消息里写清原因和相关参数值；只有成功才返回。

### 说明
这些说明会显示在画布上，读者是搭场景的人，不是读代码的人。写法见 reference.md「节点类型的说明」「输入的说明：`Doc`」「输出的说明：`Doc`」和「`ctx.metric`：指标」。
- 每个 `@node` 都写 `title`：一个说明节点做什么的中文短语（例如「HTTP 检查」），同一个包里不重复。
- 每个 `@node` 函数都写文档字符串，它是节点类型的说明：「添加节点」菜单显示第一段，检查器显示全文。按三部分写：
  1. 第一段：一句话说明做什么。
  2. 副作用：会创建什么资源，由哪个节点清理，清理节点要不要设成 always 节点。没有副作用时省略这一部分。
  3. 失败：什么情况下失败。
- 每个输入和输出字段都用 `Annotated[类型, Doc("…")]` 写含义、单位和取值范围；这些内容只写在 `Doc` 里，不写进文档字符串。用了 `Doc` 就把 `[tool.sfly]` 的 `requires-sdk` 调到 `>=0.4.0`。
- 每个指标写 `description`；有单位的写 `unit`，计数类可以留空。
- 代码注释只写读代码看不出来的东西：为什么这样做、被测系统的怪癖、等待和重试的理由、常量的来源。只有读代码的人才需要知道的事写在注释里，不写进文档字符串。注释不复述代码，不写改动历史。

### 超时
- 跑得久的节点（保持 12 小时、长时间压测）在 `@node(timeout=秒)` 里声明超时，写成它真正需要的上界，不要指望搭场景的人逐个节点去设；不声明时平台默认 1 小时，卡死的节点 1 小时后被终止。场景里这个节点自己写了超时时以场景里的为准。写法和取值见 reference.md「节点类型的默认超时」。
- 节点超时失败、错误信息提示「节点和节点类型都没有设置超时」时，先判断这个节点是不是本来就该跑这么久：是就声明 `timeout`，不是就找它为什么卡住。

### 日志、进度、指标、产物
- 信息一律通过 `ctx` 输出：`ctx.log` 带级别进入运行视图；耗时操作用 `ctx.progress` 上报进度。
- 想让看运行的人知道节点此刻在做什么（连网关、预热、保持 4 小时、每一笔下单），用 `with ctx.action(名称, 订单=订单号)` 记成动作，一个时刻用 `ctx.mark(名称)`。名称只写这是一件什么事，订单号这类变化的内容放进字段；高频压测不要每一笔都记，按批记录，每一笔的延迟用指标。单元测试里断言 `run_node(...).actions`。
- 指标先在 `@node(metrics=...)` 里声明，再用 `ctx.metric` 上报（未声明的会被丢弃）。`gauge` 是瞬时值，`counter` 是累计值；用 `primary_metric` 指出最能代表运行状况的那个。按对象（进程、连接、网卡……）分别统计时在 `Metric(labels=[...])` 声明标签键、上报时带 `labels`；带标签的指标只能画在 `line` / `area` 图表里，也不能当主指标，需要时另报一个不带标签的合计指标。
- 文件用 `ctx.artifacts.save` / `path` 保存，输出里放返回的产物引用；后续节点用 `ctx.artifacts.download(引用, 本地路径)` 下载，不要自己写 `urlopen`。
- 产物有大小上限（每个任务的合计，已经保存的也算在里面，默认 1 GB，部署者调整）：`ctx.artifacts.limit_bytes` 是上限的字节数（本地调试是 `None`），`save` 放不下时抛出 `sfly.ArtifactLimitExceeded`、不写这个文件。可能很大的文件（抓包、转储）接住这个异常，改成把文件留在本机（写在任务目录之外，任务目录按保留期清理）、在输出里给出它在哪台 Agent 的哪个路径，要用它的节点用 `ctx.agent(名称).files.download` 取；`outputs` 里声明两种分支的键、都返回（用不到的给 `None`）。保存前先和 `limit_bytes` 比也行，但最稳的是接住异常。不接住的话任务在保存那一行以 `env_error` 失败（不按 `retries` 重试）。不要在信号处理函数里 `save`（会死锁）；多个进程各自存产物时合计可以超限，由 Agent 上传前的检查兜住（同样 `env_error`）。用到 `limit_bytes` 把 `requires-sdk` 调到 `>=0.6.0`。
- 失败了通知谁、按结果发什么：节点自己失败就抛异常，不要为了通知在失败的地方当场发告警；要按整个运行的结果发一条通知，写一个**汇总节点**：把一个输入声明成 `RunState` 类型（`from sfly import RunState`），场景里把它接到 `${{ run.state }}`，节点收到整个运行此刻的状态（每个链实例上每个节点的 `status`、`attempts`、`error`（`headline` 是失败原因一行，`message` 不含堆栈），运行级的 `result_so_far`、`cancel`、`failures`），再用 `ctx.notify` 发。放法：放在链尾、设为 always 节点（前面失败或被取消时它仍然执行）；要看到某个子流程的最终结果，放在停止这个子流程的节点之后（主链不等待的子流程在汇总节点派发时可能还在进行）。`${{ run.state }}` 只能整值写在包节点的输入里，不能夹在文字里，也不能写在异步任务节点的参数映射里；`RunState` 类型的必填输入没接 `${{ run.state }}` 保存时会警告。单元测试用 `sfly.testing.run_state(nodes={...})` 造状态，断言 `run_node(...).notifications`；用一次真实运行的状态调试：`uv run sfly run show <运行> --state` 存成文件，放进输入文件，`uv run sfly debug <节点> --params @文件`。用到 `RunState` 就把 `[tool.sfly]` 的 `requires-sdk` 调到 `>=0.6.0`。
- 往飞书群发通知用 `ctx.notify(机器人, 文本)`，要带格式用 `ctx.notify(机器人, message=sfly.feishu.card(标题, Markdown 正文, 颜色))`（完整的飞书请求体也能直接给 `message=`）；机器人声明成 `FeishuBot` 类型的参数传进来，不要自己请求 Webhook 地址：消息由控制面发出，投递失败不会抛异常，也不会让节点变慢。单元测试里断言 `run_node(...).notifications`。

### 用 sfly-std 的辅助函数
- 节点里要起停后台进程、跑命令、采样整机或进程的资源、跟随日志、等端口、文件或日志行、从另一台 Agent 拉文件时，先用 `sfly-std` 的辅助函数（`sfly_std.commands`、`processes`、`resources`、`logs`、`waiting`、`agent_files`，函数、参数和完整示例见开发文档「标准节点」页，每个函数的文档字符串写明了抛出什么异常），在自己的节点里导入、组合，不要重写进程组的起停、日志轮转、判断文件写完这类逻辑；业务本身的逻辑（调用被测系统的协议、判断结果对不对）仍然写在自己的节点里。
- 用到它就把 `sfly-std` 写进 `[project].dependencies`（只写下限，例如 `sfly-std>=0.4`）。它不在 PyPI 上：这是下面「依赖必须能从 PyPI 镜像安装」的例外，由控制面的包索引提供（`sfly init` 生成的项目已经绑定它，开发机上 `uv add sfly-std` 就能装上，Agent 装依赖时也从它取）；索引里的是公共项目里已发布的版本，要先由平台管理员发布（这个办法在 #573 合入之后才有；用户文档「标准节点」页写了现状）。只导入文档里列出的模块和名字，下划线开头的模块（`sfly_std._process` 这类）是内部实现，不要导入。
- 启动后台进程的节点：要么在 `try`/`finally` 里用 `stop_background_process` 停掉，要么在场景里加一个停止它的节点（设为 always 节点）。在 `finally` 里停要在平台给的收尾时间（默认 10 秒）内做完：`stop_background_process` 的 `grace` 默认 5 秒、取消或超时（`ctx.cancelled()` 为真）时最多 3 秒，别把它调到接近 10 秒；这些是每次调用的上限，不是整个收尾的预算，每停一个忽略 SIGTERM 的服务就要用掉约 3 秒，所以在 `finally` 里停四个及以上服务时把 `grace` 给小；服务退出慢、要更长的宽限期就用单独的 always 节点停。保存文件为产物时 `ctx.artifacts.save(名称, 路径)` 要传 `Path`（`start_background_process` 返回的 `log_path` 就是 `Path`），传字符串保存的是这段字符串本身。
- 同一个节点里多次调用辅助函数是正常用法：默认的产物名、日志文件名每次调用不同，前一次的不会被覆盖；要自己决定名字就传 `stdout_artifact`、`csv_artifact`、`log_path` 这类参数。字段后缀：`*_path` 是本地路径、`*_artifact` 是产物名称、`*_ref` 是产物引用（下载地址，不是本地路径，别拿去 `open`）。

### 取消与清理
- 取消或超时时，节点里会抛出 `sfly.Cancelled`（`BaseException` 的子类）。捕获异常时写 `except Exception` 或更具体的类型，让 `Cancelled` 继续往外传；清理代码放在 `finally` / `with` 里，宽限期 10 秒内要做完。后台线程轮询 `ctx.cancelled()`。
- 节点结束后还要存活的资源（启动的进程、造的测试数据）：由创建它的节点输出句柄，清理写成另一个节点，并提醒用户在场景里把它设为 always 节点。

### 状态与依赖
- 状态只放在函数的局部变量里：每个任务是一个新进程，同一节点的多个任务可能并发。临时文件用 `tempfile`；路径从参数或 `ctx` 取得。
- 依赖写进 `[project].dependencies`，只写宽松的下限（如 `requests>=2.28`）：Agent 上所有节点包共用一个 venv，钉死版本最容易和别的节点包冲突。依赖必须能从 PyPI 镜像安装（`sfly-std` 除外，见上）。`sfly` 只放在 dev 依赖组里，因为 Agent 自带 SDK 运行时。
