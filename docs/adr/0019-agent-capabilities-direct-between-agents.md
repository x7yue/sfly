# Agent 能力由节点直接调用，Agent 之间直连，数据不经过控制面

一次运行里，A 机器上的被测系统会产生上百 GB 的轮转日志，清洗很吃资源，要放到 B 机器上的 Agent 去做。平台原先只有两种跨 Agent 传数据的办法：节点输出（JSON，不超过 1 MB，节点成功结束后才有）和产物（任务结束后才上传到控制面，单个任务默认不超过 1 GB），都传不了这个量级，也都要经过控制面。所以平台新增 **Agent 能力**：Agent 自身提供一组操作，节点在执行中通过 SDK 的 `ctx.agent()` 调用自己所在 Agent 的能力，通过 `ctx.agent("名称")` 调用另一台 Agent 的能力，两种写法和能力集合相同。调用另一台 Agent 时由两台 Agent 直接通信，为此 Agent 第一次对外监听端口，控制面记录每台 Agent 的地址。

第一批能力是文件：列出、查看属性、流式读取、下载（可续传）、写入、删除、监听目录变化。随后加入执行命令。

## 规则

- **寻址**：节点把要访问的 Agent 声明成一个「Agent」类型的输入参数，画布上用下拉框选择。节点只能访问这样拿到的 Agent 和自己所在的 Agent，这样触发前可以检查目标 Agent 已注册、版本支持所需的能力。Agent 在注册时上报自己支持的能力和版本。
- **地址**：默认用控制面看到的 Agent 连接来源地址；安装 Agent 时可以显式配置对外地址和端口，配置了就以它为准。
- **连不通就失败**：两台 Agent 之间不通时，任务以写明两端和端口的错误失败，控制面不代为中转。
- **执行命令归属于发起调用的任务**：输出进调用方任务的日志，必须带超时，调用方任务结束、被取消或被停止时远端命令一并结束；不占远端 Agent 的槽位，不产生任务，不用来启动常驻进程（那仍然把 `start_process` 节点派到那台机器上）。
- **平台不判断文件是否写完**：监听只报告发生了什么（新建、改名、写完关闭、删除）。一个日志文件算不算「不会再续写」取决于被测系统的轮转方式，由用户的节点决定。
- **不做认证**：和发布接口、产物下载一样，内网使用，只写进文档。

## Considered Options

- **每个场景里放一个「文件服务」标准节点**：不用改 Agent，但每个场景都要多一个常驻节点和一条子流程，占一个槽位，还要处理它留下的进程；每加一种跨机器的需求就要再设计一种服务节点。
- **经控制面中转（放宽产物上限、支持运行中上传）**：不用开新端口，但上百 GB 会占满控制面的磁盘和带宽，控制面成为所有传输的瓶颈。
- **平台不支持，用户用 Shell 节点跑 `rsync` / `scp`**：每个用户都要自己配免密、把 IP 写进参数，平台也看不出节点之间的依赖。
- **只做一个文件服务，不抽象成能力**：本次够用，但以后查看进程、端口、执行命令都要各自重新设计端口、寻址和版本检查。

## Consequences

- Agent 多了一个需要在防火墙上放行的监听端口；安装文档和 Agent 页面要显示每台 Agent 的地址和端口，便于排查不通的情况。
- 调用另一台 Agent 的能力比调用本机慢，而且会失败；SDK 接口要暴露超时和续传，不能假装两者一样。
- 监听基于 inotify，只在 Linux 的本地文件系统上可靠；事件可能丢失（监听开始之前、断线期间），所以监听先给出当前文件的快照再推送事件，重连后重新给快照，由调用方去重。
- 节点包用到某个能力时，要能声明所需的最低 Agent 版本，否则旧 Agent 上会运行到一半才失败。
- 远程写入、删除和执行命令让节点能改动另一台测试机；由于任何人本来就能发布执行任意代码的节点包并派到任意 Agent，这没有扩大攻击面。
