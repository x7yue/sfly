# 平台提供标准节点包 sfly-std，以普通 Python 节点包发布，不做 Agent 原生节点

平台原先只编排节点，节点全部由用户用 SDK 开发。Shell 命令、后台进程启停、系统与进程监控、等待条件、跟随日志文件、收集产物、HTTP 请求与断言、JSON 断言这类与业务无关的节点，每个团队都要重复开发，所以平台随控制面发布一个**标准节点包** `sfly-std`。它就是一个普通的 Python 节点包：在 Agent 上执行、场景按版本锁定、可以用 `sfly run` 和 `sfly.testing` 调试，也可以依赖第三方库（只写宽松的下限）。版本号跟随平台发布，控制面启动时自动登记镜像里带的版本，旧版本保留；包名前缀 `sfly-` 留给平台。业务节点仍由用户开发。

## Considered Options

- **Agent 原生节点（Rust 实现，编译进 Agent，Agent 以子命令启动自身执行）**：省掉 Python 解释器。实测 Python 执行器启动约 27 ms，每秒读 `/proc` 的监控循环约占 0.4% 单核、15 MB 内存，第一批节点都用不上这点性能；代价是要用 Rust 再实现一套上报协议、手工维护元信息、不能按版本锁定（Agent 换二进制后旧版本代码就没了）、不能本地调试，节点开发分成两条路。只有将来 `pnpm perf` 实测 Python 成为瓶颈的节点（例如高 QPS 的压测发生器）才值得考虑。
- **叫「内置节点」**：内置节点专指在控制面上执行、不占 Agent 的节点（定时、Sleep、停止子流程），标准节点在 Agent 上执行，混用会误导。

## Consequences

- `sfly-std` 和用户节点包装在同一个共享 venv 里（ADR 0002），它的依赖与用户节点包冲突时安装以 `env_error` 失败；依赖只写宽松下限、选用常见的库来降低概率。
- Shell 等节点让任何能编辑场景的人都能在 Agent 上执行命令；由于发布接口本来就没有认证、任何人都能发布执行任意代码的节点包，这没有扩大攻击面，只写进文档，等平台有了认证再统一处理权限。
