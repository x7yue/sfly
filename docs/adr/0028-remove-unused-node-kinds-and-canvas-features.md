# 删掉没有真实使用的节点种类和画布功能，读取时认得已移除的节点，不改已保存的版本

对目前唯一的真实使用方做过一次只读核对（3 个场景、33 个节点、16 个自己写的节点类型）：飞书通知节点、定时节点、Sleep 节点、便签都一处没有用到。飞书通知节点还是被明确弃用的：它只能把前面节点的输出嵌进文字，失败的节点没有输出，卡片里全是空值，也不能按输出的值决定内容；使用方改成在自己的节点里用 `ctx.notify` 发卡片。「几点做什么」由节点自己按被测机的时钟判断，定时节点和 Sleep 节点没有用武之地。在线编辑者（画布上的头像提示）不适用：场景主要由助手和命令行改，路线图（#442）定了用「哪个会话正在改这个场景」取代它。

这些种类和功能各自带着一条贯穿场景文档格式、引擎、画布、检查器、命令行和文档的实现。留着它们，后面每一步重构都要多带一种没人用的情况，助手搭场景时也多一种选错的可能。路线图的目标是把平台重构成以平台内的 AI 助手为核心的编排，所以只留真正在用的。这份决定分四个改动落地，一个一个来（它们改的是同一批文件）：飞书通知节点、定时与 Sleep 节点、便签、在线编辑者；每个改动在「各项」里补上自己的一节。

## 规则

- **存量数据：只读显示，不迁移。** 场景版本是不可变的记录（ADR 0023），不写会改动已保存版本的迁移：
  - 历史运行照常能看：运行监控、时间线、日志里，已移除的节点显示成「已移除的节点类型」加它当时的种类名（例如 `已移除的节点类型 feishu_notify`），状态、输入、输出照常，不报错；
  - 最新版本里还含有已移除节点的场景：读出时认得它们，配置原样带着（想改写成别的做法的人要读到旧配置）；画布打开时提示哪些节点已不再支持、怎么替换，它们画在原来的位置上，检查器里写明替换办法并只读地列出当时的配置；预检阻断触发（`node_kind_removed`）并给出同样的说明；
  - 带着已移除节点的文档**保存不了**：控制面返回 400 `invalid_document`，错误信息写明是哪些节点、怎么替换；画布上这类节点是字段错误，保存按钮把人带到它那里。在画布上删掉它们（前后的节点自动接上）之后可以正常保存，旧版本不动；
  - 恢复历史版本、复制场景原样带着已移除的节点，读到的文档、版本对比、版本画布都认得它们。
  - 命令行：`sfly scenario push` 的本地校验遇到已移除的种类时写明「已移除的节点类型 …」和替换办法，不再只说「不是已知的节点类型」；运行输出里的节点类型同样写成「已移除的节点类型 …」。命令行里有一份同样的清单（`sdk/python/src/sfly/cli/removed_nodes.py`），测试逐项核对它和 `REMOVED_NODE_KINDS` 一致。
- **一处登记，处处取用**：已移除的种类和它们的替换办法写在 `@sfly/schema` 的 `REMOVED_NODE_KINDS`；场景文档 schema 里不再有它们的定义（可以保存的文档 `OrchestrationDocument` 不含，导出给命令行的 JSON Schema 里也没有），读到的文档 `StoredOrchestrationDocument` 多出的只是一个占位类型 `RemovedNode`（共有的字段和种类名）。新移除一种节点，在这里加一项、在文档 schema 里删掉定义，其余地方（读取、运行记录、预检、画布提示）跟着走。
- **API 客户端的类型**：保存请求的文档类型 `OrchestrationDocumentInput` 改名为 `OrchestrationDocument`（不含已移除的种类），响应里的文档类型改为 `StoredOrchestrationDocument`（节点多一个 `RemovedNode`）；运行视图、场景列表缩略图里节点的 `kind` 仍可能是已移除的种类名。

## 各项

### 飞书通知节点

- **通知只留两条路**：节点代码里的 `ctx.notify`，和运行结束时的运行通知。飞书机器人的管理（登记、发送测试消息、删除前列出引用）、控制面的发送队列与投递（ADR 0020：重试、限速、积压、截断、重启续投）、`ctx.notify`、运行通知都不变。删掉的只是第三种消息来源：引擎不再有「轮到飞书通知节点就组装消息入队」这一步，消息入队不再有 `node` 这个来源，删除机器人前的引用列表里没有「飞书通知节点」这一项（`FeishuBotReference` 少了 `feishu_notify_node`）。
- **替换办法**：在节点代码里用 `ctx.notify`。链尾放一个总是执行的汇总节点、用 `${{ run.state }}` 拿到这次运行各节点的状态和错误再用 `ctx.notify` 发，是后续任务（#452）要做的；在它实现之前，节点里直接发。
- **场景文档**：`feishu_notify` 节点种类以及它的 `format`、`text`、`at_all`、`title`、`color`、`markdown`、`message`、`bot` 字段从文档 schema 里消失；`always` 可用的种类少了它。
- **检查**：不再有 `feishu_bot_unset`、`feishu_bot_reference_unsupported` 两种警告（它们只属于这个节点）；「飞书机器人」类型的输入（`sfly.FeishuBot`）的检查不变。
- **不再需要的代码**：控制面里只为节点组装 Markdown 卡片的 `markdownCard`、引擎里「飞书通知节点按 always 的规则解析引用」的特例和只为它存在的任务日志收尾一并删除；`sfly.feishu.card`（SDK，给 `ctx.notify(message=...)` 用）不变。

## Considered Options

- **写迁移，把旧版本里的已移除节点改成别的写法**：场景版本不可变，迁移要改写已保存的记录；而且没有哪种写法能原样替代（飞书通知节点要换成在哪个节点里发、发什么，取决于场景）。
- **读到已移除的节点就报错**：历史版本、历史运行、版本对比都会打不开；使用方已保存的场景升级后看不了历史。
- **保留已移除节点的执行（只是不让新建）**：每一步重构仍要带着它的执行语义、检查和界面，等于没删。
- **读到的文档里直接丢掉已移除的节点**：打开最新版本时前后的连线断开，历史版本看不全，也读不到旧配置。

## Consequences

- 场景文档少了 `feishu_notify` 节点种类；API 客户端里 `FeishuNotifyNode`、`FeishuNotifyNodeInput`、`FeishuMessageFormat`、`FeishuCardColor` 删除，`OrchestrationNode` 少了它，`StoredOrchestrationDocument`、`StoredNode`、`RemovedNode` 新增，`OrchestrationDocumentInput` 改名为 `OrchestrationDocument`；有飞书通知节点的已有场景要在节点里改用 `ctx.notify`，旧配置可以在它的检查器里或经版本接口读到。
- 升级时还在运行、版本里留着飞书通知节点的运行：走到它时它按配置错误（`config_error`，不重试）失败，这条链后面的普通节点跳过、总是执行的节点照常执行，运行以失败结束；不会拖住同一个 Agent 上别的运行。要避免，升级前让这样的运行跑完。
- 记在发送队列里的历史消息 `source` 还会是 `node`；读的地方不分来源，所以不留在类型里。
- 删掉的测试里，只测这个节点的行为（配置校验、引用解析、三种格式）的随它删除，和来源无关的投递规则（顺序、限速、重启续投、保留期）改用别的消息来源继续覆盖。
