# 删掉没有真实使用的节点种类和画布功能，读取时认得已移除的节点，不改已保存的版本

对目前唯一的真实使用方做过一次只读核对（3 个场景、33 个节点、16 个自己写的节点类型）：飞书通知节点、定时节点、Sleep 节点、便签都一处没有用到。飞书通知节点还是被明确弃用的：它只能把前面节点的输出嵌进文字，失败的节点没有输出，卡片里全是空值，也不能按输出的值决定内容；使用方改成在自己的节点里用 `ctx.notify` 发卡片。「几点做什么」由节点自己按被测机的时钟判断，定时节点和 Sleep 节点没有用武之地。在线编辑者（画布上的头像提示）不适用：场景主要由助手和命令行改，路线图（#442）定了用「哪个会话正在改这个场景」取代它。

这些种类和功能各自带着一条贯穿场景文档格式、引擎、画布、检查器、命令行和文档的实现。留着它们，后面每一步重构都要多带一种没人用的情况，助手搭场景时也多一种选错的可能。路线图的目标是把平台重构成以平台内的 AI 助手为核心的编排，所以只留真正在用的。这份决定分四个改动落地，一个一个来（它们改的是同一批文件）：飞书通知节点、定时与 Sleep 节点、便签、在线编辑者；每个改动在这份文档的末尾追加自己的一节（「第 N 步」），已接受的部分不改。

## 规则

- **存量数据：只读显示，不迁移。** 场景版本是不可变的记录（ADR 0023），不写会改动已保存版本的迁移：
  - 历史运行照常能看：运行监控、时间线、日志里，已移除的节点显示成「已移除的节点类型」加它当时的种类名（例如 `已移除的节点类型 feishu_notify`），状态、输入、输出照常，不报错；
  - 最新版本里还含有已移除节点的场景：读出时认得它们，配置原样带着（想改写成别的做法的人要读到旧配置）；画布打开时提示哪些节点已不再支持、怎么替换，它们画在原来的位置上，检查器里写明替换办法并只读地列出当时的配置；预检阻断触发（`node_kind_removed`）并给出同样的说明；
  - 带着已移除节点的文档**保存不了**：控制面返回 400 `invalid_document`，错误信息写明是哪些节点、怎么替换；画布上这类节点是字段错误，保存按钮把人带到它那里。在画布上删掉它们（前后的节点自动接上）之后可以正常保存，旧版本不动；
  - 恢复历史版本、复制场景原样带着已移除的节点，读到的文档、版本对比、版本画布都认得它们。
  - 命令行：`sfly scenario push` 的本地校验遇到已移除的种类时写明「已移除的节点类型 …」和替换办法，不再只说「不是已知的节点类型」；运行输出里的节点类型同样写成「已移除的节点类型 …」。命令行不另写一份清单：它读 `REMOVED_NODE_KINDS` 导出的 JSON（`sdk/python/src/sfly/schemas/removed-node-kinds.json`，`pnpm gen` 生成，`pnpm gen:check` 守着）。
- **一处登记，处处取用**：已移除的种类和它们的替换办法写在 `@sfly/schema` 的 `REMOVED_NODE_KINDS`；场景文档 schema 里不再有它们的定义（可以保存的文档 `OrchestrationDocument` 不含，导出给命令行的 JSON Schema 里也没有），读到的文档 `StoredOrchestrationDocument` 多出的只是一个占位类型 `RemovedNode`（共有的字段和种类名）。新移除一种节点，在这里加一项、在文档 schema 里删掉定义，其余地方（读取、运行记录、预检、画布提示）跟着走。
- **API 客户端的类型**：保存请求的文档类型 `OrchestrationDocumentInput` 改名为 `OrchestrationDocument`（不含已移除的种类），响应里的文档类型改为 `StoredOrchestrationDocument`（节点多一个 `RemovedNode`）；运行视图、场景列表缩略图里节点的 `kind` 仍可能是已移除的种类名。

## Considered Options

- **写迁移，把旧版本里的已移除节点改成别的写法**：场景版本不可变，迁移要改写已保存的记录；而且没有哪种写法能原样替代（飞书通知节点要换成在哪个节点里发、发什么，取决于场景）。
- **读到已移除的节点就报错**：历史版本、历史运行、版本对比都会打不开；使用方已保存的场景升级后看不了历史。
- **保留已移除节点的执行（只是不让新建）**：每一步重构仍要带着它的执行语义、检查和界面，等于没删。
- **读到的文档里直接丢掉已移除的节点**：打开最新版本时前后的连线断开，历史版本看不全，也读不到旧配置。

## Consequences

- 含已移除节点的场景要先把这些节点按替换办法改写、在画布上删掉，才能再触发和保存；历史版本和历史运行不受影响（规则见上面「存量数据」）。
- 升级时还在运行、版本里留着已移除节点的运行：规则对所有已移除的种类通用，走到那个节点时它按配置错误（`config_error`，不重试）失败，这条链后面的普通节点跳过、总是执行的节点照常执行，运行以失败结束；不会拖住同一个 Agent 上别的运行。要避免，升级前让这样的运行跑完。每一步的细节（有没有输出、升级时停在它上面的任务怎么办）写在各自的一节里。
- 每一步落地都改动 API 客户端的类型，是不兼容变化（`breaking-change`）；具体写在各自的一节和对应 PR 里。
- 删掉的测试里，只测节点或功能本身行为的随它删除；和它无关的规则改用别的路径继续覆盖。

## 第 1 步：飞书通知节点

- **通知只留两条路**：节点代码里的 `ctx.notify`，和运行结束时的运行通知。飞书机器人的管理（登记、发送测试消息、删除前列出引用）、控制面的发送队列与投递（ADR 0020：重试、限速、积压、截断、重启续投）、`ctx.notify`、运行通知都不变。删掉的只是第三种消息来源：引擎不再有「轮到飞书通知节点就组装消息入队」这一步，消息入队不再有 `node` 这个来源，删除机器人前的引用列表里没有「飞书通知节点」这一项（`FeishuBotReference` 少了 `feishu_notify_node`）。
- **替换办法**：在节点代码里用 `ctx.notify`。链尾放一个总是执行的汇总节点、用 `${{ run.state }}` 拿到这次运行各节点的状态和错误再用 `ctx.notify` 发，是后续任务（#452）要做的；在它实现之前，节点里直接发。
- **场景文档**：`feishu_notify` 节点种类以及它的 `format`、`text`、`at_all`、`title`、`color`、`markdown`、`message`、`bot` 字段从文档 schema 里消失；`always` 可用的种类少了它。
- **检查**：不再有 `feishu_bot_unset`、`feishu_bot_reference_unsupported` 两种警告（它们只属于这个节点）；「飞书机器人」类型的输入（`sfly.FeishuBot`）的检查不变。
- **不再需要的代码**：控制面里只为节点组装 Markdown 卡片的 `markdownCard`、引擎里「飞书通知节点按 always 的规则解析引用」的特例和只为它存在的任务日志收尾一并删除；`sfly.feishu.card`（SDK，给 `ctx.notify(message=...)` 用）不变。
- **API 客户端的类型**：`FeishuNotifyNode`、`FeishuNotifyNodeInput`、`FeishuMessageFormat`、`FeishuCardColor` 删除，`OrchestrationNode` 少了它，`FeishuBotReference` 少了 `feishu_notify_node`；`StoredOrchestrationDocument`、`StoredNode`、`RemovedNode` 新增，`OrchestrationDocumentInput` 改名为 `OrchestrationDocument`。
- **已有场景**：有飞书通知节点的场景要在节点里改用 `ctx.notify`，再删掉这个节点；旧配置可以在它的检查器里或经版本接口读到。
- **升级时还在运行的运行**：版本里留着飞书通知节点的运行，走到它时它按配置错误失败（通用规则见上面「Consequences」）；这个节点没有输出，后面的节点不会因此拿到空值。
- **发送队列里的历史消息**：`source` 还会是 `node`；读的地方不分来源，所以不留在类型里。
- **删掉的测试**：只测这个节点的行为（配置校验、引用解析、三种格式）的随它删除；和来源无关的投递规则（顺序、限速、重启续投、保留期）改用别的消息来源继续覆盖。

## 第 2 步：定时节点和 Sleep 节点

第 1 步（飞书通知节点）合入之后追加的一节：同一份决定的第二个改动，规则（存量数据只读显示、不迁移、一处登记）沿用上面，不重写。

- **一起删，连同只为它们存在的东西**：控制面的定时扫描（周期唤醒到期的 `waiting` 任务）和它的选项 `timerSweepIntervalMs`、任务表的 `wake_at` 列和索引 `tasks_waiting`（迁移 `0030_remove_task_wake_at`）、API 里的 `wake_at`（运行视图的每次尝试、运行列表里进行中的节点）和平台指标里每个节点的 `wait_ms`、检查器里的时刻/时区/时长表单、卡片上的摘要和运行时的剩余时间进度、监控里的「唤醒」时间和节点耗时图里的等待条、时间线上把它们画成等待段。时间解析（`parseDuration`、`timerTarget`、`isTimeZone`）和它们的静态检查（`sleep_duration_invalid`、`timer_at_invalid`、`timer_tz_invalid`）随之删除。
- **别的时间机制不动**：任务超时、排队超时、租约、运行通知的时间都留着。`waiting` 任务状态也留着：停止子流程节点等被停止的子流程结束时用它；画布和监控上琥珀色的「等待中」从此只有这一种来源。
- **替换办法**：定时节点——在节点代码里等到那个时刻，或把场景拆成两次运行；Sleep 节点——在节点代码里等待，或把场景拆成两次运行。「几点做什么」本来就由节点按被测机自己的时钟判断（ADR 0018）。
- **升级时还在等待的**：旧版本里正在 `waiting` 的定时、Sleep 节点任务，唤醒它们的扫描没有了。控制面启动时（`Engine.recover`）把这些任务按 `config_error` 失败（找它们靠节点种类，不靠 `wake_at`，所以那一列可以删），链按失败的规则往后推进；同样，升级前开始、还没走到它们的运行，走到时在 `#advance` 里同样失败。停止子流程节点的 `waiting` 不受影响。
- **它们原来有输出，别的节点可能引用着**（定时节点：`triggered_at`、`late`；Sleep 节点：`triggered_at`）：节点还在场景里时，引用检查读不到它的输出声明，不报；删掉它之后，下游的引用报 `reference_unknown_node`（「节点 X 的输入 v 引用了不存在的节点 at」，保存时是警告，触发时阻断），要把那些引用也改掉。所以画布顶部的提示和检查器里对有输出的已移除种类多写一句「引用了它的输出的节点也要一起改」（输出名登记在 `REMOVED_NODE_KINDS` 的 `outputs` 里，没有输出的种类写空数组）。升级时还在运行的运行里，总是执行的下游节点引用到它的输出时，按 docs/SEMANTICS.md §2.4 的老规则（缺失的输出解析为 `null`）处理。
- **对 ADR 0018 的影响**：它写的「等待节点（定时节点也按控制面时间理解）」不再适用，别的不变（见那份 ADR 末尾的指针）；ADR 0017 里「内置节点（定时、Sleep、停止子流程）」的列举也少了前两项。

### 对 API 客户端和使用方的影响

- 场景文档里没有 `timer`、`sleep`；API 客户端里 `TimerNode`、`SleepNode`（及 `…Input`）删除，`RemovedNode.kind` 多了 `"timer" | "sleep"`，`AttemptView.wake_at`、`RunListActiveNode.wake_at`、平台指标节点项的 `wait_ms` 删除（响应里去掉字段）；有这两种节点的已有场景要改成在节点里等待或拆成两次运行。
- 历史运行里它们的唤醒时间和等待时长不再显示（列和字段没了）；开始、结束时间和状态照常。

### 没有采纳的做法

- **只删定时节点、留 Sleep 节点**：真实使用方两者都没用到，Sleep 也只是「在节点里等一会」，节点代码里一行就能做到。
- **留着 `wake_at` 列只读显示历史**：列只为定时扫描存在，留着等于留着「等到某个时刻」的语义；历史的开始、结束时间已经够用。

## 第 3 步：便签

第 2 步（定时节点和 Sleep 节点）合入之后追加的一节：同一份决定的第三个改动。便签不是节点，是场景文档顶层的 `sticky_notes` 字段，所以存量数据的处理和前两步不一样（下面「存量数据」）。

- **一起删**：画布上的便签（显示、新建、拖动和缩放、检查器、工具栏和右键菜单里的入口、快捷键、大纲和小地图里的便签、版本画布和版本对比里的便签）、整理布局里「便签排在最上面一行」的规则、命令行读写便签（`scenario pull / push / show` 里的便签、`sfly scenario` 里的便签子命令）、文档里的 `sticky_notes` 字段和 `StickyNote` 类型（含便签的大小、颜色常量和显示文字的写法）、便签专用的设计 token 和样式。注释框、注释框的备注、注释框的颜色（ADR 0023、0025）不动。
- **替换办法**：没有对应的功能；要留的内容写进节点的备注（说明一个节点）或注释框的备注（说明一组节点）。ADR 0026 自己也是这么区分的。
- **存量数据**：ADR 0026 之后保存的每个版本都带着 `sticky_notes`（默认空数组，也可能有内容）。
  - 读取：认得并丢掉。读库、恢复浏览器里的本地草稿、比较两个文档时，先去掉文档顶层已移除的字段（`withoutRemovedFields`），再按现在的 schema 解析；历史版本、历史运行、版本对比、恢复、复制都不报错，读到的文档里没有它，也不显示。不像已移除的节点那样占位显示：便签不执行、没有连线，丢掉它不影响任何运行。
  - 不阻断触发：预检不因为便签报警告或阻断。
  - 保存分两种情况：
    - 没有 `sticky_notes`，或者是空数组：接受并丢掉，不报错，新版本里没有它。几乎所有已保存的版本都带着 `sticky_notes: []`，「读出来改一处再存回去」是自建页面和命令行最常见的写法，不该因为一个空数组被拒绝。做法：请求里的文档 schema 只收这个字段的空数组（`maxItems: 0`，导出的 JSON Schema 里同样，命令行本地校验和控制面一致），控制面存库前去掉它。
    - 数组里有内容：拒绝（400 `invalid_document`），错误信息写明有几条、怎么办（「场景文档里的 sticky_notes（便签）有 N 条内容，已不再支持，不能保存：先把要留的内容挪走，再把这一项删掉」）；命令行 `scenario push` 的本地检查写同一句。读取时丢掉的内容不能在保存时再不声不响地丢一次。
  - 画布从状态生成的文档、恢复历史版本、复制场景产生的新版本都不带 `sticky_notes`。
  - 已保存的版本一个字节都不动，不写迁移。
  - **升级后有内容的便签读不到了**：版本里还在，但读取接口、命令行 `scenario pull`、画布都不再给出。要留的内容请在升级前导出，写进节点的备注或注释框的备注：
    - 升级前，直接读旧版本的接口：`GET /orchestrations/<场景 id>/versions/<版本号>` 返回的文档里有 `sticky_notes`；命令行 `sfly scenario pull <场景> --version <版本号> -o 文件`，文件里的 `document.sticky_notes` 就是便签的内容（升级前的命令行才会写出它）。
    - 升级后，直接查库：`select o.name, v.number, v.document -> 'sticky_notes' as sticky_notes from orchestration_versions v join orchestrations o on o.id = v.orchestration_id where jsonb_array_length(coalesce(v.document -> 'sticky_notes', '[]'::jsonb)) > 0 order by o.name, v.number;`（只列有内容的版本；每个场景的最新版本就是它现在的便签）。
  - 登记在 `@sfly/schema` 的 `REMOVED_DOCUMENT_FIELDS`（和 `REMOVED_NODE_KINDS` 并列）：移除下一个顶层字段，在那里加一项、在文档 schema 里改成只收空数组的写法，读取、保存的说明和命令行都跟着走。
- **升级时还没保存的本地草稿**：浏览器里按旧格式存着的草稿可能带着 `sticky_notes`，恢复时同样先丢掉这个字段，草稿里其余的修改照常恢复。
- **对 API 客户端和使用方的影响**：`StickyNote` 类型删除，读到的文档（`StoredOrchestrationDocument`）里没有 `sticky_notes` 字段；保存请求的文档类型（`OrchestrationDocument`）里它是 `sticky_notes?: unknown[]`，只收空数组。读出来原样存回去照常可用（读到的文档里本来没有它）；自建页面或脚本里存着升级前的旧文档、里面的 `sticky_notes` 有内容的，推送前要先把内容挪走、去掉这一项。`@sfly/orchestration` 的 `diffDocuments` 结果里没有 `stickyNotes` 了。
- **没有采纳的做法**：
  - **带着 `sticky_notes` 保存一律拒绝**：几乎所有旧文件和读出来再存回去的写法都带着一个空数组，会被无谓地拒绝；只拒绝有内容的，空数组不会丢掉任何东西。
  - **保存时一律悄悄忽略 `sticky_notes`**：文件里有内容的便签会不声不响地丢掉，推送的人不知道。
  - **像已移除的节点那样占位显示便签**：占位要有卡片、检查器、横幅和一条「删掉才能保存」的规则，而便签不执行、没有连线，读不到旧内容的代价（升级前或直接查库能导出）远小于这些。
  - **写迁移把便签搬进节点备注**：版本不可变；便签不挂在任何节点上，没有一种搬法是对的。

## 第 4 步：在线编辑者

第 3 步（便签）合入之后追加的一节：同一份决定的最后一个改动。在线编辑者是编辑页面右上的头像提示，显示同一个场景还有谁打开着编辑页面；它没有任何持久化的数据，所以没有存量数据要读。

- **一起删**：三个接口——`POST /orchestrations/:id/presence`（编辑页面每 10 秒一次的心跳，带昵称和会话 ID）、`POST /orchestrations/:id/presence/leave`（关闭页面时主动离开）、`GET /orchestrations/:id/presence/events`（SSE，事件 `editors` 推送名单）——连同契约里的 `presenceApi`、`OnlineEditorView`、`EditorsEvent` 和它们的接口声明、`READS_WITH_TRACES` 里为心跳和离开做的登记（它们是这张表仅有的两项：表和对它的检查保留，现在是空表）；控制面里内存中的名单 `PresenceRegistry`（30 秒无心跳移除）和它的周期清理；编辑页面里的 `OnlineEditors` 头像、`useOtherEditors`（`lib/presence.ts`）和右上控件组里它的位置；设计规范和架构文档里关于它的说明；只读测试和 CORS 测试里借它造数据的部分。
- **不动**：保存时的乐观锁和冲突处理（版本冲突、`DraftBanner` 里「另一个标签页修改了本地草稿」）；昵称（版本作者、运行触发人）——ADR 0004 里「防止并发修改依靠编排版本的乐观锁和在线编辑者提示」这一条只剩乐观锁。
- **不做替代品**：取代它的「谁正在改这个场景」不靠心跳、不认请求里给的任何标识，由平台自己知道的事实算出（ADR 0029），在多用户的任务（#495）里做，不在这一步。删掉的同时也去掉了 ADR 0029 记下的一个已知问题：任何有读权限的调用方都能用别人的会话标识让别人从「谁在编辑」里消失。
- **升级时还开着的旧页面**：它们继续每 10 秒发一次心跳，收到 404，刷新页面之后就没有了；404 不影响页面别的功能（保存、运行状态、实时推送走别的路径）。
- **对 API 客户端和使用方的影响**：API 客户端（`@sfly/client`）的类型和调用没有变——这三个接口本来就没有开放给客户端（契约里 `client: false`）；`sfly api` 的路由清单（随 SDK 打包的 `routes.json`）少了这三项；自建页面或脚本如果直接请求这三个路径，现在得到 404，没有替代。
- **没有采纳的做法**：
  - **只去掉界面、留着接口**：接口和内存里的名单仍然要维护、要在契约里声明和测试，而且那个已知问题还在。
  - **现在就做替代品**：替代品的前提是用户和项目（ADR 0029），那之前没有可靠的「谁」可以显示。
