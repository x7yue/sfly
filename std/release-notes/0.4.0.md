## 从 0.3.0 升级：删掉的节点和怎么替换

0.4.0 把 sfly-std 改成「节点代码里可以直接调用的辅助函数，加三个节点」（ADR 0030）：只保留 `shell`、
`start_process`、`stop_process` 三个节点，行为和 0.3.0 一致；其余 14 个节点删除，对应的逻辑成了辅助函数
（`from sfly_std.<模块> import …`），在自己的业务节点里调用。已发布的 0.3.0 不变，锁定它的场景仍然可以用，但同一台 Agent 上不能同时用 0.3.0 和 0.4.0（见表后面的说明）；
要升级到 0.4.0 的场景，引用了被删节点的地方按下表改成自己的节点。

升级后场景里还引用着被删的节点时：保存和 `sfly scenario check` 的警告写「节点包 sfly-std@0.4.0 中没有节点类型 assert（0.4.0 起删除了：替换办法见开发文档「标准节点」页的「从 0.3.0 升级」一节）」，触发前的预检在「包版本锁定」这一项阻断。照下表把这些节点改成自己的节点，或者把 `sfly-std` 的版本选回 0.3.0（画布上升级和选回都是一键的）。

| 删掉的节点 | 怎么替换 |
|---|---|
| `system_monitor` | 自己的节点里调用 `sfly_std.resources.monitor_system`（指标和图表声明：`SYSTEM_METRICS`、`SYSTEM_CHARTS`） |
| `process_monitor` | `sfly_std.resources.monitor_processes`（`PROCESS_METRICS`、`PROCESS_CHARTS`）；新增参数 `refind_within`：进程重启后按名字重新找到它、接着监控；节点的 `wait_for_process` 在函数里叫 `appear_within`，节点输出的 `processes_csv` 是结果的 `csv_ref` |
| `wait_port` | `sfly_std.waiting.wait_for_port` |
| `wait_file` | `sfly_std.waiting.wait_for_file` |
| `wait_log_line` | `sfly_std.logs.wait_for_log_line` |
| `follow_log` | `sfly_std.logs.follow_log_file`（指标声明：`FOLLOW_METRICS`） |
| `collect_artifacts` | 自己的节点里用 `ctx.artifacts.save(名称, Path(文件))` |
| `pull_files` | `sfly_std.agent_files.pull_files_from_agent`（`directory`、`local_dir` 只能按关键字传；节点输出的 `files` 是结果的 `paths`，元素是 `Path`） |
| `watch_files` | `sfly_std.agent_files.watch_agent_files`（`directory`、`local_dir` 只能按关键字传；指标声明：`WATCH_METRICS`） |
| `http_request` | 自己的节点里直接用 `httpx`（写进节点包自己的依赖）；要重试到成功用 `sfly_std.waiting.poll_until` |
| `assert` | 阈值和判断写在自己的节点代码里，不满足就抛异常 |
| `file_assert` | 自己的节点里读文件、判断后抛异常（等文件写完用 `sfly_std.waiting.wait_for_file`） |
| `process_assert` | 自己的节点里用 `sfly_std.processes.find_processes(…, include_children=False)` 数进程（`include_children` 默认 True，会连子进程一起找出来）、判断后抛异常。注意：`find_processes` 的 `pid`、`name`、`match` 是**满足其中任意一个就算**，0.3.0 的 `process_assert` 同时给几个时要求**全部满足**；要全部满足，就按一个条件找、再自己过滤，写法见表后面的示例：`p.cmdline()` 可能抛 `psutil.NoSuchProcess`（进程刚退出）或 `psutil.AccessDenied`（macOS 上读别的用户的进程），0.3.0 把它们当作不匹配，过滤时同样接住 `psutil.Error` |
| `port_assert` | 自己的节点里用标准库 `socket.create_connection` 检查端口（等端口出现用 `sfly_std.waiting.wait_for_port`） |

`process_assert` 同时要求名字和命令行都满足时的写法（0.3.0 的 `name` 加 `match`）：

```python
import re

import psutil
from sfly_std.processes import find_processes


def runs_server(p: psutil.Process) -> bool:
    """命令行里有 server.py；进程刚退出（NoSuchProcess）、读不了命令行（AccessDenied）当作不匹配。"""
    try:
        return re.search(r"server\.py", " ".join(p.cmdline())) is not None
    except psutil.Error:
        return False


matched = [p for p in find_processes(name="python", include_children=False) if runs_server(p)]
```

依赖的变化：0.4.0 只依赖 `psutil`；`httpx` 随 `http_request` 一起去掉了，要用的节点包自己依赖它。

**两个版本不能在同一台 Agent 上共存。** 一台 Agent 的环境里只能有一个 `sfly-std`（一台 Agent 上所有节点包共用一个环境，见开发文档「安装 Agent」页），所以锁定 0.3.0 的场景和依赖 `sfly-std>=0.4` 的节点包（上表替换办法里「写进依赖」的那种）不能在同一台 Agent 上并存：这台 Agent 装过依赖 `sfly-std>=0.4` 的节点包之后，锁定 0.3.0 的场景在它上面执行 `sfly-std` 的节点，任务以 `env_error` 失败；反过来，先装了 0.3.0、后来又装依赖 `>=0.4` 的节点包，环境里的 0.3.0 会被换成 0.4.0，之后锁定 0.3.0 的任务同样失败。撞上时看到的是 uv 的原话，写着 `No solution found when resolving dependencies` 和 `Because only sfly-std<0.4 is available and you require sfly-std>=0.4`（版本号照抄依赖它的节点包里写的下限：写 `>=0.4.0` 就是 `<0.4.0` 和 `>=0.4.0`），不会指出是哪个节点包要求 `>=0.4`。怎么安排：同一台 Agent 上的场景一起升到 0.4.0（先把会派到这台 Agent 上的场景都升级，再装依赖 0.4 的节点包）；还要用 0.3.0 的场景留在别的 Agent 上，那些 Agent 上不装依赖 0.4 的节点包。

函数的参数、返回值和一个完整的示例见开发文档的「标准节点」页。
